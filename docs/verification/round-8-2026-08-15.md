**Correction — the functional column does not reproduce, and a claim published here was wrong.**
This document first recorded the framework arm at 7/12 rows with its `diagnostics` row failing in
both sealed scenarios, and called that a product finding. Re-running the same archive, unchanged,
scores it **9/12 with both `diagnostics` rows passing** — 0 console errors, 0 network errors, 0
runtime diagnostics. The defect did not reproduce, so it was never a product finding; it was
run-to-run variance reported as a fact, and the gap and disposition rows raised from it have been
withdrawn.

The vanilla arm scored 10/12 on both runs. The framework arm moved 7/12 → 9/12 with nothing
changed. So the framework arm still loses the functional column, by one row rather than three, and
**the column is not reproducible enough to carry a parity verdict on its own**. That is consistent
with the wall-clock dependency recorded in
`docs/verification/playtest-results-depend-on-render-speed-2026-08-15.md`: a run whose result
depends on how fast the machine renders will not repeat.

The cost column does reproduce — it is a line count, not a timing measurement — and it is the one
number in this round that means what it says.
