### Why the earlier continuation measured `0 / 67 / 0`

The guard was right and its input was wrong. Android 15 (API 35) stopped printing `mCurrentFocus`
under the `dumpsys window windows` subcommand, and both call sites asked for exactly that dump, so
the foreground check could only ever fail closed. Observed on this emulator on 2026-08-19:

```text
adb -s emulator-5554 shell dumpsys window windows   # 469 lines, zero mCurrentFocus
adb -s emulator-5554 shell dumpsys window           # mCurrentFocus=Window{2528440 u0 com.threenative.game/...MystralActivity}
```

**Harness bug, not an engine bug.** Repaired by feeding the guard the full `dumpsys window` dump
through a named helper, with a regression test carrying both real API-35 dumps as fixtures, so a
revert costs one red test instead of 66 red conformance rows. The 66 focus errors went to zero on
the next run and the captures completed at 1280x720.

### The one row that still fails

`25-camera-parented-overlay` reports `Android process exited before the conformance marker.` It
reproduces in isolation under `--only-tests`, so it is deterministic. **The process did not
crash** — logcat shows `TN_NATIVE_SMOKE_FIRST_FRAME`, then `Force stopping com.threenative.game
... from pid 14233`, the harness itself, with no ANR, no `libc` fatal signal, no `AndroidRuntime`
exception and no GPU validation error. The app reached first frame and was killed from outside
because its marker never arrived.

It is the same scene `tier-1-2026-08-10` recorded failing the *desktop* lane on GPU validation —
mismatched depth and colour attachment sizes after resize — which a 2026-08-15 desktop run measured
passing. It is the only conformance scene that resizes the swapchain mid-scene. That attribution is
[PRD-166](../PRDs/done/PRD-166-camera-parented-overlay-never-marks-on-android.md), not this ledger; this
run establishes that the row is a marker timeout and not a pixel result, and stops there.
