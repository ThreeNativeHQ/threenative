## 4. What §5 found, and why §6 must wait

### 4.1 `@threenative/playtest` does not export what `studio-probe.ts` needs — this blocks §6

`scripts/studio-probe.ts` is the judging harness that makes an unattended Studio loop honest. It
reaches for two things by workspace-relative deep import, which worked inside the monorepo and has
no equivalent outside it:

| Symbol | Module it lives in | In `@threenative/playtest@0.2.0`'s export map? |
| --- | --- | --- |
| `WEBGPU_BROWSER_ARGS` | the runner's browser module | **no** — not under `.` or `./runner` |
| `assertFrameShowsSomething`, `inspectFrame`, `CAPTURE_GUARD_LIMITS`, `ICaptureFrameStats` | the capture module | **no** — that module is not exported at all |

Verified by listing the published package's actual exports, not by reading its source. The engine's
own `scripts/capture-guard.ts` is a thin re-export of the same private path, so it has the same
problem.

`studio-probe.ts`, `studio-loop.ts` and their two specs therefore sit in `scripts/blocked/` in the
new repository, outside `tsconfig`'s and `vitest`'s `include`, with a README naming the missing
symbols. They are kept rather than deleted, and **not** worked around by deep-importing into
`node_modules/.../dist/` — §5.2 forbids that, and it would break on any release that reorganises the
build.

**This is why §6 cannot proceed yet.** §6.1 deletes `scripts/studio-probe.ts` from this repository.
Today that is the only copy that builds. Deleting it before `packages/playtest` exports the capture
module and `WEBGPU_BROWSER_ARGS` — and republishes — would strand the harness in both repositories at
once. The fix belongs in the engine's export map and is an engine change with its own release.

**Update, same day: the export map is fixed; the release is not.** `packages/playtest` now publishes
a fourth tier, `./capture` (pngjs only — a caller asking whether a screenshot is blank should not have
to pull playwright), and re-exports `browser.js` through `./runner` so `WEBGPU_BROWSER_ARGS` is
reachable. `__tests__/export-map.spec.ts` guards both, observed red by removing each in turn.

So §6's blocker has changed shape: it is no longer *"an engine change nobody has made"* but
*"`@threenative/playtest` needs a release"*. Publishing is a tag push on a public registry and is the
owner's call, not this file's. Once a version carrying `./capture` is on npm, the private repository
bumps its dependency, `scripts/blocked/` empties, and §6 is unblocked.

### 4.2 `LOCAL_PACKAGE_ROOTS` was six paths, not one

§5.2 describes a single mapping to repair. `src/server.ts` in fact mapped **six** package names to
`REPO_ROOT/packages/*` — core, physics, playtest, studio, ui and create-threenative — and
`localPackageSources()` **returns empty and carries on** when none of them exist. Outside the
monorepo all six are absent, so Studio would have started silently with no local sources and no
sign anything had changed.

Fixed by making the default empty *on purpose and in writing*, with
`THREENATIVE_STUDIO_PACKAGE_SOURCES` documented as the supported way for a framework developer to
point Studio back at a local checkout. That mechanism is genuinely meaningless in a standalone
repository — a scaffolded preview should resolve from the registry, which is what a user's machine
does — so empty is correct, and now it is stated rather than inferred.

Separately, and per §5.2's instruction to make the failure loud, `startStudio()` now calls
`assertScaffolderResolved()` before anything else. A broken install throws
`TN_STUDIO_SCAFFOLDER_MISSING` at startup naming the package, rather than failing at the first click.

### 4.3 `argon2` needed its build script approved, and the symptom did not say so

Without `pnpm.onlyBuiltDependencies: ["argon2"]` the native binding is never compiled, and every
hosting spec that touches auth kills its vitest worker. The run reports **`Errors 10`** and
`Worker forks emitted error` — ten *files* reporting as errors rather than as failures — while
`Test Files 12 passed` sits above it looking healthy. Nothing in that output names argon2 or says a
native module failed to load.

It is worth recording because a reader skimming for `FAIL` would have found none, and because 12 of
21 files running is precisely the shape of a suite that has quietly stopped covering what it claims.
The engine repository already carries this setting; it did not travel with the copied files.

### 4.4 Two `hosting/__tests__` specs imported Studio through the old layout

`../../packages/studio/src/agentProtocol.js` → `../../src/agentProtocol.js`. Mechanical, and caught
by typecheck rather than by reading.

### §6.3 is decided, with the evidence, so whoever runs §6 does not have to re-derive it

**The visual gate stays in this repository, and only the `STUDIO_ASSET_ROOT` branch is removed.**

`scripts/visual-gate.ts:92` defines `STUDIO_ASSET_ROOT` as `packages/studio/assets`, and it is
**write-only**: `persistTemplateCapture` writes each captured template frame there as a second copy
beside the canonical one in `docs/verification/visuals/`. Nothing in the gate reads it. Everything
the gate actually checks — the six-file render structure, the palette keys, the capture guard — is
about templates and never touches a Studio asset.

So it is not Studio's gate with a template branch; it is the template gate with a Studio-shaped
side-effect. The frames it copies are Studio's kit preview images, which the new repository already
carries in its own `assets/`.
