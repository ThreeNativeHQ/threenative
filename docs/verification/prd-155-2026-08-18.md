# PRD-155 — rendering defect sweep and native visual evidence, 2026-08-18

What executed, on what hardware, and what it showed. Device rows ran on a physical Pixel 8
(`37251FDJH0037Z`, Android, V8). Desktop rows ran on Linux/Dawn with an NVIDIA Turing GPU. Web rows
ran in Chromium against the same NVIDIA adapter.

## 0. Two corrections to the PRD's premise

**The present-once-per-frame fix landed in `fc2eb93`, not `473f9f3`.** `git log -S g_framePresentPending`
names one commit and it is `fc2eb93` ("game branding from launcher to first playable frame"), whose
diff moves the present out of `queue.submit` and into `endDawnFrame()`. What `473f9f3` did was move
the *screenshot capture* to the frame boundary, stop the early return from stranding an acquired
swapchain image, and add `g_presentCount`. PRD-155 §1 attributes both defects to `473f9f3`; only the
second is its.

This matters for the audit in §2 below, because the two defects have different blast radii.

**A device screenshot was never affected by the mid-frame capture bug.** The capture that ran
mid-frame is the runtime's own (`--screenshot` → `saveScreenshot` → GPU readback). Android evidence
comes from `adb exec-out screencap` and iOS-simulator evidence from `xcrun simctl io … screenshot`,
both of which read the composited display and never touch that path. So PRD-155 §3's claim that
"every native screenshot-based result in this repository is suspect" is too broad: it holds for the
runtime's own capture and not for OS-level device captures.

## 1. Phase 1 — device overlay and present gate

### What shipped

- `reportPresentTick()` in `packages/runtime-native/src/webgpu/bindings.cpp` emits
  `TN_PRESENTS_TICK:{"frames":N,"presents":M}` every 60 frames, on stdout everywhere, plus logcat on
  Android and `os_log` on Apple. The desktop CLI's `TN_PRESENTS` line only exists in fixed-frame
  screenshot mode; a device app never ends, so the invariant had to become readable from a running
  process. Frames and presents are emitted as a pair because the count alone proves nothing — the
  defect was presents outrunning frames, and only the ratio shows it.
- `analyzePresentTicks()` and `inspectOverlayBuffer()` in `verify-desktop-core.mjs`, shared by all
  three gates so the device lane asserts the identical thing rather than a weaker namesake.
- `verify-android-first-proof.mjs` now asserts both. Tick *presence* is required only in the final
  analysis, after the app has reported its frames: during the wait loop the app may legitimately not
  have reached frame 60, and failing there would reject every healthy run.
- `verify-ios-simulator.mjs` asserts both. **Not executed — no Apple machine on this operator box.**

### Checkpoint: the gate goes red on the unfixed runtime, on the Pixel 8

The runtime was rebuilt from `3677542`'s `bindings.cpp` (the parent of `fc2eb93`, which is the commit
that actually fixed the present) with only the tick emitter grafted on, so the gate would have
something to read.

| Runtime | Result |
| --- | --- |
| `3677542` (pre-fix) | **RED** — `presented 120 times in 60 frames; expected at most one present per frame` |
| working tree (fixed) | **GREEN** — 960 frames / 960 presents, 4,096 overlay pixels |

Logs kept: `packages/runtime-native/artifacts/android/prd155-prefix-redcheck-logcat.txt` and
`first-proof-logcat.txt`. Desktop is green in the same shape: 300 frames, 300 presents, 4,096 overlay
pixels, `desktop-linux-report.json`.

### The overlay pixel check does not detect this defect on a device, and that is worth writing down

On the pre-fix runtime a device `screencap` still found **4,096 magenta pixels** — a full overlay.
Presenting twice per frame does not remove the overlay from the display on Android; it makes the
display alternate between the two images, and a single screencap can land on either. So on the
device lane the pixel assertion would have stayed green through the entire defect, exactly as the
blank-screenshot check did on desktop. **The present-ratio invariant is what caught it**, and it
caught it deterministically, on the first tick. Both assertions are kept, for different reasons: the
ratio catches double-present, the pixel count catches an overlay that never drew at all.

## 2. Phase 2 — re-audit of recorded native visual evidence

The enumeration is complete; the re-runs are not. What the enumeration establishes:

- **Playtest `visual` assertions are never evaluated on `--target android|ios`.**
  `packages/playtest/src/runner/androidRunner.ts:493` says screenshots are captured as artifacts but
  "visual metric evaluation is not supported yet". So there is no recorded `visual`-metric result on
  a device to retract. PRD-155 §3 lists these among the suspect evidence; they do not exist.
- Results resting on the runtime's own capture (mechanism **a**) and dated before 2026-08-18 are the
  suspect set. They are concentrated in `packages/runtime-native/docs/G1`/`G2` and in
  `docs/verification/PRD-04x`–`PRD-05x`, plus the desktop rows of the tier-1 parity ledgers.
- Results resting on OS-level device capture (mechanism **b**) — every Android and iOS-simulator row
  — are **not** affected, per §0 above.

**The three worth re-running first**, because each decided something:

1. `docs/verification/PRD-051.md` — a *negative* native result (`bright=0`, "no text and no Three.js
   scene") taken from a mid-frame capture of a canvas-texture HUD. It is the entire basis for killing
   that candidate and scoping `@threenative/ui` to web. A capture taken before the overlay pass is
   precisely how a canvas-layer HUD would read as absent while working.
2. `25-camera-parented-overlay` across `tier-1-2026-08-10.md`, `tier-1-2026-08-15.md` and
   `parity-reconciliation-2026-08-15.md` — a conformance row about camera-parented overlays whose
   pass/fail flipped between ledgers.
3. `docs/verification/prd-055-phase-0-candidate-g-2026-08-09.md` — HUD text asserted visible on the
   desktop lane by bright-pixel count, the positive counterpart to (1).

| Result | Outcome |

The other two were **relabelled in place, not deleted and not quietly kept**, as PRD-155 Phase 2

| Platform | Capture | Roof | Sails |
| --- | --- | --- | --- |

Per PRD-155 §4, a phase that cannot make its test fail has not found its defect. D1 does not
reproduce on the current tree. Two candidate explanations, neither measured:

- The report predates `3677542` ("scene optimization stops eating the scene it optimizes"), which is
  the obvious suspect for meshes going missing. On this game the projection now stands down entirely
  (`projecting: false`, `reasonCode: "notWorthwhile"`).
- The web half of the report may have been observed on a SwiftShader-backed run — see §6.

### §6 environment finding: local WebGPU playtests silently run on SwiftShader

`CLAUDE.md` says to prefix screenshot/`visual` playtests with `sh scripts/xvfb.sh` on headless Linux.
On this machine that does **not** reach the NVIDIA GPU:

| Invocation | `adapter.architecture` | Result |
| --- | --- | --- |
| headless + `--browser-recipe webgpu` | `swiftshader` | 197 × `createBuffer failed, size (18288) is too large`, capture blank (1 colour) |
| `sh scripts/xvfb.sh` + recipe | `swiftshader` | same |
| `DISPLAY=:0 --headed` + recipe | `turing` / `nvidia` | passes, real frame |

Xvfb has no GPU, so Vulkan cannot reach the NVIDIA driver through it. On SwiftShader this game's
geometry fails to allocate and the frame is blank — so any local `visual` assertion run the
documented way is not evidence, which is the rule `CLAUDE.md` already states and the documented
recipe does not satisfy here.

## 4. Phase 4 — D2 and D3, animation on device

Method: capture N screencaps 1.2 s apart on the device (and N screenshots at differing tick counts
on web/desktop), then count the fraction of pixels that changed in fixed regions. The fox and the
windmill are the built-in positive controls: a run where the measurement itself was broken would
report ~0 % everywhere, and they do not.

| Region | Web | Desktop native | Pixel 8 |
| --- | ---: | ---: | ---: |
| Windmill | 0.38 – 0.56 % | 0.33 – 0.38 % | 1.03 – 1.42 % |
| Waterfall (left) | 31 – 34 % | 30.0 – 30.1 % | **0.00 – 0.01 %** |
| Waterfall (second) | 20.2 – 20.6 % | 15.2 – 16.2 % | **0.00 – 0.07 %** |
| Fox (idle) | 11.0 – 13.7 % | 10.1 – 12.4 % | 4.8 – 8.5 % |

**D2 — blades do not rotate: REPRODUCED.** **D3 — waterfalls do not animate: REPRODUCED.** They are
the same defect, and it is a **game bug**.

The pixel-diff table above is retained because it is what a careless reading of this measurement
produces, and it was wrong. The windmill column does not measure the blades: the region contains
drifting clouds, and 0.4–1.4 % is the clouds alone. Cropping the blades tightly from two device
frames 2.4 s apart shows them at a **pixel-identical angle** while `hub.rotation.z` advanced from
0.138 to 2.970 radians. The owner reported this from watching the game and was right; the pixel
number was not measuring what its label said.

### What was actually wrong

Three defects, stacked, in `sandbox/fox-native` — none of them in `packages/`:

1. **`level.renderRoot` is a `BundleGroup`, and upstream three.js defaults `BundleGroup.static` to
   `true`.** A render bundle records its draws once and replays them, so everything animated inside
   the group is frozen at the pose it held when the bundle was recorded. The whole level lives in
   that group. This is the cause; `static = false` is what makes the blades turn.
2. **`mergeLevelMeshes` had no dynamic check**, while `mergeStaticSceneMeshes` beside it has always
   had one. It baked `matrixWorld` into merged geometry and then called `root.clear()`, detaching
   the animated subtrees. Probing ancestry from a sail reached a parentless `Group` rather than the
   `Scene` — `rootIsScene=false` — so the updaters were animating objects nothing draws.
3. **`waterfall()` overwrote `userData.streaks`** inside its two-iteration loop, so only the second
   of two streak groups was ever animated.

### The measurement that settled it

The diagnosis needed three probes, in this order, because each ruled out the layer below it: the
updater runs and `dt` is right (rules out the game loop); the object's ancestry does not reach the
`Scene` (rules out the renderer, and found defect 2); after reattachment the transform updates
without being forced and the chain ends `… < BundleGroup < Scene` with every auto-update flag on
(rules out matrix propagation, and found defect 1).

Fixed, and verified on the Pixel 8 with clean logs:

| Region | Before | After |
| --- | ---: | ---: |
| Windmill | 0 % rotation (blades pixel-identical) | **12.34 – 12.57 %** |
| Waterfall (left) | 0.00 – 0.01 % | **19.10 – 23.47 %** |
| Waterfall (second) | 0.00 – 0.07 % | **9.35 – 9.79 %** |
| Fox (unchanged control) | 4.8 – 8.5 % | 10.35 – 10.72 % |

### Retraction

An earlier revision of this document concluded D3 was "an engine bug, Android-only, in the
wgpu-native backend". That was wrong on both counts. It rested on the waterfalls animating in a web
playtest measured at ticks 60–90 — before the deferred level reveal runs `mergeLevelMeshes` and
before the bundle is recorded — against a device run measured after both. The defect is a game bug
and it reproduces on every platform. Nothing in `packages/` was changed for it, and nothing needed
to be.

**PRD-155 §6 puts "the `BundleGroup` decision in `fox-native`" out of scope as a game's choice.**
That is still where the fix landed. Worth a separate question, not settled here: a `BundleGroup`
that silently freezes animated children is a sharp edge, and this game walked straight into it.

## 5. Phase 5 — D4, the shadow cost: RUN, hypothesis NOT SUPPORTED

### Preconditions were waived, by owner decision

PRD-155 requires the device discharging, at least 50 % battery, and thermal `NONE`. None of the
three held, and the owner directed the measurement to be taken anyway rather than deferred. Actual
state, recorded before and after every run:

| | battery | thermal status | battery temp |
| --- | --- | --- | --- |
| across all six runs | 22 % → 21 % | 1 (not `NONE`) | 37 °C, stable |

The device stayed on USB throughout. **These numbers are therefore not comparable with the
~4-minute discharging soak in PRD-155 §2 that they exist to explain**, and no comparison with it is
drawn below. What they can support is the within-session comparison between the three switch
settings, which were run back to back under the same conditions.

### Method

Six runs: baseline, `__TN_PROBE_SUN_FOLLOW__=false`, and `__TN_PROBE_SHADOWS__=false`, twice each,
interleaved so thermal drift could not settle on one condition. Each run patched the switch into the
bundle as a prelude, reinstalled, launched, and held the left stick right via
`adb shell input swipe` so the fox advanced into denser level rather than idling at the start —
`foxX` reached 44.7 to 52.3 in every run. Frame rate came from the game's own
`TN_FOX_NATIVE_FRAME_RATE` windows of 300 frames each.

### Result

| Condition | windows | median fps | mean fps | min | max | median worst frame (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline (sun follows, shadows on) | 11 | 38.8 | 38.6 | 26.2 | 46.9 | 91.9 |
| `PROBE_SUN_FOLLOW` off | 10 | 42.2 | 39.2 | 21.5 | 49.0 | 78.2 |
| `__TN_PROBE_SHADOWS__` off | 9 | 34.9 | 35.1 | 19.0 | 50.7 | 90.5 |

**The hypothesis is not supported.** Turning the sun-follow off moves the median by 3.4 fps while
the means are within 0.6 fps of each other and the ranges overlap almost completely. And turning
shadows off came out **slower than baseline**, which cannot be a causal effect: not casting shadows
cannot cost more than casting them. That inversion is the tell — the run-to-run noise floor is
larger than the effect being looked for, so this measurement cannot attribute the frame rate to the
sun or to the shadow map either way.

PRD-155 §4 anticipates this outcome: "If it is not the cost, this phase's result is the number that
rules it out." These are those numbers. They rule out a large, obvious shadow cost at this level
position under these conditions. They do not rule out a smaller one, and they say nothing about the
degradation-over-time shape that motivated D4, because the windows are not locked to level position.

### What this says about the probe, which is the part that generalizes

The game's own `renderCalls` counter shows **no correlation with the switches at all** — medians of
4,446 / 4,328 (baseline), 4,218 / 2,158 (shadows off), 2,186 / 4,452 (sun off). The ~2× split tracks
how far the level had streamed in, not what was switched off. So the instrumentation could not even
confirm that disabling shadows changed the rendering workload, and `drawCalls` read 0 throughout.

PRD-155 §2 says of D4 that "the framework owes it a way to see the cost, not a fix." This run is the
evidence for that sentence: a hand-rolled per-frame counter in game code cannot see a shadow pass,
so a game asking "what is my shadow map costing me" currently has no way to find out. That is the
follow-up this phase produces, and it is a framework question, not a game one.

### What a cleaner measurement needs

Windows locked to a fixed level position rather than to elapsed frames, a discharging device at the
stated battery and thermal preconditions, and a pass-level cost signal from the framework rather
than a game-side frame counter.

## 6. §5 hardening

**Optimizer annotations in `sandbox/fox-native`.** The PRD asks whether they are inert. Two of the
three are; one is not, and not for the reason the PRD assumed.

- `threeNativeTransformOwner` and `threeNativeTransformMode` — **inert, deleted** (17 assignments).
  Their only readers are `gpuTransformMergeScene`, `flattenMarkedDynamicGroups`,
  `batchMarkedDynamicGroups` and `instanceMarkedDynamicGroups`, each gated behind a `PROBE_*`
  constant that is `false`. After deletion the device still rotates the blades (1.03 – 1.10 %) and
  animates the fox (4.8 – 8.5 %), and the frozen waterfalls are unchanged.
- `threeNativeDynamic` — **live, kept.** It is read by the game's own `mergeLevelMeshes`, called
  unconditionally when the deferred level arrives, to keep animated objects out of a static merge.
  That is the game's own optimizer needing its own marker, not the framework's bug in game clothing.

**`scripts/verify-golden-path.ts`** now skips a directory under `packages/` that has no
`package.json` and names it on stdout, instead of failing the whole gate with a raw `ENOENT` naming
a file rather than the directory that caused it.

**Probe audit.** No other probe reads `info` off the framework's renderer wrapper. `IRendererLike`
deliberately has no `info`. The examples that read `renderer.info` (`engine-load-test`,
`native-cpu-load-test`) construct `WebGPURenderer` directly, so they are reading the real renderer;
`packages/playtest/src/three/observations.ts` takes the raw renderer and omits the field rather than
reporting `-1`; `packages/core/src/game.ts` already reads through `renderer.raw`. The `fox-native`
probe that reported `-1` was the only one, and it was already fixed.

## 7. Two pre-existing red gates, fixed

Both predate this session and both were left by `473f9f3`.

- `tests/desktop-core-gate.test.mjs` failed with `missing TN_PRESENTS count` — the `TN_PRESENTS`
  assertion shipped without updating the test's fixture log.
- `tests/resize-attachment-invariant.test.mjs` failed because acquisition became idempotent within a
  frame, so `WGPUTexture texture = getCurrentSwapchainTexture()` became `texture = …` on its own
  line. The invariant it guards — the surface is reconfigured to the canvas size before anything
  acquires from it — still holds and is still asserted. Its *second* assertion had also silently
  degraded: it sliced the source to a comment that no longer exists, so `indexOf` returned `-1` and
  it searched the rest of the file while appearing to scope a function. It is now bounded by
  `captureFrameScreenshot()`'s own extent, and fails closed if either anchor disappears.

`packages/runtime-native`: 48 test files, 322 passed, 30 skipped.
