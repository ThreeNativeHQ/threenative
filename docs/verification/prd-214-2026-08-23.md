## What executed, and what it cost to get there

Three defects on `main` stood between a built APK and a presented frame. None is PRD-214's, all
three are recorded here because the next person will hit them:

1. **`@threenative/core` at HEAD cannot build for Android.** The KTX2 support added by
   `docs/bugs/android-ktx2-unsupported-2026-08-23.md` reaches `KTX2Loader` through a dynamic
   `import()`; the native bundler inlines it, the inlined transcoder contains the token
   `WebAssembly`, and `TN_NATIVE_WASM_ON_MOBILE` refuses the build. The same game, same
   `src/`, built cleanly against the older `threenative-core-0.2.0-prd186p1` tarball. Bypassed
   for this measurement with an uncommitted local patch to the sandbox's installed CLI, after
   confirming the sandbox ships no `.ktx2` asset, so the transcoder is never constructed.
2. **OGG audio is a hard startup failure on Android, not a warning.** With PRD-211's asset
   preflight skipped, `decodeAudioData` rejects and core turns the rejection into
   `TN_NATIVE_START_FAILED: decodeAudioData could not decode the supplied audio.` The game never
   presents a frame. The preflight was right to refuse the package. Worked around exactly as the
   preflight's own message instructs: the 30 OGG payloads were transcoded to WAV in place for
   the build and the originals restored from backup afterwards.
3. **A stale `public/assets.manifest.json` in the sandbox blocks startup.** It lists
   `models/enemy-terrorist.glb` while the game requests `assets/enemy-terrorist.glb`, and core's
   manifest gate throws `Asset 'assets/enemy-terrorist.glb' is not listed in the asset manifest`.
   Moved aside for the build and restored byte-for-byte; it belongs to another lane's in-flight
   asset move.

A fourth, cheaper trap: the device was **dozing**, so the first launch reached `onResume()` and
immediately `onPause()`/`onStop()` with a black screen and no native output. `mWakefulness=Dozing`
is the tell. Every later run wakes and unlocks the device first.

## The shadow refutation is withdrawn

The bug doc and the batch README both record "shadows refuted as the lever". That refutation is
circular and this record withdraws it.

- `sandbox/fps-framework/.threenative/build/game.js`, mtime **2026-08-23T20:13**, is the last
  native bundle built before the 20:18 measurement. Its compiled probe disables the shadow map
  and clears `castShadow` on every light unconditionally — the `KILL_SHADOWS` constant was folded
  away as always-true by the bundler.
- The APK built from it is `dist-native/bayview-noshadow.apk`, mtime 20:13. `TN_SHADOWS_KILLED`
  executed at 20:14:04. PRD-214 dates its attribution table "measured 2026-08-23 20:18".
- Therefore **the 49.42 ms / 54.44 ms table describes a scene with shadows already off.**

Whether a matching shadows-ON breakdown was ever recorded could not be established: the probe file
was untracked, so there is no history to date, and no `TN_OUTSIDE_BREAKDOWN` text survives anywhere
in the sandbox tree or in `docs/`. The PRD's phrasing "the post-kill breakdown *still* reads ~49 ms"
implies a pre-kill number existed; it is not reproducible here and is not treated as evidence.

Rather than argue from a missing log, R0 below has shadows **on** and R1 turns them off.

## Phase 0 — the bisect inside `renderer.render()`

**Method.** One APK, eleven rungs switched at runtime, so the whole bisect fits one device session
(the battery floor bites after four to six rebuild cycles). The driver advances on the engine frame
budget's own window edge, so a rung boundary can never fall inside a measurement window. Each rung
restores the scene before the next applies, so every rung is measured against the same baseline
rather than against the accumulation before it. The first window after every change is discarded as
settle — a pipeline rebuild or shader compile lands in it and is not steady state — so each rung
spends two windows of 180 presented frames, one to settle and one to measure.

All milliseconds below are `p50` over the measured window. `render` is the whole
`WebGPURenderer.render()` call; `update` is the fixed-step simulation; `hostGap` is present wait
plus host work between callbacks.

**`renderer.info.render.calls` is not usable in this build.** It reported a monotonically rising
total across rungs (1110 → 11 561) rather than a per-frame count, so no conclusion here rests on
draw-call counts. `visibleMeshes` is counted by the driver and `triangles` did move both ways, so
both are used instead. Correcting the draw-call readout is left open.

### What the rungs establish

**1. The attribution reproduces, independently of the old probe.** R0 puts `renderer.render()` at
46.15 ms of a 58.96 ms presented frame — 78.5% — at 16.89 fps. The bug doc's 18.3 fps and ~88%
came from a hand-written probe that monkey-patched `requestAnimationFrame` and guessed the phase
boundaries from outside the loop. This number comes from the loop itself.

**2. Shadows are a lever, worth about 11 ms of render.** R0 → R1 takes render from 46.15 to
35.20 ms and fps from 16.89 to 20.37, *while drawing more objects* (822 visible against 492). The
extra visible meshes make this a conservative reading of the shadow saving, not a generous one.

**3. Material and node evaluation is the largest single lever.** R4 and R3a hold object count
fixed at 830 visible meshes and ~1.1M source triangles and differ only in material: real materials
cost 52.47 ms, one shared `MeshBasicMaterial` costs 27.21 ms. Roughly half of `renderer.render()`
is material and node-graph work. R3b sharpens it — collapsing duplicate material *instances* of
the same type, with no change of material class, still buys 52.47 → 37.77 ms — so a large share is
per-material-**instance** work (bind groups, uniform writes, per-instance node updates) rather than
shader complexity. That is mechanism, not appearance, and is therefore reachable by the framework.

**4. There is a fixed floor of about 13.7 ms.** R2c draws one visible mesh and `renderer.render()`
still costs 13.68 ms. No amount of culling, instancing or object-count reduction reaches below it.
At a 16.67 ms vsync interval, that floor alone is 82% of the budget.

**5. Above the floor, cost tracks object count sub-linearly.** 492 → 410 → 208 → 1 visible meshes
gives 46.15 → 38.94 → 20.24 → 13.68 ms. A purely per-object model predicts 27.4 ms at 208 objects
against 20.24 measured, so per-object work dominates the variable part but is not the whole story.

**6. The frame is CPU-bound in JavaScript — settled, not inferred.** Quartering the pixels did not
reduce render CPU at all; it rose (52.47 → 62.54 → 74.11 ms). The resolution change genuinely took
effect — `EGL mtrack` fell 103 640 → 64 780 → 55 120 KB across the same rungs — so this is not a
no-op rung. **The rise is read as an artifact of calling `setPixelRatio` mid-run** (surface and
render-target reallocation), not as a claim that fewer pixels are slower. What it does establish is
the negative: there is no fill-rate or GPU-bound component to recover by rendering fewer pixels.

**7. Fixed per-call setup is refuted.** R6 renders the same scene twice per frame and costs
111.93 ms against ~52 ms for one. The second call costs what the first did; there is no warm-cache
saving, so the cost is repeated per-object work every frame rather than one-time setup a cache
could absorb. The render-bundle spike the PRD listed as a candidate is *not* refuted by this — a
pre-recorded command stream would remove exactly this repetition — but "one-time setup we are
paying repeatedly" is.

### Re-ranked lever list

| lever | status after Phase 0 | evidence |
| --- | --- | --- |
| Material/node evaluation and per-material-instance work | **first** | R4 vs R3a: 52.47 → 27.21 ms at fixed object count; R3b: 52.47 → 37.77 ms from instance sharing alone |
| Shadow pass | **second, and newly live** | R0 vs R1: −10.95 ms render, +3.5 fps |
| Draw-call / object-count reduction (instancing, culling, static freeze) | third, bounded | R2 sweep is real but bounded below by the 13.68 ms floor |
| Pre-recorded command streams (render bundles) | open, unrefuted | R6 shows the per-object stream is rebuilt every frame |
| Resolution / fill rate | **refuted** | R5: quartering pixels does not reduce render CPU |
| Fixed per-call setup absorbed by a cache | **refuted** | R6: second render costs the same as the first |
| Engine plumbing (loop, physics dispatch, present wait) | **refuted, re-confirmed** | `hostGap` p50 0.94–5.00 ms, `residual` p50 ≤ 0.03 ms in every rung |

## The permanent frame budget

`packages/core/src/frame-budget.ts`, wired through `FixedStepLoop` and `defineGame`, on by default.

- Emits `TN_FRAME_BUDGET` every 300 presented frames (the sandbox ran 180 for the bisect) with
  `fps`, the presented interval, and `hostGap` / `update` / `render` / `overlay` / `residual` as
  summaries and as shares of the frame.
- Emits `TN_FRAME_HITCH` the moment a gap between presented frames exceeds `hitchMs`, with a wall
  clock, and **excludes that frame from the window**. Observed working on the device: the run
  logged `TN_FRAME_HITCH:{"gapMs":16982.38,"uptimeMs":29693488.34,"wallClock":1787545992220}` — a
  17-second startup stall, tagged and kept out of the percentiles. This is the mechanism the bug
  doc's unexplained `worstMs: 27489` needed.
- Feeds the same per-frame split into the playtest render series, so a gate can bound it.
- Named override on the same object: `defineGame({ frameBudget: false })` silences the marker.
  It does **not** silence the measurement — the per-frame phase samples still reach
  `assert.performance`, so turning the convention off does not turn its measurement off. Named in
  the templates' shared `performance-default` fragment, which every template renders.

Fails closed: malformed options throw at construction, out-of-order phase calls throw, a
non-finite sample throws rather than producing a clean percentile, and a phase nothing measured
reports `samples: 0` so a consumer must fail rather than skip.

## The budget gate

`assert.performance` gains `minFps` and `maxPhaseMsP95`, reading the same observation path as the
existing frame-time and draw-call bounds.

```json
{"performance":{"maxFrameMsP95":33,"minFps":30,"maxPhaseMsP95":{"render":12}}}
```

Fails closed in four directions, each with a test:
- a series with no phase split cannot satisfy a phase ceiling — it fails naming the missing
  evidence, and never skips;
- a wrong-typed phase (`{"render":"slow"}`) invalidates the whole sample rather than being ignored;
- a budget naming a phase the engine does not measure throws **at scenario load**;
- an empty budget object, and a non-numeric `minFps`, throw at load.

**Observed red before trusted green, twice.**

In the unit lane, `performance.spec.ts` runs the measured device frame through the gate and
requires it red at `minFps: 30` (observed 18.12 fps) and at `maxPhaseMsP95.render: 12` (observed
50.1 ms), then runs a 16.7 ms frame through the same budget and requires both green.

In the **browser lane**, `examples/abyss-framework/playtests/frame-budget.playtest.json` drives
the real build through the real runner. As shipped it exits 0:

```
"details": { "actual": 86.96, "expected": 24, "sampleCount": 23, "unit": "fps" },
"id": "performance.minFps", "pass": true
"details": { "actual": 15.8, "expected": 30, "phase": "render", "sampleCount": 23, "unit": "ms" },
"id": "performance.maxPhaseMsP95.render", "pass": true
```

With the floor raised to an impossible `minFps: 1000` and nothing else changed, the same run
exits 1:

```
"id": "performance.minFps", "pass": false
"code": "TN_PLAYTEST_PERFORMANCE_ASSERTION_FAILED",
"message": "performance.minFps expected at least 1000 fps, observed 277.78.",
"suggestion": "Read the TN_FRAME_BUDGET marker for this run: it names which frame phase owns the time."
```

The artificial cap was reverted and the committed scenario carries `minFps: 24`. Note this is a
desktop browser on a discrete GPU — the numbers are healthy and mean nothing about a phone. What
it proves is that the gate reads a live render loop, moves in both directions, and names the
instrument to read next.

## Still open

- **Phases 1–2 (the levers) are not implemented.** Phase 0 re-ranked them; each lands as its own
  vertical slice with a consumer-scoped acceptance, red-green against this gate, and kill-switch
  LOC scoring. Nothing in this record claims a game got faster.
- **The 30 fps acceptance criterion is not met.** Bayview presents at 16.89 fps with shadows on.
  What this record delivers is the attribution and the instrument, not the fix.
- **The budget gate has not been run on `--target android`.** It is proven on the browser lane
  and in the unit lane; the device numbers in this record come from the marker stream, not from a
  playtest run. `assert.performance` declares `supportedOn: ["web", "desktop", "bevy"]` and was
  left alone rather than widened on an untested lane. Wiring the gate into a device scenario is
  the honest next step and is not claimed here.
- **The browser scenario is not wired into `pnpm test:playtest`.** It was executed by hand, in
  both directions, and that output is above; it is deliberately not chained into the shared
  playtest gate yet. An fps floor that passes on this machine's discrete GPU can fail on a CI
  rasteriser, and reddening every other lane's gate to decorate this one would be the wrong
  trade. The gate this PRD actually asked for is a device gate, and that is what Phases 1–2 need.
- The three `main` blockers above need owners; none is PRD-214's layer.
- `renderer.info.render.calls` reports a running total rather than a per-frame count on this
  native build.
- iOS is out of scope until a physical lane exists, per the batch's exclusion.
