# PRD-314 verification

Status: recorded 2026-08-31. Baseline `c8f0f306`.

## Layer

Engine. The four checks are measurement of a Three.js `AnimationClip` against a Three.js
`Skeleton`; they move nothing and decide no appearance. They land in `@threenative/core` rather
than `@threenative/playtest` because core already depends on playtest — `@threenative/core/playtest`
imports `@threenative/playtest/three` — so nothing in playtest can reach `measureThreePose`,
`posedBounds` or `skeletonBones`, and `boneContact` is built on `measureThreePose`.

## Capability search before writing

Recorded per the discovery rule; `engine_search_capabilities` returned:

| Mechanic | Result |
| --- | --- |
| retarget an animation clip from one skeleton to another with a different bind pose | **empty** |
| a clip's tracks fail to bind and the character plays its bind pose | `AnimationPlayer`, `measureThreePose`, `posedBounds` — none check binding |
| which bones of a skeleton a clip does not animate | `skeletonBones` (names bones; does not read a clip) |
| a seated character's hands should touch the keyboard and hips the chair | `attachToBone` only (attaches; does not measure) |
| the full four-part request, `scope: "request"` | `AnimationPlayer`, `attachToBone`, velocity/temporal helpers — no match |

`measureThreePose` and `skeletonBones` are reused rather than duplicated: `boneContact` calls
`measureThreePose` for both the bone and the target, and the clip checks share `skeleton.ts`'s bone
walk.

## Playtest

`examples/prd314-clip-audit` builds two rigs whose `Arm` bind poses differ by a pure 90-degree
twist about the bone's own axis, so both rigs stand in exactly the same place and only the roll
distinguishes them. Both arms ran on `WebGPURenderer` under `--browser-recipe webgpu --headed`.

```text

  --url http://127.0.0.1:5199 \
  --server-command "pnpm --filter prd314-clip-audit dev --host 127.0.0.1 --port 5199 --strictPort" \
  --browser-recipe webgpu --headed

```

Observed on the correct arm: `pose.meanDegrees=1.6e-7`, `pose.maxDegrees=1.7e-6`, `bindings 4/4`,
`coverage.driven=4`, `contact.handMetres=0.035`, `contact.hipsSeated=true`.

```text

exit 0 — all 9 resource assertions, the diagnostics policy and the visual region passed
```

Observed on the broken arm: `pose.maxDegrees=45.7`, `pose.worstDegrees=24.4` (Arm and Hand),
`bindings 1/2` with `unbound=["Hips.undefined"]`, `coverage.undriven=["Hips","Arm","Hand"]`,
`contact.handMetres=0.329`.

The broken scenario carries an explicit `consoleErrorsOptOutReason`: `AnimationMixer` logs its own
error for the misnamed track, and that log is the defect being proven rather than an unrelated
failure. Every other assertion in that scenario is independent of the opt-out.

Both captures were opened. `/tmp/clip-audit-ok/after.png` shows the retargeted limb matching the
reference limb's shape with its tip resting on the keyboard slab; `/tmp/clip-audit-shots/after.png`
shows the broken arm standing upright and missing the keyboard entirely, which is the same story
the numbers tell.

## Fixture traps found while building it

Two are worth recording because they cost time and both produce a silent zero:

1. Stepping an `AnimationMixer` by exactly `clip.duration` wraps a repeating action back to zero,
   so an "end of clip" sample reads as bind pose. The fixture sets `LoopOnce` with
   `clampWhenFinished`.
2. Reading a bone's end position without restoring the bind pose first lets the previous clip's
   pose stand in for the one being measured — defect 3, reproduced by accident. `boneAtEnd`
   restores, and the comment says why.

## Portability

No DOM, no `window`, no WASM, no dynamic import; the unit suite executes every function in Node
with no browser. `pnpm budgets` ran `check-native-shims` and `check-core-boundary` green. This was
not admitted for being unportable, so no `--target` conformance case is owed; nothing here is
web-only.
