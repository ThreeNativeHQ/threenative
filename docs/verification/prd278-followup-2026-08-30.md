## Original real-GPU Chromium failure — resolved by `fdafd9ba`

All bisects run in the throwaway scaffold `/tmp/wn-starter2` (fresh tarball install at 11:03,
server on `127.0.0.1:5219`).

### Defect A — the WebGPU instance is garbage-collected under the fixed-step loop

`THREE.Error resolving queries: AbortError: Failed to execute 'mapAsync' on 'GPUBuffer': A valid
external Instance reference no longer exists.` — from `WebGPUTimestampQueryPool._resolveQueries`,
called per frame by core's `FixedStepLoop` → `resolveGpuFrame`.

- Root cause read out of `three@0.185.1` (`WebGPUBackend.init`): it calls
  `navigator.gpu.requestAdapter(...)`, creates the device, and **stores neither the adapter nor the
  instance**. When Chromium collects them, every `mapAsync` fails; rendering may continue but the
  timestamp metering errors every frame.
- Timing-dependent: 0 errors in one run, 280 in the next; present with bloom+sharpen only, with the
  full SSGI/SSR chain, and with **no chain at all** (216–233 errors per run). It did not fire in the
  ~10 s menu screen the doctor samples — the collection needs longer than that.
- CI never sees it: the scaffold-smoke lane runs SwiftShader (`TN_PLAYTEST_ALLOW_SOFTWARE=1`).

**Fix (engine lane, `packages/core` or the distributed three patch):** retain a strong reference.
Either patch `WebGPUBackend.init` to keep `this.adapter = adapter` (the repo already distributes
`patches/three@0.185.1.patch` — three copies must move together: repo `patches/`,
`packages/core/patches/`, `create-threenative/template-assets/patches/`), or hold `navigator.gpu`
in core's renderer bootstrap. Then the per-frame `mapAsync` resolves again.

### Defect B — the play scene renders a black canvas, with or without the chain

The scenario capture (`artifacts/playtest/after.png` in the scaffold) shows the React HUD fine and
a **black 3D canvas**. Bisected to the bottom: black with the full SSGI/SSR chain, black with
bloom+sharpen only, and black with `setupPost` disabled entirely. The menu scene renders normally
(6,085 colours per `doctor --url`).

So this is not the WorldEnvironment port and not the chain mechanism — something in the play scene
or the loop kills presentation on this machine. Live suspects, in order:

1. **Defect A escalating to presentation loss.** The instance loss is timing-dependent; once the
   device's instance is gone, Dawn may stop presenting. The menu check ran only seconds — fix A
   first, then re-check B; they may be one bug.
2. **The cloth lane's template changes** (`Goal` on `SoftBody3D`): its compute dispatch already
   crashes hard on this Chromium —
   `createBuffer failed, size (360) is too large for the implementation when mappedAtCreation == true`
   (a 360-byte storage binding!). The scaffold currently runs with a stubbed `SoftBody3D`
   (in `/tmp/wn-starter2/src/entities/Goal.ts`, clearly marked) — the stub removes the crash but the
   canvas stays black, so it is not the whole story, but the real `SoftBody3D` failure needs its own
   root-cause (the 3900-byte vertex variant of the same error fired in `Geometries.updateAttributes`
   too, in an unrelated run).
3. **The renderer's timestamp/present path in the fixed-step loop** — `resolveGpuFrame` is new from
   the realism merge; lumen-hall (running since 02:48 on an older core dist) renders fine for hours,
   which is consistent with the new metering path being the difference.

**Next probes (cheap → expensive):**

1. Land the adapter-retention fix for A, re-run the scaffold scenario: if the console goes clean AND
   the canvas renders, A and B were one bug. This is the single highest-value next action.
2. If still black: run with `--js-flags=--expose-gc` and force `gc()` on the menu screen to make A
   reproduce deterministically; then bisect play-scene content (physics off, GLB loads off, cloth
   stub off) until presentation returns.
3. File the `mappedAtCreation` crash against the cloth lane with the stack in
   `/tmp/pt-fresh.json` (`SoftBody3D.process` → `WebGPURenderer.compute` →
   `createStorageAttribute`).
