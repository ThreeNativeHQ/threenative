# PRD-222 Phase 0 — Pixel 8 browser/native calibration — 2026-08-25

**Result: native is behind Chrome on identical hardware.** The same Bayview build measured
59.99 fps in Chrome 151 and 19.15 fps in the native host on physical Pixel 8 serial
`192.168.1.192:5555`. FPS parity is **0.319** and inverted render-p95 parity is **0.301**,
both below the 0.85 Floor. Per PRD-222 this routes Phase 2 to engine work; the native render
phase is the largest attributable gap.

## Steady-state result

Window 1 was discarded. The result is the median of windows 2–4, as PRD-222 requires.

| Measure | Chrome on Pixel | Native on Pixel | Parity |
| --- | ---: | ---: | ---: |
| fps | **59.99** | **19.15** | **0.319** (`native ÷ web`) |
| frame p50 | 9.5 ms | 32.43 ms | report only |
| frame p95 | 15.5 ms | 45.67 ms | report only |
| render p95 | 10.1 ms | 33.53 ms | **0.301** (`web ÷ native`, inverted) |
| hostGap p95 | not captured by the helper | 29.10 ms | unmeasured |
| update p95 | not captured by the helper | 11.58 ms | unmeasured |

Native windows 4–6 settled after the simulation's early work spike at 20.14–20.19 fps, render p95
33.59–34.77 ms, update p95 2.40–2.46 ms and presented mean 49.52–49.65 ms. This confirms the
existing vblank finding: Bayview is held in the 20 fps cell, and render remains the first bounded
lever. The early update p95 spike is not the steady-state owner.

## Commands and raw evidence

The surviving raw marker streams are committed at
`docs/verification/artifacts/prd-222-phase0-browser-console.txt` and
`docs/verification/artifacts/prd-222-phase0-native-logcat.txt`. The browser stream was transcribed
from the helper's terminal output after the run rather than written atomically by the helper, and
the pre/between/post thermal probes survive only in this record. A fresh Gauntlet critic therefore
returned **FAIL** on evidence retention. Phase 0 must be rerun after a valid ≥50% device preflight,
with one immutable artifact written during the pair; these numbers remain a routing baseline, not
the final accepted parity proof.

```sh
node packages/playtest/dist/runner/cli.js doctor --device 192.168.1.192:5555 --text
node packages/runtime-native/scripts/device-preflight.mjs 192.168.1.192:5555
node ../sandbox/fps-framework/phone-web-tmp.mjs 90
adb -s 192.168.1.192:5555 shell am start -W \
  -n com.threenative.bayview/com.threenative.runtime.MystralActivity
adb -s 192.168.1.192:5555 shell pidof com.threenative.bayview
adb -s 192.168.1.192:5555 logcat -d -v brief | rg TN_FRAME_BUDGET
```

Chrome windows 2–4 were 59.77/59.99/59.99 fps with render p95
9.6/10.1/10.7 ms. Native windows 2–4 were 18.91/19.15/20.14 fps with render p95
33.26/33.53/34.77 ms. The native process was alive at both 45 and 90 seconds, so the known physics
callback SIGSEGV did not contaminate this run.

Two harness failures were retained rather than treated as performance evidence:

- `phone-web-tmp.mjs` initially threw because `pidof` exit 1 (the required no-native-process state)
  was not handled; the helper now treats that as clean.
- The fixed-step native scenario completed 1,800 ticks in 27 seconds and emitted no complete
  wall-clock budget window through the runner, so it was discarded and replaced by the normal
  90-second Activity launch above.

## Phase 0 decision

`parity < 0.85`: **engine work**. Build the Android-browser runner lane and `assert.parity` gates,
then take the first Phase 2 lever from native render/material-node evaluation. Do not spend another
device run on resolution or fill rate; those levers are already refuted.
