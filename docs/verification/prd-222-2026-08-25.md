# PRD-222 Phase 0 — Pixel 8 browser/native calibration — 2026-08-25

**Result: native is behind Chrome on identical hardware.** The same Bayview build measured
59.99 fps in Chrome 151 and 19.15 fps in the native host on physical Pixel 8 serial
`192.168.1.192:5555`. FPS parity is **0.319** and inverted render-p95 parity is **0.301**,
both below the 0.85 Floor. Per PRD-222 this routes Phase 2 to engine work; the native render
phase is the largest attributable gap.

## Phase 0 decision

`parity < 0.85`: **engine work**. Build the Android-browser runner lane and `assert.parity` gates,
then take the first Phase 2 lever from native render/material-node evaluation. Do not spend another
device run on resolution or fill rate; those levers are already refuted.

## Phase 2 development probes — charging-confounded, relative evidence only

The owner connected the phone to power and explicitly waived the no-charger requirement while
diagnosis continued. These runs are therefore **not Tier 1–4 acceptance evidence**. They are useful
only as back-to-back development probes: every arm used the same physical Pixel 8, Bayview source,
native resolution, compile-time `TN_ANDROID_JS_PROFILE` telemetry and plugged-in thermal window.

### Render bundles reduce crossings but do not improve frames

Candidate commits `93370365` and `a95d5402` wrapped each of the 13 material-keyed `BatchedMesh`
groups in a Three.js `BundleGroup`. Runtime telemetry commit `c1d73718` counted direct and bundled
command boundaries. The candidate did exactly what it claimed mechanically: direct
`drawIndexed` calls fell by about 909 per frame and total measured JS/native command crossings
fell 23.2%. It did not make Bayview faster.

| arm | fps | render p95 | crossings/frame | binding time/frame |
| --- | ---: | ---: | ---: | ---: |
| control, FIFO | 18.85 | 33.43 ms | 5,145.18 | 3.901 ms |
| bundle, FIFO | 18.35 mean | ~33.2 ms | 3,951.43 | 3.688 ms |
| bracketed control, FIFO | 18.78–18.94 | 31.14–33.05 ms | — | — |

The bundle arm executed about 51.91 bundles through 3.99 `executeBundles` calls per frame and
reported zero steady-state bundle recordings, proving that the cached path was reached rather than
silently falling back. The bracketed control recovered the original result. Disposition:
**rejected and reverted**; a 0.21 ms binding-time reduction is below the 5–7 ms lever required to
leave the 20 fps vblank cell, and keeping extra machinery with no frame win violates the kill
switch.

### Mailbox present mode does not remove the wait

A control build with `threenativeVsync=false` selected mailbox rather than FIFO. It measured
18.71 fps, render p95 32.9 ms, presented mean 53.45 ms and 17.49 ms inside
`wgpuSurfacePresent`, indistinguishable from the FIFO control's 18–20 fps and ~17–18 ms present.
The present call is therefore waiting on completion of the submitted GPU/backend work, not merely
sleeping for FIFO vblank. Disposition: **refuted**; do not spend another arm on swapchain mode.

### Layer decision after native profiling

Bayview game logic is not holding the frame: recorded game-frame p99 is 2.99–5.72 ms while the
outside-game portion is 32.9–65.9 ms. Chrome on the same Pixel renders the same authored scene at
59.99 fps. Bayview's 835 renderables, node materials and shadow pass amplify the cost, but the
threefold platform gap belongs to the native engine/backend. A game-side visual downgrade could
raise FPS and would evade the parity requirement rather than satisfy it.
