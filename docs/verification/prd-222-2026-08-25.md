# PRD-222 Phase 0 — Pixel 8 browser/native calibration — 2026-08-25

**Result: native is behind Chrome on identical hardware.** The same Bayview build measured
59.99 fps in Chrome 151 and 19.15 fps in the native host on physical Pixel 8 serial
`192.168.1.192:5555`. FPS parity is **0.319** and inverted render-p95 parity is **0.301**,
both below the 0.85 Floor. Per PRD-222 this routes Phase 2 to engine work; the native render
phase is the largest attributable gap.

## Phase 0 decision

`parity < 0.85`: **engine work**. Build the Android-browser runner lane and `assert.parity` gates,
then take the first Phase 2 lever from native render/material-node evaluation. Do not spend another
device run on resolution or fill rate; those levers are already refuted.

## Phase 2 development probes — charging-confounded, relative evidence only

The owner connected the phone to power and explicitly waived the no-charger requirement while
diagnosis continued. These runs are therefore **not Tier 1–4 acceptance evidence**. They are useful
only as back-to-back development probes: every arm used the same physical Pixel 8, Bayview source,
native resolution, compile-time `TN_ANDROID_JS_PROFILE` telemetry and plugged-in thermal window.

### Render bundles reduce crossings but do not improve frames

Candidate commits `93370365` and `a95d5402` wrapped each of the 13 material-keyed `BatchedMesh`
groups in a Three.js `BundleGroup`. Runtime telemetry commit `c1d73718` counted direct and bundled
command boundaries. The candidate did exactly what it claimed mechanically: direct
`drawIndexed` calls fell by about 909 per frame and total measured JS/native command crossings
fell 23.2%. It did not make Bayview faster.

| arm | fps | render p95 | crossings/frame | binding time/frame |
| --- | ---: | ---: | ---: | ---: |
| control, FIFO | 18.85 | 33.43 ms | 5,145.18 | 3.901 ms |
| bundle, FIFO | 18.35 mean | ~33.2 ms | 3,951.43 | 3.688 ms |
| bracketed control, FIFO | 18.78–18.94 | 31.14–33.05 ms | — | — |

The bundle arm executed about 51.91 bundles through 3.99 `executeBundles` calls per frame and
reported zero steady-state bundle recordings, proving that the cached path was reached rather than
silently falling back. The bracketed control recovered the original result. Disposition:
**rejected and reverted**; a 0.21 ms binding-time reduction is below the 5–7 ms lever required to
leave the 20 fps vblank cell, and keeping extra machinery with no frame win violates the kill
switch.

### Mailbox present mode does not remove the wait

A control build with `threenativeVsync=false` selected mailbox rather than FIFO. It measured
18.71 fps, render p95 32.9 ms, presented mean 53.45 ms and 17.49 ms inside
`wgpuSurfacePresent`, indistinguishable from the FIFO control's 18–20 fps and ~17–18 ms present.
The present call is therefore waiting on completion of the submitted GPU/backend work, not merely
sleeping for FIFO vblank. Disposition: **refuted**; do not spend another arm on swapchain mode.

### Layer decision after native profiling

Bayview game logic is not holding the frame: recorded game-frame p99 is 2.99–5.72 ms while the
outside-game portion is 32.9–65.9 ms. Chrome on the same Pixel renders the same authored scene at
59.99 fps. Bayview's 835 renderables, node materials and shadow pass amplify the cost, but the
threefold platform gap belongs to the native engine/backend. A game-side visual downgrade could
raise FPS and would evade the parity requirement rather than satisfy it.

### Per-command attribution and wgpu-native version A/B

Profiler commit `efee855d` split the pooled binding time into ten commands and added the two calls
that Linux `simpleperf` had already ranked but the marker omitted: `GPUQueue.writeBuffer` and
`GPURenderPassEncoder.end`. Focused red/green: the marker-contract test failed on missing
`commandNs`; after implementation both profiling and fail-closed parser suites passed, 20/20. The
Android V8 host then built successfully with profiling enabled.

The steady v25 control below averages frames 877–1076 (200 physical-device frames). It used the
same plugged-in development window and Bayview projection as the earlier probes. The APK is
`dist-native/prd222-bayview-command-profile.apk`, SHA-256
`e44f11570d13246937e27cbfcba506d14130c03467885baffb6bc2d1961a69ca`.

| v25 command | calls/frame | native time/frame |
| --- | ---: | ---: |
| `writeBuffer` | 538.00 | **3.990 ms** |
| `renderPass.end` | 3.00 | **2.702 ms** |
| pipeline + bindings + vertex/index buffers | 1,757.18 | 2.435 ms |
| direct draw + indexed draw | 839.00 | 0.303 ms |
| **all profiled commands** | **3,137.18** | **9.431 ms** |

Submit/poll added 0.637 ms and present waited 15.876 ms. The adjacent complete frame-budget
windows measured 18.69–18.88 fps and render p95 31.57–33.79 ms. The implication is narrower than
"too many calls": actual draw encoding is cheap; wgpu-native's upload staging and pass finalization
own 6.69 ms, enough to explain the bounded lever needed to leave the 20 fps display cell.

Android is pinned to wgpu-native `v25.0.2.2`; Chrome uses Dawn. An isolated A/B used official
wgpu-native `v29.0.1.1` Android release assets without changing the repository pin. Both downloaded
archives matched the publisher's SHA-256 (`721741…bdd573` arm64 and `ef16fc…2c491` x86_64). One
callback ABI addition was adapted locally so both native slices compiled; the candidate APK was
`aee23d3cce8196fd847e251fd2c8cb301d6c6d4095c882a26a38814190a3e181`.

The newer backend is a decisive regression on this Pixel, not an upgrade candidate:

| backend | fps | render p95 | profiled commands | `writeBuffer` | `renderPass.end` |
| --- | ---: | ---: | ---: | ---: | ---: |
| v25.0.2.2 | 18.69–18.88 | 31.57–33.79 ms | 9.431 ms | 3.990 ms | 2.702 ms |
| v29.0.1.1 | **10.86** | **80.13 ms** | **16.667 ms** | **13.260 ms** | 0.023 ms |

v29 removes almost all pass-finalization CPU time but makes per-frame uploads 3.3× slower, for a
net 42% FPS loss. Disposition: **rejected**; remove the unused compatibility adaptation, keep v25,
and trace upload sizes/reuse before changing the engine's write path.

### Upload shape and exact-rewrite fingerprint

Size-bucket telemetry (`16ac7f07`) narrowed the v25 upload cost. A 200-frame physical-device
window averaged 639.42 `writeBuffer` calls and 491,245 bytes per frame. Writes no larger than 256
bytes accounted for 485.42 calls and 3.717 ms: 76% of calls and 66% of measured upload time. The
payload is only about 0.5 MB/frame, so bandwidth is not the limiting resource; native call and
staging overhead is.

Fingerprint telemetry (`d4315dc6`) then compared each write with the preceding write to the same
buffer in the same submit, including offset, size and content hash. Focused red/green first failed
on the absent duplicate fields, then passed 20/20; the profiled Android V8 host built successfully.
The APK is `dist-native/prd222-bayview-upload-fingerprint-profile.apk`, SHA-256
`7961defb6c5a06f38815547bf6250e83a0ecfeeb0f145fd792af706951708622`.

Frames 660–859 averaged 746 `writeBuffer` calls, 496,024 bytes and 4.864 ms per frame. Exact
same-buffer, same-range, same-content repeats were **zero calls and zero bytes**. The adjacent
frame-budget window measured 18.92 fps. Disposition: **reject exact-write elision** without building
a candidate; the repeat-target writes contain changing data. Trace range adjacency next to decide
whether multiple small changing writes can be coalesced without changing WebGPU ordering.
