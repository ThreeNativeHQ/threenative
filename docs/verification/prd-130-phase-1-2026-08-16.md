# PRD-130 Phase 1 — V8 runs on x86_64, and an ABI without a snapshot can no longer ship

2026-08-16. [PRD-130](../PRDs/done/PRD-130-android-default-js-engine.md) Phase 1. Two
devices, both engines read from logcat rather than inferred from the build flag.

**Headline: V8 has now run on the x86_64 emulator.** Every previous V8 run in this repository was on
the arm64 phone, which is why the defect below survived.

**And a correction to the PRD's own reasoning, recorded because it changes what this phase claims.**
PRD-130 §1 says the x86_64 slice "would ship an arm64 snapshot" and files it as the first thing in
the way. The bytes part is true. The implied consequence is not: the mismatch does not break x86_64,
and the control proving that is in §3.

## 1. What was wrong, precisely

`build.gradle.kts` staged **one** snapshot — arm64's — to a single asset path `v8/snapshot_blob.bin`,
while `abiFilters` shipped `arm64-v8a` *and* `x86_64` in the same APK. `android_main.cpp` read that
one path. So the x86_64 slice carried arm64's bytes.

The two blobs are genuinely different: **44,884 of 45,420 bytes differ**, starting at byte 9 — V8's
checksum field (`22b4704e` against `bdd7eb3f`). Same version string, `11.0.226.16`, in both.

## 2. The fix

- `threeNativeAbis` is declared once and feeds **both** `abiFilters` and `copyV8Snapshot`, so the set
  of slices shipped and the set of snapshots staged cannot drift.
- `copyV8Snapshot` stages one snapshot per ABI to `v8/<abi>/snapshot_blob.bin`.
- `android_main.cpp` selects the path at compile time from `__aarch64__` / `__x86_64__`, and an ABI
  with no case is a `#error` rather than a fallback.

Built APK, both slices, sizes proving they are the distinct files rather than two copies:

```
45420  assets/v8/arm64-v8a/snapshot_blob.bin
45421  assets/v8/x86_64/snapshot_blob.bin
```

### Both ABIs launch V8, read from logcat

| Device | ABI | logcat |
| --- | --- | --- |
| Pixel 8 `37251FDJH0037Z` | arm64-v8a | `Loading asset: v8/arm64-v8a/snapshot_blob.bin` → `JS engine created: V8` |
| `emulator-5554` (`sdk_gphone64_x86_64`, API 35) | x86_64 | `Loading asset: v8/x86_64/snapshot_blob.bin`, `Asset size: 45421 bytes` → `JS engine created: V8` |

## 3. The negative controls, and the one that did not fire

PRD-130 Phase 1 pre-commits two controls. One fired and one did not, and the one that did not is the
more informative.

### `wrong-abi-snapshot` — **did NOT fire.** Recorded rather than reworded.

The control: stage arm64's snapshot into the x86_64 slice and reinstall; the emulator "must die with
`V8 startup snapshot asset is missing` or an equivalent refusal, not run." The PRD adds: *"If it
runs, the snapshot is not being read and the gate proves nothing."*

Executed by reverting `copyV8Snapshot` to the single-source staging, rebuilding, and installing on
`emulator-5554`. Both slices then carried 45,420 bytes — arm64's. Result:

```
Loading asset: v8/x86_64/snapshot_blob.bin
JS engine created: V8
TN_NATIVE_SMOKE_300_FRAMES:300
TN_ANDROID_JS_FRAME:{"elapsedMs":17950.4,"frames":300,"msPerFrame":59.83}
```

**It ran. Three hundred frames of JavaScript, on the wrong ABI's snapshot.** The snapshot *is* being
read — the asset path and byte count in the log prove that — so the PRD's stated inference does not
hold here. V8 accepts a blob whose checksum does not match its own and carries on, silently. Most
likely it discards the blob and builds the isolate from scratch, but this run does not establish
which, and no `[V8]` diagnostic reaches logcat because that path writes to `std::cout`.

**So Phase 1 is correctness of what ships, not a repair of a reproduced failure.** Shipping one ABI
the other ABI's 45 KB is wrong on its face; it is not the reason the emulator lane had never run V8
— nothing had tried. Anyone restating this phase as a crash fix is overclaiming, and the build
comment says so at the site.

**Open, and not chased here:** whether V8 silently falls back or silently deserializes foreign data.
The first is benign-but-slow; the second would be a latent correctness hazard on any future
mismatch. Deciding it needs a corrupt-blob control and a startup-time comparison, which is a
different question from this phase's.

### `missing-snapshot` — **fired, exit 1**

Moved `third_party/v8-android/snapshot_blob/x86_64/` away and rebuilt:

```
$ ./gradlew assembleDebug -PthreenativeJsEngine=v8
exit 1
* What went wrong:
A problem was found with the configuration of task ':app:copyV8Snapshot' (type 'DefaultTask').
  - Property '$2' specifies file '.../third_party/v8-android/snapshot_blob/x86_64/snapshot_blob.bin'
    which doesn't exist.
```

**This is the guarantee Phase 1 actually buys.** An ABI listed in `abiFilters` with no snapshot for
it stops the build instead of producing a slice that would reach a user. Given §3's finding — that a
wrong snapshot does *not* announce itself at runtime — a build-time refusal is the only place this
can be caught at all.

## 4. What this does not claim

- **Not a performance result.** The 59.83 ms/frame in §3 is a swiftshader-rendered emulator running
  the smoke bundle, from the control build. It is evidence that JavaScript executed, nothing more.
- **Not mobile-ready, and not an engine-default change.** The Gradle default is still QuickJS;
  everything here was built with an explicit `-PthreenativeJsEngine=v8`.
- **Not a claim that the old staging was harmless.** It shipped wrong bytes. §3 says only that the
  harm was not observable at runtime on this V8 build.
