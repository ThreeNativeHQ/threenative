# Phase 2 evidence — PRD-162

Date: 2026-08-20
Lane: `lane-162`
Status: **EXECUTED — RED with attribution**

The subject capability is: **the desktop build replays a run recorded by the browser, tick for
tick, and both report the same state hash.** The consumer observation is `stateHash = 1884960806`
on both the web and native desktop legs.

The capability shipped and both consumer legs executed. The gate is still recorded RED, on one
condition and one only: **the instrument cannot run the control arm without handing it the
capability.** A plain-Three.js project has no desktop runtime of its own, so the only way to
execute the arm's native leg was to bundle and run it on ThreeNative's own host — which this
PRD's instrument-leakage rule makes void as evidence. Under that lend, the arm did reproduce its
browser hash on desktop. No exclusivity claim is therefore made from this arm, in either
direction. This section supersedes the earlier GREEN reading of the same run, which rested on a
`WebGLRenderer` failure the control arm did not need to incur.

## Phase 0 — subject litmus

### Question (a)

Yes, the capability passes question (a). A game can describe its own state hash and input
sequence, but it cannot write the native host leg portably: the browser and native build need the
same fixed-step driver, event delivery seam, runtime compatibility check, and native host
execution. The framework already owns that plumbing; this change makes its replay recording
explicitly portable across those hosts.

### Question (b)

No, the capability does not decide how anything looks. Replay records input and deterministic
state; it creates no geometry, material, light, shader, camera framing, colour, texture, or timing
choice that changes the screenshot. The consumer owns the state hash and all appearance.

### Vanilla-arm budget, declared before the run

The plain-Three.js arm may use at most 50 non-blank source lines for input sampling, a fixed-tick
state hash, and an in-browser replay attempt. It may not import `@threenative/*`, use the
ThreeNative playtest bridge, or add a native host shim. One browser run records whether the arm
can reproduce its own hash; a native build attempt records whether it can deliver the same
outcome on the desktop host. The result is recorded even if the arm fails.

## Phase 1 — shipped implementation

The public replay recording now accepts `portable: true`. Core validation continues to check the
seed, fixed step, random state, core version, and Rapier version, while a portable recording
deliberately does not require the host user-agent string to match. The playtest recording schema,
converter, and world-runtime assertion preserve the flag and apply the same narrow exception.

The native leg required no native source change: the existing native fixed-step, keyboard,
EventTarget, and WebGPU seams were sufficient. The native conformance proof is the desktop
`--target` playtest below, in the same commit as this implementation and consumer.

## Phase 2 — consumer and control arms

The consumer is `examples/prd162-replay`, a consumer-scoped project importing only the public
`@threenative/core` and `@threenative/playtest` surfaces. Its package manifest uses published
version ranges (`0.2.0`/`0.2.2`), not `workspace:*`. The packaged-consumer proof packed the four
ThreeNative packages, installed the tarballs into `/tmp/prd162-consumer.hbGRNT/app` outside the
workspace, and reported core/playtest/runtime/CLI at `0.2.0`/`0.2.2` with
`PACKAGED_CONSUMER_NO_WORKSPACE_LINKS=PASS`. Its game owns the state hash and marker; the framework
owns the replay transaction and host plumbing. The browser and desktop scenarios assert the
consumer's `stateHash` resource, not an internal framework observation.

The browser recording was captured from the running consumer with
`pnpm --filter prd162-replay capture:recording http://127.0.0.1:5193 src/browser-recording.ts`.
The observed artifact is SHA-256
`df52b648947cdb6e5cd60b650d9db55f9dd9bae9b7ce4c393ccb08d49424dff9`, with input `KeyD` at tick 0
and release at tick 12. The native bundle imports that generated artifact; it is not the source of
the browser recording.

The control is [`vanilla.ts`](../../examples/prd162-replay/src/vanilla.ts). It imports only
`Object3D` and `Scene` from `three` plus its own captured recording, has 30 non-blank source
lines, contains no `@threenative` import, no playtest bridge, and no native shim. A real browser
KeyD event was sampled into 24 fixed ticks and replayed to the same browser hash:

**Recorded result: the arm reproduced the outcome, and the run is void as a control.** Once the
unnecessary renderer construction was removed, the plain-Three.js arm replayed its own
browser-captured input on the desktop host and matched its browser hash. It reached a desktop host
at all only because it was handed ThreeNative's bundler and native runtime; plain Three.js ships
no desktop runtime, and §4 of the PRD voids any run in which the instrument supplies the thing
under test. So this arm settles exclusivity in neither direction, and the gate condition it exists
to satisfy is recorded RED with that attribution.

What the arm does show is where the difficulty is not: the 24-integer replay itself is arithmetic
any game can write. What it cannot show, because it never had a host of its own, is whether the
framework's validated portable recording — seed, fixed step, random state, core and Rapier
version compatibility — is exclusive.

## Claims deliberately not made

- This is desktop-ready and web-proved only; it is not a mobile-ready, Android-device, iOS-device,
  or physical-hardware claim.
- The capability is not a visual-rendering feature, and the screenshotless assertion scenario is
  not presented as visual evidence.
- The vanilla arm is not claimed to match the cross-runtime capability, and is not claimed to
  fail it either. It matched its browser hash on the desktop host, and it only reached that host
  by borrowing the framework's bundler and runtime, which voids the run as control evidence.
- The capability is not claimed exclusive. Nothing here establishes that a plain-Three.js project
  with its own desktop runtime could not reach the same hash.
- The desktop instrument is not claimed reliable: it timed out on two of four consecutive runs.
- The consumer is not claimed to typecheck inside this repository. Its manifest pins the published
  `@threenative/core` `0.2.0` and `@threenative/playtest` `0.2.0`, which predate the portable
  recording this PRD ships, so `tsc` against that surface reports `'portable' does not exist`
  until a release publishes it. The example therefore carries no `typecheck` script and is not in
  the recursive root gate; what proves it is the executed web and desktop runs above and the
  packed-tarball consumer install outside the workspace. An earlier lane checkout typechecked
  green only because its `node_modules` still held workspace symlinks from before the manifest was
  repaired.
- No native runtime source was changed; the existing native host seam was sufficient.
