# PRD-216 verification — React UI on native

**Date:** 2026-08-24
**Result:** PASS on browser, Linux desktop native, and a physical Pixel 8. iOS is unproven.
**Amended 2026-08-24:** one acceptance row is downgraded to PARTIAL — see the correction at the
end. The renderer's device proof stands; the "one shared component" claim was spliced across two
different games.

## What shipped

This is an engine fix. Games cannot portably create a React renderer over a native framebuffer;
`@threenative/core/react` owns that mechanism. The starter keeps all appearance in generated
`src/ui/` source. The main `@threenative/core` entry remains React-free; React and
`react-reconciler` are optional peers reached only through the `./react` subpath.

The public path is `createReactOverlay({ canvasLayer })`, with React Native-shaped `View` and
`Text` primitives. It maps React commits to Three.js objects, lays them out in framebuffer pixels,
and draws them through the existing `CanvasLayer`. Unknown elements, styles, and glyphs fail by
name. A thrown component leaves the last good overlay mounted and can recover on the next render.

## Correction, 2026-08-24 — what the shared-component row actually proved

Re-reading the two games behind that row, the original `PASS` spliced evidence from different
artifacts. Recorded here rather than edited away, because the mechanism it was testing does work
and the overstatement is narrow.

**Proven, and unchanged by this correction.** `createReactOverlay` renders on the Pixel 8: the
device scenario returned `mounted true`, `objectCount 26`, `crosshairPresent`/`crosshairCentered`
true, with commits at p50 2.156 ms / p95 3.655 ms. The layout, glyph and failure paths hold. The
framework-side LOC claim also holds — `count-loc.ts` reports `native React HUD LOC: 61 (geometry
HUD 69)` against the starter template.

**Overstated.** "One React component on web and Pixel" was never true of one artifact:

| Half of the claim | Which game | Which lane |
| --- | --- | --- |
| One component tree behind both renderers | `templates/starter`, where `HudContent.tsx` (67 lines) is driven by `Hud.tsx` (71, Tailwind) and `NativeHud.tsx` (61, `View`/`Text`) | `native-playtests/react-hud.playtest.json` is `"target": "desktop"`. Linux desktop only; it never ran on a phone. |
| Rendering on the Pixel | `sandbox/fps-framework` | Ran on the device, but its web `Hud.tsx` (497 lines) and native `NativeHud.tsx` (242) are separate trees. The only genuinely shared component is `Crosshair.tsx`, 32 lines and three parts; `hudReadouts.ts` shares the numbers, not the tree. |

The gap closes by running the starter's `react-hud` scenario with `--target android`. Until that
executes, the honest claim is: **the native React renderer is proven on a phone, and the
one-tree-two-primitives pattern is proven on desktop.**

### Defects this surfaced in `sandbox/fps-framework`

Game bugs, not engine bugs — filed here because the double-check found them, and fixed in that
repository:

1. **No restart on a phone.** `restart` is bound to `["Enter", "NumpadEnter"]`. The web HUD adds a
   `RUN IT AGAIN` touch button for exactly this reason; the native HUD has neither, so a native
   player who runs out of time cannot start another round.
2. **The loading bar never moves.** The native track is a childless
   `<View style={{ background: "#1b2530", height: 6, width: 480 }} />`; `loadFraction` reaches it
   only as a percentage in text.
3. **Poly Haven's credit is missing on native.** Its licence requires a credit a player can see.
   The web end card carries it; the native end card does not.
4. **The key legend lies on touch.** Web hides it behind `desktop-only`; native always draws
   `WASD MOVE · MOUSE1 FIRE · R RELOAD`.

### Frame rate on the device, which this PRD never measured

`uiCommitP50Ms`/`uiCommitP95Ms` are per-commit React costs, not frame time — the doc already says
so. Nothing here measured what the phone actually presents. Measured afterwards on the same Pixel 8
at 2400x1080, thermal status 0 at 31.4 °C, 20 s of steady state via
`dumpsys SurfaceFlinger --timestats`:

```text
totalFrames   = 325      (20 s)
droppedFrames = 0
averageFPS    = 16.360
```

Not stutter — a constant rate with a periodic wobble. `present2present` is 58 ms x185 and 66 ms
x127, i.e. every frame lands seven or eight vsyncs apart on a 120 Hz panel, and
`present2presentDelta` is 0 ms x157 / 8 ms x157, so the interval alternates. `post2acquire` sits in
a 70-98 ms band: the cost is GPU render, not the game. The device playtest's own `sectionP99` puts
`gameFrame` at 2.99 ms, `enemies` 2.87 ms, `physics` 0.65 ms.

Two leads, neither yet A/B'd — the confirming run is blocked on a locked device:
`renderer.resolutionScale` is unset, so native draws all 2.59 Mpx, against 0.32 Mpx for the mobile
web surface the earlier `artifacts/device-profile.json` measured at ~60 fps; and
`src/render/lighting.ts` re-renders a 2048x2048 `PCFSoftShadowMap` with `radius: 3` over a
100 m frustum every frame.

**A trap for whoever measures next.** Frame figures read from the Android playtest lane are not
frame rate. That run reported `p50 1.42 ms` over 1829 frames for 1800 ticks: the harness steps one
frame per tick as fast as it can rather than presenting. A `frame-smoothness`-shaped assertion
(`p95 <= 20`) run with `--target android` passes on a game rendering at 16 fps.
