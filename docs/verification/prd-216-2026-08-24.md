# PRD-216 verification — React UI on native

**Date:** 2026-08-24
**Result:** PASS on browser, Linux desktop native, and a physical Pixel 8. iOS is unproven.
**Amended 2026-08-24:** one acceptance row is downgraded to PARTIAL — see the correction at the
end. The renderer's device proof stands; the "one shared component" claim was spliced across two
different games.

## What shipped

This is an engine fix. Games cannot portably create a React renderer over a native framebuffer;
`@threenative/core/react` owns that mechanism. The starter keeps all appearance in generated
`src/ui/` source. The main `@threenative/core` entry remains React-free; React and
`react-reconciler` are optional peers reached only through the `./react` subpath.

The public path is `createReactOverlay({ canvasLayer })`, with React Native-shaped `View` and
`Text` primitives. It maps React commits to Three.js objects, lays them out in framebuffer pixels,
and draws them through the existing `CanvasLayer`. Unknown elements, styles, and glyphs fail by
name. A thrown component leaves the last good overlay mounted and can recover on the next render.

### Defects this surfaced in `sandbox/fps-framework`

Game bugs, not engine bugs — filed here because the double-check found them, and fixed in that
repository:

1. **No restart on a phone.** `restart` is bound to `["Enter", "NumpadEnter"]`. The web HUD adds a
   `RUN IT AGAIN` touch button for exactly this reason; the native HUD has neither, so a native
   player who runs out of time cannot start another round.
2. **The loading bar never moves.** The native track is a childless
   `<View style={{ background: "#1b2530", height: 6, width: 480 }} />`; `loadFraction` reaches it
   only as a percentage in text.
3. **Poly Haven's credit is missing on native.** Its licence requires a credit a player can see.
   The web end card carries it; the native end card does not.
4. **The key legend lies on touch.** Web hides it behind `desktop-only`; native always draws
   `WASD MOVE · MOUSE1 FIRE · R RELOAD`.

### Frame rate on the device, which this PRD never measured

`uiCommitP50Ms`/`uiCommitP95Ms` are per-commit React costs, not frame time — the doc already says
so. Nothing here measured what the phone actually presents. Measured afterwards on the same Pixel 8
at 2400x1080, thermal status 0 at 31.4 °C, 20 s of steady state via
`dumpsys SurfaceFlinger --timestats`:

```text
totalFrames   = 325      (20 s)
droppedFrames = 0
averageFPS    = 16.360
```

Not stutter — a constant rate with a periodic wobble. `present2present` is 58 ms x185 and 66 ms
x127, i.e. every frame lands seven or eight vsyncs apart on a 120 Hz panel, and
`present2presentDelta` is 0 ms x157 / 8 ms x157, so the interval alternates. `post2acquire` sits in
a 70-98 ms band: the cost is GPU render, not the game. The device playtest's own `sectionP99` puts
`gameFrame` at 2.99 ms, `enemies` 2.87 ms, `physics` 0.65 ms.

Two leads, neither yet A/B'd — the confirming run is blocked on a locked device:
`renderer.resolutionScale` is unset, so native draws all 2.59 Mpx, against 0.32 Mpx for the mobile
web surface the earlier `artifacts/device-profile.json` measured at ~60 fps; and
`src/render/lighting.ts` re-renders a 2048x2048 `PCFSoftShadowMap` with `radius: 3` over a
100 m frustum every frame.

**A trap for whoever measures next.** Frame figures read from the Android playtest lane are not
frame rate. That run reported `p50 1.42 ms` over 1829 frames for 1800 ticks: the harness steps one
frame per tick as fast as it can rather than presenting. A `frame-smoothness`-shaped assertion
(`p95 <= 20`) run with `--target android` passes on a game rendering at 16 fps.

## Follow-up, 2026-08-24 — the starter's shared tree, run on Android

The PARTIAL row above asks for the starter's `react-hud` scenario on `--target android`. Run on the
x86_64 emulator (`emulator-5554`), because the Pixel 8 was locked behind a secure keyguard at the
time. Scaffold reused from this document's own browser lane, `/tmp/threenative-starter-mkjxtm/starter`.

```text
PASS  resource.state.playerX           before -2      after -1.2000024318695068
PASS  component.native-ui.mounted      true
PASS  component.native-ui.objectCount  11
FAIL  diagnostics                      consoleErrors 259, runtimeDiagnostics 259

```

**What this settles.** The starter's one-tree-two-primitives pattern — `HudContent.tsx` driven by
`NativeHud.tsx`'s `View`/`Text` primitives — commits drawable objects under the native Android
runtime, against live game state (`playerX` moved while the HUD was mounted). That was previously
proven only on Linux desktop.

**What it does not settle.** This is an emulator, not the Pixel 8, and there is no pixel proof:
`adb shell screencap` returns black for this SurfaceView, which is a known capture limitation on
emulator GPU surfaces and cannot be told apart from a blank render from the outside. The row stays
PARTIAL until the same scenario runs on the phone with a screenshot step.

### Two engine defects this uncovered

Both sit in `packages/`, and both are on the path between "scaffold a starter" and "see it on
Android" — so neither shows up in a browser or desktop lane.

1. **A freshly scaffolded starter cannot build for Android.** `pnpm build:android` exits 1 with
   `TN_NATIVE_KTX2_UNSUPPORTED: android cannot ship compiled KTX2 textures (native-proof.png)`.
   The shipped `templates/starter/threenative.config.ts` has no `assets` block at all, so textures
   compile to KTX2, which the mobile runtime has no transcoder for. The build only succeeds after
   adding `assets: { models: "none", textures: "none" }` — which is exactly the line
   `sandbox/fps-framework` carries, evidently discovered the same way. The template should either
   ship that default or the android target should fall back to source textures.
2. **`FrameBudget.beginFrame called before the previous frame ended` floods the log.** 259 errors
   across 20 frames — over twelve per frame — and they are what fails the run above. On a longer
   idle launch the same message repeated 341 times. It is not fatal: the app reaches
   `TN_NATIVE_SMOKE_READY` and `TN_PRESENTS_TICK` and keeps presenting. But `noConsoleErrors` is on
   by default, so **every** Android playtest of the starter fails on this regardless of what it
   asserts, which is a plausible reason this lane had not been run before.

### Pixel proof for the Android run

`adb shell screencap` was the wrong tool — it returns black for this SurfaceView. The runner's own
capture path works, so the scenario was re-run with a `screenshot` step
(`docs/verification/prd-216-android-starter/react-hud-shot.playtest.json`, the same assertions plus
a capture). Same three passes, same one diagnostics failure, and this time an image:
`docs/verification/prd-216-android-starter/starter-shared-hud-android.png`, 2400x1080.

Every part of the shared `HudContent.tsx` tree is legible in it, drawn by `NativeHud.tsx`'s
`View`/`Text` primitives at the offsets its `STYLES` table declares (`left: 24, top: 24, gap: 8`):
the `SCORE` label, the score itself in the 5x7 glyph font, the three life pips, and the position
meter with its fill. That is the whole `panel` subtree.

The scene behind it is nearly black — the emulator's software GPU draws little of the platform
geometry. Unrelated to the HUD claim, and not investigated: the assertion here is about the React
tree, which is present, positioned and driven by live state.

So both halves now hold on Android — assertions and pixels. **The row stays PARTIAL for one reason
only: this is an x86_64 emulator, not the Pixel 8.** Re-running this exact scenario against the
phone is what upgrades it, and needs nothing new written.

### `resolutionScale` A/B on the Pixel

`sandbox/fps-framework`, two builds differing only in `renderer.resolutionScale`, measured back to
back through `dumpsys SurfaceFlinger --timestats`, both at thermal status 0 and within 0.1 °C of
each other at launch:

| Arm | Start temp | Frames in 20 s | averageFPS |
| --- | --- | --- | --- |
| unset, i.e. 1.0 — 2400x1080, 2.59 Mpx | 31.5 °C | 335 | **16.88** |
| `resolutionScale: 0.6` — 1440x648, 0.93 Mpx | 31.6 °C | 476 | **23.80** |

A 41% gain from one line, and the baseline reproduces the 16.36 fps measured earlier in the day.

**The more useful half of this result is what it rules out.** Cutting pixels by 2.8x bought only
1.41x the frame rate, so a little over half the per-frame cost does not scale with resolution at
all. Fill rate is a real term but not the dominant one, and shipping a lower `resolutionScale`
would leave most of the problem in place. The obvious resolution-independent suspect is the
2048x2048 `PCFSoftShadowMap` in `sandbox/fps-framework/src/render/lighting.ts` — a fixed-size
render target redrawn every frame over a 100 m ortho frustum, whose cost is identical at either
scale. That is the next thing to A/B, and it has not been measured.

The earlier 11.5 fps reading for the 0.6 arm was thermal throttling (35.7 °C, status 1), not the
change. Recorded because it is the shape of mistake this lane invites.

### The loading screen never appears on native — an engine bug

Reported from play, then traced. On a phone the game shows a black screen for the whole asset load,
where the browser shows a progress bar. `sandbox/fps-framework/src/ui/NativeHud.tsx` does implement
the loading state — an `if (!state.ready)` branch with a plate, the title and a percentage — so the
game is not at fault. It cannot be reached.

`packages/core/src/game.ts` boots in this order:

```text
for (plugin of plugins) await plugin.setup(...)   // the React overlay mounts here
await scene.load(ctx)                              // every asset loads here, blocking
this.#enterScene(scene, ctx)
gameLoop.start()                                   // last line of boot
```

On native the render loop is the only thing that can put pixels on the screen, and it does not
start until after `await scene.load(ctx)` has resolved. The overlay is mounted and React has
committed, but no frame is drawn, so nothing the HUD contains can be seen until the very moment it
is no longer needed. On web the same component works, because `react-dom` paints into the DOM
without waiting for the game loop.

This is the framework's own "a feature that works on web only is unfinished" case, and it applies
to every native game, not just this one: **no ThreeNative game can currently show a loading screen
on a phone.** Fixing it means giving the native path a way to draw before the scene has loaded —
starting the loop before `scene.load` and gating the scene step rather than the whole loop, or
drawing the overlay once between mount and load.

### Why the loading-screen fix is not a one-line move

The obvious fix — hoist `gameLoop.start()` above `await scene.load(ctx)` — is wrong, and the reason
is worth writing down before someone tries it.

What already works in favour of a fix: the render callback draws the CanvasLayer overlay
**unconditionally**, `if (canvasLayer.scene.children.length > 0)`, while everything scene-shaped is
guarded behind `#sceneEntered` — `scene.render`, `scene.update`, the scene frame function. So a
loop running during `scene.load` would draw the React HUD and step no gameplay. The machinery is
already correct; only the boot ordering withholds it.

What breaks: `runtime.holdStart` (`packages/core/src/playtest.ts:89`). The playtest plugin hands the
game a gate and the boot waits on it at `await Promise.all(startGates)`, immediately before
`gameLoop.start()`. Its whole purpose is that **no frame is stepped before the runner attaches**,
which is what makes a scenario deterministic. Starting the loop earlier steps frames during load
and voids that contract — the class of change that makes a harness report green on nothing.

Two designs, and they differ in what they risk:

1. **Gate the step, not the loop.** Start the loop before `scene.load`; make the start gates
   suppress `onUpdate` instead of suppressing `gameLoop.start()`. Rendering proceeds, gameplay does
   not. Needs the fixed-step accumulator to not bank elapsed time during the hold, or the first
   real tick arrives with a `dt` covering the whole asset load. Touches the loop every replay and
   playtest depends on.
2. **A boot render pump.** Between plugin setup and `scene.load`, draw the overlay from a small
   separate pass, stopped when the real loop starts. It cannot touch the accumulator, so
   determinism is untouched by construction. But it is a second render path — the exact "fast path
   nobody tests" this file's own comments warn against — and the React overlay needs its
   per-frame `refresh()` to show changing progress, which means the pump grows a scheduler.

(1) is the smaller surface and the honest shape; (2) is safer for the playtest contract and worse
for the codebase. Either way the acceptance test is the same: a native scenario that asserts a
drawable overlay object exists **while `state.ready` is still false**, which no current scenario does.
