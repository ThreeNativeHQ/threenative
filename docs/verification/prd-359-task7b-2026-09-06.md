# PRD-359 Task 7b — networking qualification matrix aggregator

Recorded 2026-09-06 UTC, worktree `.worktrees/networking-359`, branch `networking-359`.

Task 7b adds the aggregator that decides whether the PRD's platform qualification actually
passed. It reads the lane manifest and the per-lane result files written by
`scripts/run-networking-proof.mjs` (Task 7a) and produces the release verdict. It does not
run any lane; Task 7c does that.

## Files

| File | Role |
| --- | --- |
| `scripts/verify-networking-matrix.mjs` | The aggregator. `node scripts/verify-networking-matrix.mjs --manifest <path> --results <dir>` |
| `scripts/__tests__/networking-matrix.spec.ts` | 13 tests, including the five the execution row names |
| `docs/PRDs/networking/qualification-lanes.json` | 19-lane manifest derived from the PRD platform matrix |
| `.github/workflows/native-platforms.yml` | New `networking-matrix` job invoking the aggregator over collected evidence |

## What the aggregator rejects

Aggregation is by exact `(laneId, profile)` pair. It fails closed on a duplicate pair, a
missing required row, a commit that disagrees with the manifest or with the other rows, a
protocol version that differs across rows, a per-lane binary hash that does not match that
lane's expected hash, an empty `observations` array, a zero `assertionCount`, and a
non-finite metric. Only lanes labelled iOS may carry `owner-deferred`; a non-iOS lane
marked deferred is rejected by name. Deferred rows are printed explicitly and never
counted as passes.

Expected hashes in the manifest are `null` today because no lane has run. A required lane
with a null expected hash fails, which is the honest current state: Task 7c fills those in
as it records each real run.

## Manifest

19 lanes: four desktop browsers plus Chrome on Android, four desktop OS/arch pairs,
physical Android arm64 and the x86_64 emulator, two crossplay pairs, one server soak, and
the three iOS lanes plus `browser-safari-ios` and `crossplay-android-ios`. Sixteen are
required; the five iOS-labelled lanes are `owner-deferred`, which is the only deferral the
PRD allows. Every lane requires both the `clean-lan` and `impaired` profiles.

## Review correction

The first draft of the aggregator embedded the execution row's test names in its own error
messages — `... (rejects Android deferral)`, `... (rejects wrong commit)`, `... (rejects
missing required lane)` — and three tests asserted on those parentheticals. That couples
the assertion to a label rather than to behavior. The parentheticals were removed from the
production messages and the affected assertions were repointed at the real text
(`/cannot be deferred: only iOS lanes may be owner-deferred/`,
`/commit .* does not match manifest commit/`). Removing them turned `rejects wrong commit`
red until its assertion was corrected, which is the evidence that the coupling was real.
The red-green controls above were re-run after the correction.

## Complexity refactor

The first draft put `validateResultRow`, `validateManifest` and `aggregateMatrix` at
cognitive complexity 32, 24 and 68 against a limit of 15. They were split into named
per-concern helpers until `biome check` reports zero complexity warnings for the file; no
suppression was added. Behaviour was held fixed and checked differentially — the
pre-refactor and post-refactor scripts produce byte-identical stdout, stderr and exit codes
for the empty-evidence, missing-directory and missing-argument cases — and both negative
controls above were re-run against the refactored file with the same red and green.

## CI

The first shape of this job demanded full lane evidence on every push, so it was red on
every run. That was the wrong gate: ordinary CI cannot execute the qualification lanes, so
their absence is the normal state, not a failure. Demanding them made a permanently red job
that reported nothing anyone could act on.

The job now runs the aggregator over whatever evidence the run has. With none, the verdict
is `UNQUALIFIED`, exit 0, and the summary says so in as many words:

```text
=== Networking Qualification Matrix Summary ===
Verdict: UNQUALIFIED
Required lanes: 0 / 28 passed
Deferred lanes: 0
No lane evidence in this run: no platform is qualified and no verdict is claimed.
The release verdict requires --require-evidence over real lane results.
```

The false green the execution row forbids is closed from two sides. `--require-evidence`
makes an empty evidence set a failure, and that is the release path. And **partial evidence
still fails**: the moment a single lane result appears, every required row is enforced.
Verified against the real 19-lane manifest with one passing `desktop-linux-x64` result and
nothing else:

```text
partial-evidence exit=1
```

So a green here means "the gate works and nothing ran", which is true, and it can never mean
"the platforms passed".

The job is three steps: checkout, download, verdict. The aggregator is plain Node with no
dependencies, so it needs no pnpm install or toolchain setup, and its own suite already runs
in CI's `test-unit` shards — running it here too would only duplicate that work.

The download pattern is `networking-lane-*`, not `native-*`. The platform jobs upload
conformance artifacts under `native-*`, and the aggregator validates every JSON under its
results path, so pointing it at those would have failed the gate on the wrong evidence.
Task 7c's proof runner publishes the `networking-lane-*` artifacts; until then nothing
matches and the directory is empty.

`native-platforms.yml` is not in the nine required checks either way.

## Limits

version and OS minimum in `qualification-lanes.json` is an explicit `null` placeholder that
Task 7c must fill from real runs. Nothing here is evidence that any platform works.
