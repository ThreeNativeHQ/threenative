## The performance dimension — measured, and NOT REACHED

This is PRD-064 Phase 4, which is PRD-058 Phase 5 executed unchanged: the unmodified scaffolded
platformer at 1920×1080, web against native on one identified host, with the two arms resolving to
different process and artifact identities. The authoritative budgets are PRD-058's own.

**The measurement, from the branch's own corrected judge**
(`.runtime/prd064/production/desktop-pair-8/production-evidence.json`, live display, corrected to read
*presented* frames rather than rAF callbacks): **web** p50 16.70, p95 16.80, p99 16.80 ms, mean
**59.97 fps**; **native** p50 16.91, p95 18.06, p99 18.94 ms, mean **58.08 fps**; startup p95
1,501 ms; draw calls 81 and triangles 3,276. Every absolute budget passes except `minMeanFps: 60`,
which web misses by 0.03 fps, and **all four pair legs fail**, so `TN_PROD_PERFORMANCE_BUDGET`
carries both a web and a native finding.

**The web miss is a ceiling of this host's display path, not the game's cost.** Measured today, with
the profiler's own browser recipe and no workload at all:

| Measurement | mean interval | implied fps |
|---|---:|---:|
| profiler's display path, zero workload (X11 ozone, `WAYLAND_DISPLAY` stripped by `captureEnvironment.ts`) | 16.676 ms | **59.966** |
| the same probe with the session's Wayland variables intact | 16.666 ms | **60.001** |
| the unmodified platformer, profiler instrumentation, clean checkout at `bba8631fc` (1.0 s window, 59 presented samples) | 16.6746 ms | 59.9715 |
| the 30 s collection the box is judged on, `desktop-pair-8` (4,435 presented intervals from 12,900 callbacks) | 16.675 ms | 59.97 |

The active mode is `1920x1080@60.00` on both outputs (`kscreen-doctor -o`), so the 59.966 is not a
59.94 Hz panel. It is what an X11 client on Xwayland measures on this KDE Wayland session, and
`packages/playtest/src/runner/captureEnvironment.ts` strips `WAYLAND_DISPLAY`, `WAYLAND_SOCKET` and
`XDG_SESSION_TYPE` from every browser child, so no profiled web run can take the 60.001 path. A mean
of ≥ 60.0 fps needs a mean interval of ≤ 16.6667 ms and the path delivers 16.676 ms: **a 0.056 %
shortfall, and the platformer reaches it without dropping a frame** (p99 16.80 ms against a 33.0 ms
limit). The floor has no tolerance by construction — one dropped frame in the 2026-09-28 collection's
32 s, 1,919-sample run gives 59.969 fps and fails too.

**The native miss is real and is root-caused, not attributed to the host.** Native's deficit sits
below web's ceiling rather than at it, and the branch's trace finds it in the pacer:
`paceToDisplayFrame()` (`packages/runtime-native/src/webgpu/bindings_presentation.cpp:125`) returns
`SoftwareDeadline` on its first check at `:127` because `g_presentationPacing.running` is set only by
`notePresentationFramesStarted()`, whose sole caller is the Android JNI shim under
`#if defined(__ANDROID__)`. Desktop therefore never gets a display timestamp and always falls through
to the `steady_clock` branch at `:245-254`, sleeping 1/60 s of host clock per frame. The run's own
meter reads `periodP50Ms 16.96` / `periodMeanMs 17.04` against `sumP50Ms 1.23` of frame work — about
15.7 ms of every 16.96 ms period is that sleep, and its wake-up latency is the deficit. The
2026-09-28 API check narrowed the fix and claimed none: SDL 3.2.30 and the Dawn surface expose no
desktop per-present timestamp or vblank callback to feed the existing condition variable, and wiring
it to a host-clock guess would repeat the timing error. The same missing signal is why native's
"presented" series is a dispatch cadence rather than the display's.

**Uncollected, and therefore not claimed either way.** The profile's `--live-clock` flag exists
because a profile run *is* a playtest run, and core froze the live clock, so the synthetic workload
presented a standing world — the 163–174 fps means and ~16.8 ms p95 in the 2026-09-27 collections
describe that frozen world. No live-clock collection has ever been executed, so no number in this
file moves on it. This host is shared, so an uncontended GPU measurement is not available here either.

The two honest readings are therefore: **web cannot meet this floor on this host's display path at
all**, and **native has a named, unfixed pacer deficit that would have to close before
"native no slower than web" could hold even on a display path that permits it.** Redefining the
p95 statistic is PRD-058's call and was left untouched rather than relaxed to pass.

## Android executed every row for the first time, and every verdict is a build failure

The 2026-08-29 ledger recorded Android `0 / 0 / 74` — blocked before Gradle on a stale SDL3 pin, no
row executed. That pin is fixed (`SDL3_ANDROID_VERSION` is `3.2.30` in
`packages/runtime-native/scripts/package-android.mjs:268`, and `third_party/sdl3-android/SDL3-3.2.30.aar`
is present), the AVD boots, and today's run returns **a per-row verdict for all 93 registry rows**,
which is the property PRD-064 §6 criterion 3 asked for: never 67 silent passes, never a skipped
target counted as green.

**Every one of the 90 failures is the same environmental one.** Each row carries
`native.completed: false`, `phase: "build"`, and:

```
Android V8 build receipt is missing: <checkout>/packages/runtime-native/third_party/v8-android/build-receipt.json
Execution failed for task ':app:verifyV8Dependency'.
```

The payload it receipts (`include/`, `lib/`, `snapshot_blob`) is present; the receipt is produced by
`packages/runtime-native/scripts/build-android-v8.mjs`, which is the heavy Android V8 build the CI job
`native-platforms / Publish the Android V8 payload` currently skips. So **no Android row failed on its
merits today** — the lane cannot render anything until that payload is built, and the same cause fails
the `androidMultitouch` supplemental (`status: "fail"`, exit 1), which is PRD-055 criterion 2. Phase
3's *"closed in this phase or explicitly is not"* resolves to **explicitly not**.

The three blocked rows are dispositions, not failures: `99-scroll-input` and `100-world-field-hash`
are `Registry row is not implemented`, and `90-document-window-stubs` is
`TN_PARITY_ROW_EXCLUDED: android-canvas2d-document-window-stubs` — the Android preset keeps
`TN_ENABLE_CANVAS2D=OFF`, declared in `registry.json`'s `exclusions[]` with an owner and a reason.

**A reader must not take `0 pass / 90 fail` for a mobile-readiness verdict.** It is one build
precondition, and this file names it rather than letting the summary imply ninety engine defects.
