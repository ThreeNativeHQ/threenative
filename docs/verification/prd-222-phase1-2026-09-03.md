# PRD-222 Phase 1 — the gates exist and are observed red — 2026-09-03

What executed: the `assert.parity` evaluator, the shipped-scenario fps floors, and one red
observation on a real scaffolded-template run. What did **not** execute: any device lane — every
number below is the browser lane (private Xvfb, SwiftShader), and no claim is made past it.

## `assert.parity` (ledger row 2)

Landed in `packages/playtest`: scenario key `assert.parity`, hydrated at load from the other
half's saved run report (the `reachability` artifact pattern), evaluated by
`src/evaluators/parity-evidence.ts`. It proves what the artifacts can prove — same device
(`deviceMetrics.serial` on both halves), thermally comparable pair, fps ratio at or above the
floor — and reports the directed `nativeFps ÷ webFps` ratio on every path, including the
refusals. Which scene the reference ran is the pair protocol the operator owns; the report
format carries no scene identity, and the assertion does not claim it did.

Red-first, as the phase requires: the spec (`__tests__/parity.spec.ts`, 16 tests) ran against the
unmodified schema first. The shape tests failed because `assert.parity` did not exist —
`validatePlaytestScenario` rejected the key — and every evaluation test failed with it. After the
implementation: 16/16 green, and the package's registry meta-specs (doc drift, runner observation
paths, vacuous-assertion audit, all-families dispatch) updated in the same change.

## The fps floors (ledger row 3)

All ten templates now carry an fps floor beside their ceilings: the eight game kits'
`performance.playtest.json` plus `minimal` and `starter`'s `play.playtest.json`, each
`minFps: 30` — Tier 3's Floor for a medium/heavy scene.

**Red observed once**, on the platformer template, by moving the floor above the measured value
(`scripts/verify-one-template.ts platformer`, floor mutated to 2000, full scaffold + browser run):

```
performance.minFps expected at least 2000 fps, observed 1000.
{"actual": 1000, "expected": 2000, "sampleCount": 1024, "unit": "fps"}
exit: 1
```

Restored to 30, the same run passes (a prior green run with the 30 floor is in the same log
family; `maxDrawCalls` 160/200, triangles 6127/7700, fps 1000).

**The lane finding that matters:** the browser lane measures ~1000 fps, not ~60 — the private
Xvfb + SwiftShader lane runs the render loop uncapped, so `performanceSeries.frameMs` on this
lane is the tick cost, not a presented frame at a panel cadence. The shipped floor is therefore a
safety net on the browser lane, and **the device lane owns every presented-fps claim** (method
rule 2, again). A `minFps` floor on `--target android` runs against the device's real presented
rate and is the gate the Tier table means.

## No lane skips (the third Phase 1 item)

Pre-existing and unchanged: `TN_PLAYTEST_UNSUPPORTED_ON_TARGET` names the working target on
lanes without the observer (androidRunner + step dispatch; covered by `click-step.spec.ts`).
`assert.parity` declares `supportedOn` and required capabilities like every other registry kind,
so an unsupported lane refuses by the same mechanism rather than skipping.
