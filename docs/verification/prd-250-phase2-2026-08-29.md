# PRD-250 Phase 2 — worker message, clone, error and teardown semantics, 2026-08-29

Closes Phase 2 of `docs/PRDs/done/PRD-250-native-workers-are-actually-workers.md`.
Phase 3 (URL/scope matrix, CI lanes, rollback selector) stays open.

**Host:** Linux x86-64, V8 desktop engine, `build/tn-linux` Release.
**Artifacts:** `threenative-worker-production-test`, `libmystral-runtime.a`, both rebuilt for every
mutation below. **Node** v20.19.6, **vitest** 4.1.10.

## What was wrong

Phase 1 made native workers real threads. The wire between the isolates was still a bare
`JSON.stringify` in both directions.

| Value a game might post | What arrived before | Now |
| --- | --- | --- |
| `{ run: () => 1 }` | `{}` — the field vanished | refused, `DataCloneError`, names `function at message.run` |
| `{ missing: undefined }` | `{}` | refused, names the path |
| `{ n: NaN }` / `Infinity` | `{ n: null }` | refused, names `NaN` / `Infinity` |
| `{ bytes: new Uint8Array(4) }` | `{ bytes: {"0":0,…} }` | refused, names `Uint8Array` |
| `{ when: new Date(0) }` | an ISO string | refused, names `Date` |
| `new Map()` / `new Set()` | `{}` | refused |
| a class instance | a bare record, prototype gone | refused, names `<Name> instance` |
| a reference cycle | `TypeError` from `JSON.stringify` | refused, names `a reference cycle at <path>` |
| `{ x: shared, y: shared }` | two objects; shared identity lost | refused, names `a second reference to one object` |

Admitted rows are the ones JSON round-trips exactly: `null`, boolean, finite number, string, plain
array, plain object, and top-level `undefined` as an empty payload. `ArrayBuffer` transfer stays
refused by name, which this PRD's "either implement each row or reject it with a named clone error"
permits.

The walk tests **prototype depth, not prototype identity**. Identity is per-realm: the first
implementation refused a plain object built in another realm for carrying the wrong
`Object.prototype`, which the existing `url-worker-shim` test caught immediately.

## Three more defects found while wiring it

1. **A top-level throw reported success.** `WorkerThread` evaluated classic worker source with
   `Engine::eval`, which compiles as an ES module (`v8_engine.cpp:316-370`). A module that throws
   resolves to a **rejected promise**, so `module->Evaluate(...).ToLocal(&result)` *succeeds*:
   `eval` returned true, the host printed `[Worker 4] User code executed successfully`, no
   `ERROR` was queued and the game was never told its worker was dead on arrival. Classic Blob
   source is now evaluated with `evalScript` (classic script, `Script::Run`), which is both the
   correct scope semantics for a classic worker and the reason the throw is observable. The
   pending-exception branch now queues an `ERROR` as well instead of only printing to stderr.
2. **A handler throw was swallowed.** `__processMessages` caught it, printed it to the worker's own
   console and called the worker's local `onerror`. The caller on the main thread received neither a
   result nor an error. New `__workerPostError` queues it as one `ERROR` message.
3. **A self-closing worker's final result was destroyed.** `processWorkerMessages` pushed a stopped
   worker onto `deadWorkers` and `continue`d *before* draining it, then `terminateWorker` destroyed
   the queue. Draining now happens first, and a worker is reaped only once nothing is left to
   deliver.

Also fixed: four worker natives guarded `g_workerEngine` for null and then built the early return by
dereferencing it. `shutdown()` is now idempotent, closes the registry to creation, and
`runtime.cpp` calls it after terminating tracked workers.

## A regression this phase shipped, then caught and fixed

The first Phase 2 commit added `WorkerRegistry::instance().shutdown()` to the runtime's teardown so
a script running during teardown could not start a thread whose completions would land in a
released engine. `shutdown()` flipped the registry's `initialized_` flag — and **the registry is a
process-wide singleton**, so the first Runtime to tear down closed it for every later Runtime in
the same process. `setupURL()` then failed its availability check and the whole URL/Worker layer
never installed.

`threenative-webgpu-bindings-reentrancy-test` creates three Runtimes in one process
(`webgpu_bindings_reentrancy_test.cpp:1753`, `:1754`, `:1822`) and went red with a revoked-proxy
failure that named nothing about workers. It was caught by `pnpm budgets` demanding a coverage
regeneration, and confirmed by reverting only the four source files this phase touched and watching
the same target go green (22 passed / 3 skipped).

The fix separates the two ideas the flag was carrying: `initialized_` still means "the worker
sources are linked", and a new `accepting_` flag means "this Runtime's registry takes new workers".
`shutdown()` clears `accepting_` and joins; `open()` sets it, and runtime startup calls it. Storage
stays process-wide, lifetime is per-Runtime.

A contract now pins it rather than leaving it to an unrelated target to notice:
`registryReopensForASecondRuntime` destroys the first Runtime, creates a second, and requires a
worker in it to deliver a message. Observed red — delete `workerRegistry->open()` from
`setupURL()`: `WORKER_CONTRACT registryReopensForASecondRuntime FAIL`, `FAILED: a second Runtime
could not use workers`, exit 1.
