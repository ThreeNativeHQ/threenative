## Implementation

- `/game` carries the exact four-channel map from `PROTOCOL.md`: input and state
  datagrams, ordered action and clock streams.
- The server advances one authoritative simulation at 60 Hz and broadcasts
  per-player state snapshots every third tick (20 Hz).
- Input axes are finite-number validated and clamped to `[-1, 1]`; stale input
  ticks and duplicate action IDs are discarded.
- Client state parsing rejects malformed or stale snapshots and tracks the local
  player, one authenticated peer, server tick, remote distance, and accepted
  action acknowledgements.
- The native-smoke scene owns separate local and remote player meshes; they stay
  hidden until the corresponding validated snapshot state exists and are
  positioned from `networkLocalX/Z` and `networkRemoteX/Z`.

## Two-client live proof

Two actual native runtime clients joined the authenticated `/game` fixture with
four channels, sent different inputs, observed each other’s server snapshots,
and received numbered action acknowledgements. The live raw-client probe
reported:

```text
PASS: player-a observed peer and accepted action distance=0.283
PASS: player-b observed peer and accepted action distance=0.283
```

The sender-drop case is covered by `TestDroppedInputDoesNotMovePlayer`, which
holds a joined player for 60 authoritative ticks with no input and asserts that
the server position remains `(0, 0)`.

The production `networking-game.ts` wrapper also reached its staged grant in a
native runtime, but the local self-signed HTTPS issuer was rejected by the
runtime fetch implementation before WebTransport (`grant-status:200`, then
`SSL peer certificate or SSH remote key was not OK`). This fixture limitation
does not weaken the live `/game` result above; it remains an unclaimed wrapper
qualification until a system-trusted issuer certificate is available.
