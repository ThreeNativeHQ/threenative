# PRD-244 verification

Date: 2026-08-28

Status: implementation complete in this lane. The source PRD remains unchanged at
`docs/PRDs/feature-mining/PRD-244-the-scenes-bvh-reaches-the-gpu.md`.

## What shipped

- `GPUSceneBVH` packs selected visible meshes into world-space positions, indices, normals, and
  the serialized `three-mesh-bvh` node layout exposed as named TSL storage nodes.
- The BVH is built with `indirect: true`, so `geometry.index` keeps source order while the packed
  index buffer is materialised in leaf order through `resolveTriangleIndex`. The per-triangle
  material assignment is permuted by the same map and then run-length encoded, so
  `materialGroups` addresses the uploaded buffer. One source material can therefore span more than
  one range once the SAH sort interleaves its triangles; the type comment says so.
- The core entry point exposes the upstream `bvhIntersectFirstHit` and `rayStruct` directly; the
  example owns the WGSL adapter and the visible contact-occlusion material in `src/render/`.
- Stable storage-node identities survive `rebuild()`. `GPUSceneBVH` implements `IComputeDriven`,
  releases all four storage buffers on detach, and is registered through `ctx.add`.
- The picking example exercises indexed grouped geometry, transformed meshes, and an
  `InstancedMesh`; its playtest asserts a changed rendered contact effect after rebuild.

The playtest, desktop conformance and `native:build` rows were recorded before the material-group

The differential test logs the two implementations explicitly:

```text
{"cpuImplementation":"ScenePicker.raycast (CPU Raycaster/MeshBVH)","gpuImplementation":"packed bvh.nodes stack walk (CPU mirror of the TSL node layout)","samples":64}
```

**What that unit comparison proves, precisely.** The second side is a CPU mirror of the uploaded
node layout, not the shipped GPU kernel. `bvhIntersectFirstHit` is a TSL/WGSL function and cannot
execute in the node-environment vitest suite, so the unit test instead walks `bvh.nodes` with the
same stack, slab test, leaf-offset and leaf-count decoding the shipped WGSL uses — six float bounds
per node, then `rightChildOrTriangleOffset` and `splitAxisOrTriangleCount`. It therefore proves that
the uploaded node buffer, positions and indices are mutually consistent and agree with
`ScenePicker`; it does not prove the WGSL kernel itself. The GPU kernel is exercised only by the
playtest and the desktop conformance row below, which drive the real build.

An earlier revision of this record claimed the unit test executed
`three-mesh-bvh/webgpu bvhIntersectFirstHit`. It did not, and the helper it used never read
`bvh.nodes` at all: with one root node word overwritten, that helper still passed all 64 samples.
The replacement helper fails on the same mutation (see the integration controls below).

The conformance runner reports 71 unselected historical rows as blocked when invoked with
`--only-tests 76-gpu-scene-bvh`; the selected web and desktop rows both pass. The native process
reports `[MystralRT] No hardware RT available, using stub backend`; this feature uses WebGPU TSL
storage tracing, not hardware ray-tracing calls.

The positive lifecycle proof now runs a real `game.goto()` loop rather than a mocked registry.
Three `trace → idle → trace` transitions were driven through `defineGame`; every departed snapshot
reported `released === true`, all four storage attributes of all four snapshots fired their real

of every cycle. That is an accounting of engine-held buffer handles and bytes across a real
transition — it is not a process-RSS measurement, and no claim about heap growth is made here.

## Cost and boundary

The public capability documentation records that `rebuild()` performs an explicit CPU flatten and
SAH build proportional to selected triangles. In the 72-triangle example, the observed build
measurement was approximately `1.3 ms`. `process()` is intentionally a no-op, so the package adds
no per-frame dispatch; the game-owned TSL kernel pays for each shader ray, and this example invokes
it per contact-floor fragment.

`ScenePicker` and `GPUSceneBVH` remain separate. `ScenePicker` owns object-local CPU BVHs and
camera/pointer ray semantics; `GPUSceneBVH` owns one predicate-selected, world-space storage
snapshot whose lifetime follows the renderer. Sharing the trees would couple CPU picking to GPU
buffer replacement and release without removing either representation.
