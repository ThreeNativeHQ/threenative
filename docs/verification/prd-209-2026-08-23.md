## What the spike had to decide

Phase 0 was written to decide whether `@threenative/core` gains a portable text surface
(candidate E) or whether the generated `src/render/hud.ts` alone is enough (candidate G). The
PRD's own rule: *if a game reaches readable text in under 20 lines using candidate G alone, this
PRD closes having shipped G's promotion and no package code.* It does. The measurements below are
why.

## Arm B — SDF atlas, and why it stopped

Arm B was authored in full and executed on web:
`/tmp/.../scratchpad/spike-armB/sdf-text.js` (kept out of the tree; it is not being adopted).
It builds a signed-distance atlas as a `DataTexture` at boot — Canvas2D cannot rasterise it,
because the native host's `document.createElement('canvas')` is a stub — and shades the edge with
TSL nodes, because `raw-glsl-shader-material-webgpu` is an **excluded** conformance row: raw GLSL
`ShaderMaterial` fails under `WebGPURenderer` on every target.

Result on web: **2 791 bright pixels, bounds `[49,55,313,86]`.** It clears the 1 000-pixel floor
by 2.8× — and it is **not readable**. At a 5×7 source resolution the distance field merges
adjacent cells and destroys glyph identity: the capture
(`/tmp/.../scratchpad/spike-armB/armB-normal.png`) reads **`2COKE ]500`** where it should read
`SCORE 1200`. The `S` collapses into a `2`, the `R` into a `K`, the `1` into a `]`.

This is the single most useful thing the spike found: **the bright-pixel instrument passes arm B.**
A spike that had only read the number would have adopted the worse arm and shipped an unreadable
HUD. The PRD's insistence that the capture be looked at — "readable text on the emulator
screenshot, not just a green number" — is what caught it.

Arm B was not carried to desktop or Android. It lost on web, on the criterion that matters, and
carrying a losing arm to two more lanes would not change the decision. That is a deliberate
omission, stated here rather than left implied.

## The decision rule, evaluated

> *If a game reaches readable text in under 20 lines using candidate G alone …*

Candidate G ships `src/render/hud.ts` as generated user source. What the **game** writes to get a
readout, from `templates/minimal/src/scenes/Play.ts`:

```ts
import { createHud } from "../render/hud.js";                                    // 1
const hud = ctx.entities.add("hud", createHud(ctx.camera as PerspectiveCamera, "SCORE"));  // 2
hud.update({ primary: state.score, seconds: elapsed });                          // 3
```

**Three statements.** The bar was twenty lines. Adding a second readout is one more field on the
`update` call. There is no cost a package could remove.

And rule 3 of the root AGENTS.md decides the rest: the glyph table, colour, size, anchor, labels
and update timing are all things a game must be free to change, and under candidate G it changes
them by editing its own file. A `@threenative/core` text surface would have to expose every one of
those as an option, which is a widget with extra steps.

**Conclusion: G-only. No package code. Ledger row 1 narrows to the template helper; the rows about
package surface are deleted, not left TBD.**

## What changed in the tree

No package gained a line. Two template `AGENTS.md` files did, because a convention missing from
the templates' `AGENTS.md` does not exist:

- **`templates/starter/AGENTS.md`** — the portability section said *"Add a native HUD in your
  game-owned render code only if your game needs one."* That sentence is how bug 2 happened: an
  agent building for Android reads "only if" and ships a game whose entire HUD is `createRoot` in
  `src/main.ts`, which the native host never executes. It now states plainly that `src/ui/Hud.tsx`
  draws nothing on any native target, names the 69-line file to lift from the `minimal` template,
  carries the measured pixel counts, warns off `CanvasTexture` with the 1 939-vs-0 number, and
  repeats the one-HUD-layer rule.
- **`templates/minimal/AGENTS.md`** — its HUD section claimed *"`main.ts` subscribes a plugin to
  the store and writes to a DOM node."* `src/main.ts` says the opposite in a comment: *"No DOM
  readout here."* Prose and code disagreed, so the prose was fixed. It now names the geometry HUD
  as the shape that survives every target, with the measured counts.

`pnpm sync:agents` regenerated both `CLAUDE.md` mirrors (`16 mirrors, 2 written`).

### Criterion 1, precisely

What **is** proven: the geometry text path renders identical, legible text on web, Linux desktop
native, the Android emulator and a physical Pixel 8, from one unbranched source; and the `minimal`
template's native entry `src/game.ts` reaches `Play` reaches `createHud`, so its HUD is on the

`playtests/play.playtest.json` asserts `hud.glyphs` *changed* at boot, and

the shared scene, not from a scaffolded project's bundle. Doing that properly needs a built
`create-threenative` dist and a full install of the scaffolded project, which was out of the Phase 0
budget. This is the honest gap in criterion 1 and it belongs to the PRD's Phase 1 user verification.

## Two gate bugs found while running this, neither fixed here

Both are outside PRD-209 and are reported rather than patched, since fixing another PRD's file
is exactly the unrelated tidying the root AGENTS.md rejects.

1. **An Android parity run poisons `pnpm test`.** `runtime-next-contract.test.mjs`'s
   "generated Android bundle provenance" case is `skipIf` the artifact at
   `android/app/build/generated/threenative/assets/scripts/main.js` is absent — but the
   conformance Android lane writes that **same path** with its own bundle. After
   `--target android`, the test un-skips and compares a conformance bundle against
   `examples/native-smoke/src/game.ts`'s SHA-256, and fails:

   ```
   AssertionError: The input did not match the regular expression
   /THREENATIVE_ANDROID_NATIVE_SMOKE_SOURCE_SHA256:723f96a8…/
   ```

   The written meta names the culprit outright:
   `{"kind": "threenative-android-conformance", "source": ".../artifacts/conformance/android-hardware-bundles/31-hud-readout-updates.js"}`.
   The guard should discriminate on `kind`, not on existence. Any agent who runs an Android
   parity lane and then `pnpm test` gets this red and will hunt it in the wrong place. Deleting
   the build output cleared it here.

2. **`orphan-cleanup.sh` cannot separate lanes for processes.** Its own comment explains that
   counting every `/tmp/threenative-*` made a sibling lane's directories read as this run's
   leak, and it fixed that for *directories* with `TN_TEST_TEMP_TAG`. The process check has no
   equivalent: `owned` matches any `playwright_chromiumdev_profile-` in the whole process
   table. Whatever the true cause of the failure above, the guard cannot currently tell a real
   leak from a neighbour's browser.
