# The path to 60 fps native — found, with the arithmetic that closes it

**2026-08-27.** Filed as [PRD-227 — the frame crosses once](../PRDs/PRD-227-the-frame-crosses-once.md).
This is the answer the ablation ladder was built to produce. It is a **compound
fix of two changes that must land together**, and it is the only combination whose arithmetic
reaches 60 fps. Companion to the [handover](HANDOVER-native-60fps-2026-08-27.md).

---

## The finding in one line

**The native host crosses the JavaScript↔C++ seam 5,713 times per frame, and the *cost of the seam
itself* — dispatch, per-value handles, allocator churn, and the megamorphic inline caches that
dynamically-shaped wrapper objects force on three.js — is 22.3 ms of the Pixel 8's 37.7 ms frame.
Removing the seam removes 59% of the frame and lands at ~15.4 ms, which is 65 fps.**

---

## Where the frame goes

### Desktop, measured directly this session

Profiled control, 619 eligible frames, `work = threadCpu − present` = 23.919 ms/frame:

| Term | ms | % | Source |
| --- | ---: | ---: | --- |
| JavaScript + non-bridge render-thread work | 14.77 | 61.8% | `work − bridgeNs` |
| bridge marshalling + handle churn | 3.79 | 15.8% | `bridgeOverheadNs` |
| in-handler work (arg parse, wrapper create) | 3.32 | 13.9% | `bridgeNs − overhead − commandNs` |
| backend commands (wgpu) | 2.04 | 8.5% | `commandNs` |
| **bridge total** | **7.11** | **29.7%** | overhead + in-handler |

Per frame: **5,713 crossings, 15,005 marshalled arguments.**

**Cross-check, and it is the one the PRD demanded.** The A2 ablation — physically removing the
backend calls and re-measuring — gives the backend term as **1.95 ms**. The `commandNs` instrument,
which is a completely different mechanism, gives **2.037 ms**. **0.09 ms apart.** Two independent
routes to the same term now agree, so the budget is cross-checked rather than true by construction.
This closes the gap that arm A4 was scheduled to close.

### Device, from F13's symbolized simpleperf profile

SDLThread self time, 37.2 ms CPU/frame, Pixel 8:

| Term | ms | Fate under the fix |
| --- | ---: | --- |
| actual JavaScript running three.js (V8 JIT) | 10.1 | **stays** |
| V8 machinery (22.9 V8 total − 10.1 JS) | 12.8 | **removed** — per-crossing scaffolding + megamorphic ICs |
| `libmystral` (bridge dispatch + backend) | 8.1 | **mostly removed** — per-crossing dispatch |
| `libc`/scudo allocator churn | 4.3 | **mostly removed** — one Persistent + wrapper per crossed value |
| Mali driver | 2.3 | **stays** |
| **total** | **37.7** | F13 states 37.2 — the model closes |

## The fix: two changes, together

### Change 1 — the frame crosses once, not 5,713 times

Three.js records the frame's WebGPU command stream in JavaScript; C++ replays and submits it in a
single crossing. **The op stream already exists** behind `TN_WEBGPU_BATCHED_PASS` — but only for the
render-pass encoder subset, and it is default OFF. It must be extended to **every per-frame
command**, `queue.writeBuffer` included (428 calls/frame, the single highest-frequency crossing).

Removes: per-crossing dispatch in `libmystral`, the API scaffolding half of the V8 machinery
(`LookupIterator`/`Object::Get`, `GlobalHandles::Create`, `Isolate`/`Context` re-entry,
`Value::IsExternal`), and the `bridgeOverheadNs` marshalling term.

### Change 2 — wrapper objects get fixed shapes

Every WebGPU wrapper is currently a property bag assembled from C++ with `Reflect.set`, read back by
name through `Object::Get`, with a `v8::Persistent` per crossed value. Replace with `ObjectTemplate`
+ internal fields, and stop wrapping every crossed value in a Persistent.

Removes: the megamorphic stub cache and name-dictionary lookups (measured at **3.9 ms/frame** on
device) that three.js pays *because we hand it new object shapes every frame, and its inline caches
go megamorphic*, plus most of the 4.3 ms of scudo churn.

### Why neither works alone — and this is the whole point

Change 1 alone leaves every still-crossing object dynamically shaped, so the inline-cache pollution
survives. Change 2 alone leaves 5,713 crossings paying full scaffolding. **Both have already been
tried in partial form and both measured ~zero**, which is exactly what this model predicts.

## The arithmetic

```
 10.1 ms  JavaScript (unchanged — this is real three.js work)
  2.3 ms  Mali driver (unchanged)
  2.0 ms  batched submit from C++
  1.0 ms  residual allocation
-------
 15.4 ms  =>  65 fps          target: <= 16.67 ms / 60 fps

removed: 22.3 ms of 37.7 (59%)
```

**The margin is thin — 1.3 ms.** Treat 60 fps as achievable, not comfortable. If the residual terms
come in worse than modelled, the next lever is the game's own draw-call count, not more seam work.

Sanity anchor: Chrome runs this same scene at **59.99 fps on this same phone** with the same
three.js. The JS term is therefore not the problem; the seam around it is.

## The test this model passes: it retro-predicts all five failures

A diagnosis that cannot explain why the previous attempts failed is not a diagnosis. This one
explains every single one, quantitatively.

| Lever | What it did | Model predicts | Measured |
| --- | --- | --- | --- |
| **F12** batched pass | removed 1,900 of 5,713 crossings (33%), encoder subset only; shapes and Persistents untouched | ~33% of the dispatch term only ≈ 1–2 ms of 37.7 ≈ **4%** | **+5%** |
| **F14** / PRD-224 | binding table installed once per class — but only ~6 calls/frame use those classes | ~0.3 ms of a 24 ms frame | **0.02 ms** |
| **Lever A** wrapper pooling | pooled the wrapper; kept per-call crossings and dynamic shapes | ~0 | **flat, removed** |
| **A1** Dawn swap | changed the backend implementation; backend is 8.5% | ~0 | **flat** |
| **A2** null backend | removed the backend entirely | 8.5% | **1.95 ms of 11.21 = 17%** ✓ |

F12 is the strongest confirmation: a **partial** version of Change 1, on a **third** of the
crossings, with Change 2 absent, delivered +5% — within the model's prediction. That is the
signature of a correct diagnosis of a compound problem, not of a dead end.

## How to kill this quickly if it is wrong

Do these in order. Each is cheap and each can falsify the model before the expensive work starts.

**P1 — one night, desktop.** Extend the op stream to cover all per-frame commands including
`queue.writeBuffer`, run the profiled lane.
*Prediction:* `bridgeNs` collapses **9.15 → under 1.5 ms**, and `work` falls **23.9 → ≤ 17 ms**.
*Falsified if:* `bridgeNs` collapses but `work` does not — that would mean the seam's cost is not
where the model puts it, and Change 2's premise dies with it.

**P2 — one device capture.** With Change 2 in, take a fresh symbolized simpleperf.
*Prediction:* megamorphic stub cache + name dictionary falls from **10.5% to under 3%** of
render-thread self time.
*Falsified if:* it does not move — three.js's ICs are megamorphic for a reason other than our
wrapper shapes.

**P3 — the acceptance run.** Both changes in, cool discharging Pixel 8, live windows only, three
captures, cross-checked against `dumpsys SurfaceFlinger --latency`.
*Prediction:* **≥ 60 fps.**

**Pre-registration, per PRD-226's binding rule:** Change 1 predicts **13.4 ms/frame** on device and
Change 2 predicts **8.9 ms/frame**; both clear the 2 ms threshold by a wide margin, and both are
stated here *before* implementation.

## Caveats that must ride along

1. **The device model is built on F13's percentages**, taken from one symbolized profile on a
   Bayview build that is not today's. The desktop terms are measured fresh; the device split is
   inherited. P1 tests it on desktop before anyone spends a device night.
2. **The desktop A0/A2/A5 absolutes were taken on `:0`**, which a sibling lane voided in favour of
   Xvfb at `d42d1a3d`. The 29.7% bridge share comes from the profiled Xvfb lane and is unaffected;
   the 11.21/9.26/4.05 ms figures should be re-taken on Xvfb before being quoted.
3. **`bridgeNs` is inclusive** — it brackets the whole top-level native callback including the
   backend call — and `bridgeOverheadNs` is prologue + epilogue only. The in-handler term is derived
   by subtraction, not measured directly.
4. **1.3 ms of margin.** This reaches 60 fps; it does not reach it comfortably.
