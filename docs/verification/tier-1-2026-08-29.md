**`pnpm native:build` would not have fixed it.** The dependency is already downloaded; it is
`SDL3-3.2.30.aar`, and `androidDependencyBlocker` at

This is a known shape in this repository, already diagnosed once and fixed everywhere except here.
`packages/runtime-native/android/app/build.gradle.kts:34` carries the note in its own words: the
version "was written out in four separate places, and the bump to 3.2.30 — for 16 KB page alignment

Gradle input-file error three layers away from the pin it disagreed with." Gradle was then changed
to find the AAR by name (`sdl3AarIn`). The conformance runner is the fifth place, still naming the
old archive by hand.

**The Android row is therefore blocked, not failed, and it is blocked by the framework rather than
by the platform.** The engine fix — mirror Gradle's name-find in `androidDependencyBlocker`, with
the red-green test in `packages/runtime-native/tests/conformance-runner.test.mjs`, whose three
fixtures also hardcode `SDL3-3.2.8.aar` — belongs to the runtime-native lane and is not made here.
Until it lands, **no Android claim is available from this repository at all**, on emulator or
hardware, because the lane cannot reach a device.

## The Android exit divergence is closed

**Updated 2026-08-30.** When this ledger was first written the Exit cell for Android read `2` and
the Android process had exited `1`. Both were true, because the runner carried the rule in two
places:

- `reportExitCode` said `fail > 0` → `1`, `blocked > 0` → `2`, and knew nothing else.
- The Android execution path then overrode the process exit to `1` whenever the
  `androidMultitouch` supplemental failed — which it did, on the webp build error above.

`scripts/check-parity-ledger.ts` imports `reportExitCode` precisely so a ledger cannot invent an
exit code, so it could only ever see the rule and not the override. This file recorded the observed
`1` in prose and left the rule's `2` in the cell, and noted that folding the override into
`reportExitCode` would close the gap.

**That fold has since landed.** `run-conformance.mjs:2129` is now part of `reportExitCode` itself:

```js
if (report.summary.fail > 0) return 1;
if (report.supplemental?.androidMultitouch?.status === "fail") return 1;
if (report.summary.blocked > 0) return 2;
```

So the rule and the process exit now agree on `1` for this report, and the Exit cell above is `1`
— the value the runner actually emitted and the value the checker recomputes from
`parity-2026-08-29-android/report.json`. `pnpm parity:ledger` passes on this file. No measurement
changed: the summary is still `0 pass / 0 fail / 74 blocked` and the lane still executed nothing.
