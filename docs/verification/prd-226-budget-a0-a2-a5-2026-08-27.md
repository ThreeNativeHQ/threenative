# PRD-226 — the native frame budget, measured: JavaScript and the bridge own it

**Date:** 2026-08-27, HEAD `a3c27b34` + the ablation commits. Desktop lane, display `:0`,
`SDL_VIDEODRIVER=x11`, NVIDIA RTX 2080. **This is the Phase 1 gate the PRD said no optimisation may
precede.** Three arms, one session, one meter (`TN_FRAME_BUDGET.phases.render.p50`).

## The budget

| Arm | What it is | `render.p50` |
| --- | --- | ---: |
| **A0** control | native, HEAD, unmodified | **11.21 ms** |
| **A2** null backend | native with the hot backend command entry points no-oped | **9.26 ms** |
| **A5** Chrome | the same scene in Chrome, same machine, same meter | **4.05 ms** |

```
native backend command recording + the GPU work it causes   T0 − A2  =  1.95 ms   (17%)
native JavaScript + bridge                                       A2  =  9.26 ms   (83%)
Chrome, all of it                                                A5  =  4.05 ms
```

**Native's JavaScript-and-bridge term alone is 2.3× Chrome's entire render phase.** The excess over
Chrome is 7.16 ms; at most 1.95 ms of it can be backend and GPU, and Chrome pays part of that too,
so **at least 5.2 ms — 73% of the excess — is on the JavaScript and bridge side.**

Five levers were spent on the 17%.

- `hostGap.p50` rose 3.0–4.3 → 5.1–6.2 ms. The host idles more once real work is removed, which is

## What this closes, and what it does not

**Closed.** The backend is not the owner, now by two independent routes: A1 (swapping in Dawn, which
*is* Chrome's backend, changes nothing — 11.85 against 11.51 ms) and A2 (removing the backend
entirely buys 1.95 ms of 11.21). No further work on backend choice, wgpu-native upstream, or
command-recording cost is justified by this evidence.

**Open, and now the only question.** The 9.26 ms splits into *JavaScript executing three.js* and
*the bridge* — and this budget does not separate them. That is **arm A3 (null bridge)**, and it
decides which architectural option PRD-226 Phase 5 takes:

- if the term is mostly **JavaScript**, the lever is V8's build configuration, not the bindings;
- if it is mostly **bridge**, the lever is moving three.js's encode off the per-call seam.

**A4 (no-JS op-stream replay) is still owed** as the independent second route to backend+GPU. With
only A0/A2/A5 the sum gate is satisfied by construction rather than by cross-check — A2 and T0−A2
add to T0 because that is how they were defined. A4 is what makes 1.95 ms a measurement instead of a
definition.

## Disclosure ledger

- **Bundle mismatch between the native and Chrome arms.** Native ran `.threenative/build/game.js`
  (rebuilt 2026-08-27 00:52 by another lane); Chrome ran the `dist/` web build from 2026-08-26 13:41.
  `src/` is byte-unchanged between them (newest source file 13:41:04), so the game code is the same;
  the installed framework package versions are not. The matching `update.mean` on both sides is the
  evidence that the scene weight did not move, but a same-moment rebuild of both is owed before the
  4.05 ms figure is treated as final.
- **A5 is one session, not six interleaved runs.** Its windows 2–7 span 3.6–4.3 ms, tighter than the
  native arms' spread, but it has not been repeated.
- Machine load 3.6–5.2 across the native block, from an unrelated long-running server. It is steady
  rather than spiky and both arms were interleaved through it, which is the mitigation; the A0
  validity check above is what actually establishes the lane was good.
- One 404 for a missing resource appeared in Chrome's console. It did not stop the scene rendering
  or the meter reporting; it is not attributed and not investigated here.
- Nothing in this record is a device measurement. The Pixel 8 stands at **20.44 fps** against a
  30 fps floor, measured this morning.
