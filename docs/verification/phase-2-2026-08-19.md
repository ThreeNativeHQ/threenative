## Gate under test

Phase 2 exits only when all three conditions hold:

1. A user-visible capability ships that vanilla Three.js has no answer for, proven by the
   outcome a consumer observes rather than by framework artifacts.
2. The instrument does not hand the control arm the capability under test. The paired benchmark
   is not used here because its design gives both arms the `playtest` bridge.
3. The same subject and Phase 3 execution include a negative control observed red; missing capability fails,
   never skips or passes vacuously.

The litmus was applied before adoption. The positive composition was already shipped and measured
by PRD-081 on 2026-08-12, so reproducing it is consumer evidence but not new post-adoption
shipping evidence. It cannot close this gate by itself.

## Subject and result

Subject: the generated `platformer` template and its
`playtests/physics.playtest.json` scenario. The scenario waits 240 fixed ticks and evaluates a
`settled` assertion for the named `crate`; the generated project contains no hand-rolled
capability or observation bridge.

| Criterion | Observation | Result |
| --- | --- | --- |
| Consumer outcome | `settled` evaluated and passed in the generated platformer | observed |
| Instrument boundary | The positive run used the scaffolded framework, while the control removed `rapier()` instead of receiving the physics capability | observed, but not a vanilla-arm comparison |
| Same-subject negative control | The same scenario on the mutated scaffold failed with `TN_PLAYTEST_CAPABILITY_MISSING: runtime.physics` | observed red |
| New capability after adoption | The composition was already shipped in PRD-081 before the 2026-08-19 decision | **not met** |
| Literal core boundary | `packages/core/src` already contains generic `runtime.rapier` metadata and `ctx.physics` references | **not met as written**; no new physics dependency was added |

The gate is red because the execution reproduced an existing capability rather than shipping a
new post-adoption capability, and because the control is a framework-plugin deletion control,
not a vanilla implementation proving exclusivity. This is a valid Phase 3 result; it does not
invalidate the consumer proof and does not claim that vanilla beat or lost any benchmark column.
