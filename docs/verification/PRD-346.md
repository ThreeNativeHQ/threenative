## Phase 1 — the config generator gets a gate, and the last two hand-typed lists are derived

### A correction to the PRD, found before any code was written

PRD-346 §2 says the `pnpm sync:mcp --check` generator has no gate: *"`grep -rn "sync:mcp"
scripts/ci-fast.sh .github/workflows packages/*/__tests__` finds only an unrelated path listing."*

That grep was looking for the pnpm alias. `pnpm budgets` invokes the script by path, as its last
step:

```
"budgets": "... && tsx scripts/check-template-quality.ts && tsx scripts/sync-mcp-configs.ts --check"
```

and `scripts/ci-fast.sh` runs `pnpm budgets`, as does CI's `budgets` job. **The gate already
existed.** No `ci-fast.sh` edit was made. The real gap was that a local `pnpm test` did not catch a
hand-edited template config, and that is what this phase closes.

## Phase 2 — the fourth server, on a machine with no Blender

### The proof subject was the hard case

`scaffold-mcp.spec.ts` launches the real shim over real stdio, with `PATH` scrubbed to one empty
directory and `HOME` to another, and reads a real `tools/list` and `tools/call`:

```
✓ scaffolded blender MCP > should list blender tools with no Blender installed 66ms
```

with `blender_status` returning `available: false`, `cause: "blender-missing"`, install guidance for
all three platforms, and no dead server.

Two earlier drafts of that gate were **weak and were replaced**, both caught by their own negative
controls:

1. The first read the committed template `.mcp.json` for a hardcoded `"threenative-blender"` key.
   Removing the entry from `MCP_SERVERS` left it green, because the template bytes still had it.
   It now looks the server up in the table.
2. The second edited `src/index.ts` without rebuilding. `launchMcpServer` resolves the package's
   `bin`, which is `dist/index.js`, so the control was measuring stale bytes.

### The defect this phase found: a published package cannot name an unpublished one

Declaring `threenative-blender-mcp` as a dependency of `@threenative/core` — the obvious reading of
the PRD — breaks every install:

```
ERR_PNPM_FETCH_404 GET https://registry.npmjs.org/threenative-blender-mcp: Not Found - 404
This error happened while installing the dependencies of @threenative/core@0.3.0
threenative-blender-mcp is not in the npm registry, or you have no permission to fetch it.
```

caught by `verify-golden-path.spec.ts`'s mutated-CLI control. Core now carries the built server at
`mcp/blender-server.mjs` and devDepends on the workspace package — the mechanism
`mcp/engine-server.mjs` has used all along, and the reason `threenative-engine-mcp` was already a
devDependency. `blender_status` therefore works offline, with no npx and no network.

**The same defect recurred in `@threenative/assets` in Phase 5** and is recorded there.

### Two corrections to the PRD

- **No `@modelcontextprotocol/sdk`.** The PRD's key-decision line says the SDK matches
  `packages/engine-mcp`. That package hand-writes stdio JSON-RPC and uses no SDK. Following it
  exactly leaves `threenative-blender-mcp` with **zero runtime dependencies**, which is what lets
  `@threenative/assets` inline the conversion bridge without inheriting an MCP transport.
- **`scripts/ci-fast.sh` needed no edit** (see Phase 1).

### Three defects found and fixed here

1. **The health report could not read its own input.** Classifying `.fbx` as a model pointed
   `runHealthReport` at the source bytes, and it fails the whole compile on anything unreadable as
   glTF:

   ```
   TN_ASSETS_MODEL_UNREADABLE: could not parse 'character.fbx' for the health report:
   Unexpected token 'K', "Kaydara FB"... is not valid JSON
   ```

   The report still measures the source for everything the runtime can load — that is deliberate.
   For an imported source the converted GLB is its earliest readable form, and that is what is
   measured, on the cache-hit path too.

2. **`resolveBlender` half-honoured its environment.** It read the caller's `PATH` and the real
   `homedir()`, so a scrubbed environment still resolved `~/.local/bin/blender` and reported
   Blender present. Found by a gate that passed when it should not have.

3. **`importedFrom` never reached the manifest.** `IAssetManifestEntry` narrows the fields a pass
   may declare; the new one had to be added there and to `sameEntry`, or a rebuild rewrites an
   entry it should reuse.

### The fixtures, and the deviation

`flag_A_blue.fbx` is a genuine untouched CC0 download (KayKit Platformer, via
`asset_download_bundle_entry`, sha256 `7f324fd4…0055a639`, 32,876 bytes) — a real third-party FBX
writer's output, external texture reference included.

`character.fbx` is the rigged proof subject, and **it was authored here** rather than downloaded.
PRD-346 asks for a real Fab or Sketchfab character. Four sources were tried:

| Source | Result |
| --- | --- |
| Sketchfab | `sketchfab_get_downloads` → `SKETCHFAB_AUTH_REQUIRED`; needs `SKETCHFAB_API_TOKEN`. Source archives 0.2–390 MB. |
| Fab | Free listings are added to an Epic library, not downloaded; `fab_download_free_asset` covers only directly available files. |
| Quaternius Universal Animation Library | itch.io returned HTTP 429 to every `asset_list_bundle_animations` and `asset_list_bundle_entries` call. |
| KayKit Platformer FREE | Reachable, and used — but props only. No armature, no actions. |

The full log and what the deviation costs are in
`packages/assets/__tests__/fixtures/blender/README.md`. `make-character.py` is committed and
GPL-headed, so the fixture is reviewable line by line rather than an opaque binary.

## Phase 5 — discoverable

### The tool snapshot is not a self-comparison

`packages/create-threenative/blender-mcp-tools.json` was captured by
`scripts/capture-blender-mcp-tools.ts`, which packs the workspace, `npm install`s **that tarball**
into a clean directory, and reads a live `tools/list` and `blender_status` off the installed
server. It is never read from `src/`. (The PRD asks for a published tarball; the package has never
been published, so this is the nearest available artifact — the same one CI scaffolds from.)

```
tools:  blender_convert, blender_inspect, blender_recipes, blender_run_python, blender_status
status: available, detail, install, installCommand, minimumVersion, path, version
```

### The Phase-2 defect recurred, in `@threenative/assets`

```
ERR_PNPM_FETCH_404 GET https://registry.npmjs.org/threenative-blender-mcp: Not Found - 404
This error happened while installing the dependencies of @threenative/assets@0.3.0
```

`pnpm dlx --package <assets tarball>` resolves that package's own dependencies from the registry,
so the scaffold died before the CLI ran. Fixed the same way core was: devDependency, the bridge
inlined by tsup, and the GPL scripts copied into `dist/blender-gpl/` by
`scripts/bundle-blender-gpl.mjs`. `package-dist.spec.ts` now gates all three properties, so the
class cannot return silently.

### Three more gates found this work, and two gaps this work found in the gates

`pnpm exec vitest run` caught all three before they could ship:

1. **`package-externals.spec.ts`** — *"a package that imports a module it only declares in
   `devDependencies` publishes a private copy of it"*. That is exactly what both consumers now do,
   deliberately, because the alternative is an uninstallable package. It is allowed by name, with
   the reason and the condition for deleting the row, plus a second test that the allowance stays
   matched to what is actually imported.
2. **`package-list-drift.spec.ts`** — a *comment* in `bundle-blender-gpl.mjs` naming
   `@threenative/core` invented a build-order edge (`@threenative/core builds after
   @threenative/assets`), because the scan reads build scripts as text. Reworded.
3. **`temp-dir-guard.spec.ts`** — five new `mkdtemp` callers. The three specs now use the
   registering `makeTempDir`; the two production callers are allowlisted, and
   `capture-blender-mcp-tools.ts` was given the `finally` cleanup its allowlist row claims.

And two of PRD-346's own revert checks turned out to describe gates that **did not exist**. Both
controls passed when they should have failed, and both gates were written:

- Removing the blender row from `verify-golden-path.ts`'s `MCP_SURFACES` left every test green.
  `probes every server the scaffold actually wires` now derives the required set from `MCP_SERVERS`.
- Leaving `AGENT-INTERFACE.md` claiming three servers left every test green.
  `should name every MCP server the scaffold wires in the agent interface` now derives it too.

## §7 — what was NOT executed

Stated so nothing here is read as a claim it does not support.

- **No playtest scenario drives the converted character in a running game.** PRD-346's first
  acceptance criterion asks for one; the compile-to-manifest path is proved by
  `blender-import.spec.ts`, and the GLB is read through the runtime's own reader, but no browser
  loaded it. **Unverified.**
- **No human looked at a decimated or AO-baked mesh.** The Phase 3 and Phase 4 manual checkpoints
  are outstanding; the numeric assertions above are what exists. **Unverified.**
- **macOS and Windows install guidance is shipped but not exercised.** Only Linux was run, which
  is what PRD-346 §8 already scopes.
- **`pnpm test:templates`, `pnpm test:playtest`, `pnpm verify:golden-path` (the full matrix) and
  the CI native lanes were not run locally.** The golden path's mutation control was, twice, and
  is recorded above.
