# PRD-050 verification — native build parity

**Result:** PASS on Linux desktop and the Android x86_64 emulator, 2026-08-09.
iOS is packaging-and-contract only. Windows, macOS, arm64 hardware, HUD rendering, audio
parity and frame-rate parity are not claimed.

## What changed

- Native builds resolve `threenative.nativeEntry` (default `src/game.ts`), require its
  default export, and generate the import/start entry. Source truncation and start-string
  matching are deleted.
- The generated game is closure-scoped before classic-script execution, preventing bundled
  library locals such as Three.js `AudioContext` from replacing host globals.
- Desktop uses normal package export conditions. Android and iOS use
  `threenative-native`; only mobile rejects WASM. Every native target rejects a portable
  graph containing web UI.
- Desktop, Android and iOS stage `public/` at web-root paths. Android fetches packaged
  files from `asset://game/`; iOS launches with the staged `game/` directory as its working
  directory.
- The proving subject is the scaffolded starter with Rapier, a PNG texture and a GLB. Its
  React entry remains web-only; PRD-051 owns native HUD rendering.

## Open boundaries

- iOS staging and SHA-256 reports passed locally, but no Apple runtime executed.
- Windows and macOS starter jobs are not claimed; the new durable starter lane is Linux.
- The starter's OGG pickup playback was not exercised. Linux logged the existing
  unsupported decode path, so this PRD makes no audio-parity claim.
- React HUD rendering remains PRD-051. Navigation remains PRD-052.
