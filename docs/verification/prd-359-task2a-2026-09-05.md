# PRD-359 Task 2a — datagram surface — 2026-09-05

Replaces the invented `maxDatagramSize: 1200` with the capacity the connection actually
negotiated, makes the JavaScript write honour the native send status instead of discarding it, and
bounds the **native** datagram queues — send and receive — with a local-drop count that means
backlog and nothing else.

Layer: native shim and its polyfill. No second transport, no reliability layer, no stream or DNS
work — those belong to rows 2b and 2c. This row is the datagram surface, not networking: the
JavaScript receive path still has no back-pressure, which is row 2b's streams work and is listed
among the open items at the end.

## What was wrong

`webtransport-polyfill.js` published `maxDatagramSize: 1200` — a constant with no relationship to
the connection — and its `write()` called `__wtSendDatagram(...)` as a statement, discarding the
return value. Every failure mode was therefore silent and indistinguishable: a datagram sent on a
closed session, a datagram too large for the path, and a datagram dropped from a local queue all
resolved the write. The red run below shows a 65-byte datagram accepted and echoed on a connection
whose real limit is 1321.

## Native design

`quiche_conn_dgram_max_writable_len` is the QUIC datagram frame budget. An HTTP/3 datagram spends
the front of that frame on the quarter-stream-id varint for the CONNECT stream; the rest is the
payload a game may send. The subtraction is a pure function so it can be unit-tested without a
connection:

| Symbol | Definition | Callers |
| --- | --- | --- |
| `varintLength` | `webtransport.cpp:171` | `datagramPayloadCapacity` |
| `datagramPayloadCapacity` | `webtransport.cpp:188` | `refreshDatagramCapacity` (`:1071`) |
| `clampDatagramCapacity` | `webtransport.cpp:201` | `refreshDatagramCapacity` (`:1072`) |
| `classifyDatagramSend` | `webtransport.cpp:235` | `sendDatagram` (`:1116`) |
| `admitDatagram` | `webtransport.cpp:245` | `sendDatagram` (`:1123`) |
| `drainDatagramReads` | `webtransport.cpp:263` | `readDatagramsBudgeted` (`:288`) |
| `readDatagramsBudgeted` | `webtransport.cpp:285` | `readDatagrams` (`:649`) |
| `drainDatagramQueue` | `webtransport.cpp:307` | `pumpDatagramSends` (`:1096`) |
| `refreshDatagramCapacity` | `webtransport.cpp:1069` | `processEvents` ready (`:1263`), steady state (`:1294`) |
| `failSession` | `webtransport.cpp:1085` | invalid clamp (`:1264`, `:1296`), hard send error (`:1108`) |
| `pumpDatagramSends` | `webtransport.cpp:1094` | `sendDatagram` (`:1126`), `processEvents` (`:1305`) |
| `readDatagrams` | `webtransport.cpp:646` | `pumpSocket` (`:532`) |

`datagramPayloadCapacity` returns 0 rather than a guess whenever the input cannot support a
datagram: quiche answering `Done` (negative), a zero writable length, no CONNECT stream yet
(`connectStreamId < 0`), or framing that consumes the whole frame. Zero means "refuse the write",
which is what the polyfill does before `ready` arrives.

`MYSTRAL_WEBTRANSPORT_MAX_DATAGRAM` (`webtransport.cpp:105`) only ever **lowers** the negotiated
value — it exists so a test can pin a small limit on a real connection, and it cannot be used to
claim capacity the path does not have. **Unset means no clamp. An explicit value the runtime cannot
use fails the session** (`webtransport.cpp:201`): keeping the negotiated number while whoever set
the variable believes a limit is in force is the same silent substitution the hardcoded 1200 was.
`strtoll` alone was not enough — it skips leading whitespace and accepts a leading `+`, so `" 64"`
parsed clean; the first character is now checked directly (`webtransport.cpp:207-211`).

Capacity reaches JavaScript twice: as the `code` argument of `ready`, and again through the new
`EventType::DatagramCapacity` → `'datagramCapacity'` event (`webtransport.cpp:242`, `:749`, `:763`)
whenever the path changes it. The polyfill assigns both to the same live object
(`webtransport-polyfill.js:202`, `:207`), and `makeDatagramWritable` reads `datagrams.maxDatagramSize`
at write time rather than capturing it (`:74`, `:82`), so a capacity change takes effect on the
next write without rebuilding the stream.

### Queues and the drop count

Outgoing: `Session::outgoingDatagrams` (`webtransport.cpp:427`), bounded at
`kDatagramQueueLimit = 256` (`:110`) by `admitDatagram`, which discards the oldest waiting datagram
to admit the new one and returns how many it discarded — the shape PROTOCOL.md specifies. The
count lands in `Session::droppedDatagrams` (`:428`, incremented only at `:1124`).

Incoming: the reader's budget belongs to **the whole poll tick**, carried on
`Session::datagramReadsThisTick` (`webtransport.cpp:434`) and reset in exactly one place — the top
of `processEvents`' pass over a session (`:1236`). This matters because `pumpSocket` calls
`readDatagrams` once per inbound UDP packet (`:532`), inside its own `while` loop; the first
version of this change put the budget inside `readDatagrams`, where it restarted on every packet
and therefore bounded nothing. `pumpSocket` has one caller (`:1239`) and `readDatagrams` has one
caller (`:532`), so the reset covers every path into the reader. Nothing is discarded on receive —
the remainder waits in quiche's own receive queue for the next tick.

The drop counter is **local backlog, never network packet loss**. The polyfill comment says so at
`webtransport-polyfill.js:97-100`, and the write resolves on a drop exactly as it does on a clean
accept, because unreliable delivery discarding a stale local datagram is that transport doing its
job, not an error the game should handle.

### Statuses, and why a hard error is not a drop

`kDatagramAccepted 0` / `kDatagramInvalidSession -1` / `kDatagramTooLarge -2` / `kDatagramDropped -3`
/ `kDatagramSendFailed -4` (`webtransport.cpp:115-122`), mirrored in `webtransport-polyfill.js:26-30`
with a comment naming the C++ file as the source. `classifyDatagramSend` checks session usability
before size, so a write to a closed session reports the closed session even when it is also
oversized — the actionable fault, not the incidental one.

`QUICHE_ERR_DONE` alone means "no room right now": `drainDatagramQueue` stops and leaves the queue
intact for the next frame, exactly as `pumpStream` does for a congestion-blocked stream write. Any
**other** negative is a transport failure. It does not touch `droppedDatagrams`, it fails the
session through the same `EventType::Error` channel a handshake failure uses (`failSession`,
`webtransport.cpp:1085`), and `sendDatagram` answers `kDatagramSendFailed` rather than reporting
the write as sent (`:1130`). `sendDatagram` also now refuses a session already marked failed
(`:1114`), so the next write reports a closed session instead of queueing into a dead connection.

## Divergence from the W3C specification, on purpose

W3C WebTransport discards an oversized datagram **silently** and resolves the write. This runtime
throws a `WebTransportError` instead (`webtransport-polyfill.js:83-87`). Two reasons, recorded here
rather than left for a reader to discover: PROTOCOL.md requires the write to be validated against
the real negotiated limit, and the repository's fail-closed rule says a malformed input throws. A
game that writes past the limit has a bug, and silence hides it until the packets vanish in the
field. The check is in the polyfill and not only in native so the error names the limit the game
can read from `datagrams.maxDatagramSize`.

The fallback at `webtransport-polyfill.js:101-103` throws on any status the polyfill does not
recognise, so a future native status cannot be read as success by omission.

## Review round — five defects, and what each one actually was

Reviewed after the green above. Two of the five were real defects in the shipped repair, one was a
wrong claim in this document, one was a fail-open configuration path, and one was a coverage gap
that turned out not to be a defect. Each is separated below, because reporting a coverage gap as a
bug found-and-fixed would inflate the result.

### 1. The receive budget bounded nothing — real defect

**Claimed here originally:** "the `readDatagrams` loop … is now bounded to `kDatagramQueueLimit`
admissions per pump". **That claim was wrong and has been corrected above.** The budget was a local
`for` counter inside `readDatagrams`, and `pumpSocket` calls `readDatagrams` once per inbound UDP
packet inside its own `while` loop (`webtransport.cpp:532`). A burst of *n* packets therefore
admitted up to *n* × 256 events into `g_events` in a single `processEvents` pass: not bounded per
tick, only per packet.

Repair: the counter moved to `Session::datagramReadsThisTick` (`:434`), spent through the
production helper `readDatagramsBudgeted` (`:285`) which takes it by reference, and reset in
exactly one place — the top of `processEvents`' pass over a session (`:1236`).

Proof (`webtransport_wire_test.cpp`, the "bounded receive across a whole poll tick" block): ten
calls to `readDatagramsBudgeted` against a peer that always has another datagram — the shape
`pumpSocket` produces when ten packets arrive in one tick — admit `kDatagramQueueLimit` reads and
emit `kDatagramQueueLimit` events, not ten times that; the socket stops being read once the budget
is spent; a fresh tick starts from a full budget; a foreign flow id costs budget but emits nothing;
`Done` ends the drain at once.

Scope of that proof, precisely: it drives the production helper that `readDatagrams` delegates to,
so the *carry* semantics are executed code. That the counter lives on the session and resets only
in `processEvents` is verified by reading the call graph — `pumpSocket` has one caller (`:1239`)
and `readDatagrams` has one caller (`:532`) — not by a test that counts events out of a real burst.

### 2. Every hard quiche error was filed as a legitimate drop — real defect

`pumpDatagramSends` treated any negative that was not `QUICHE_ERR_DONE` as a local drop:
`droppedDatagrams += 1`, a stderr line, and on to the next frame. `sendDatagram` then returned
`kDatagramAccepted`, so a transport that refused the frame outright looked to the game exactly like
unreliable delivery working normally.

Repair: `drainDatagramQueue` (`:307`) separates the two. `Done` breaks and leaves the queue intact;
any other negative discards that frame, stops the drain, and is returned as `hardErrors` /
`lastError`. `pumpDatagramSends` (`:1094`) then calls `failSession` and sets `datagramSendFailed`,
leaving `droppedDatagrams` untouched; `sendDatagram` returns the new `kDatagramSendFailed` (−4), and
the polyfill throws on it (`webtransport-polyfill.js:97-101`).

Proof: the wire test's "outgoing queue pressure" block drives `drainDatagramQueue` — the function
`pumpDatagramSends` actually calls — with an injected sender returning −7, and asserts
`hardErrors == 1`, `lastError == -7`, `sent == 0`, the drop counter unchanged, and that exactly the
failing frame was discarded. The surface test adds a `send-failed` arm proving the JS write rejects
on −4 while the `queue-drop` arm on −3 still resolves, in the same run.

### 3. An unusable explicit clamp was logged and ignored — fail-open configuration

`clampDatagramCapacity` printed a warning and returned the negotiated capacity, so
`MYSTRAL_WEBTRANSPORT_MAX_DATAGRAM=abc` produced a working session at the full limit while whoever
set the variable believed a smaller one was in force.

**Behavioural red, on the then-current binary** (`/tmp/prd359-2b-red-live.log`, exit 1):

```
 × fails the session on an unusable explicit datagram clamp 516ms
AssertionError: clamp value "abc": expected '…' to contain 'PASS: bad clamp refused'
[log] FAIL: ready:1321
```

`ready:1321` is the session coming up at the full negotiated capacity with the clamp discarded.

Repair: the function now returns `bool` with an out-parameter and a message (`:201`), unset stays
"no clamp", and `refreshDatagramCapacity` returns `CapacityUpdate::Invalid` (`:1064`) which
`processEvents` turns into `failSession` on both the ready path (`:1264`) and the steady-state path
(`:1296`). It never throws; the session fails through the existing error channel and JS sees a
rejected `ready` naming the variable.

Proof: the live test loops `"abc"`, `"0"`, `"-5"` and `""` and requires each to reject `ready` with
a message containing `MYSTRAL_WEBTRANSPORT_MAX_DATAGRAM`. The wire test adds `" 64"`, `"+"` and an
overflow value. `" 64"` is worth naming: it **passed** the first repair, because `strtoll` skips
leading whitespace, so the value parsed clean as 64. The first character is now checked directly.

### 4. Native limit enforcement past the JS guard — coverage gap, not a defect

The two live oversize tests both stopped at the polyfill's own size check, so on their own they
proved the JavaScript guard and said nothing about the native limit under it. A direct test was
added: `__wtSendDatagram(wt._state.id, …)` — `_state.id` is the native session id the polyfill
stores when it opens a session — asserting `limit` returns 0, `limit + 1` and `limit + 4096` return
−2, and an unknown session id returns −1 rather than a size error.

**This test passed on the unmodified binary**, in the same run that produced defect 3's red
(14 passed alongside the 1 failure). The native side was already enforcing the limit; what was
missing was the test. Reported as a gap closed, not a bug fixed.

### 5. Queue pressure and counter behaviour — now proven at a labelled seam

The previous version of this document recorded that nothing filled the 256-deep queue. It now does,
deterministically: 300 admissions into a 256-deep queue drop exactly 44, the queue never exceeds its
bound, and the survivor at the front is the 45th datagram. The drain is then run three ways against
the production helper — `Done` (nothing sent, nothing failed, queue intact for retry), a hard error
(counted once, drop counter unchanged, only the failing frame discarded), and a clear path (drains
completely, every byte reaching the sender).

**Labelled honestly: this is a seam proof, not a network result.** The sender is injected because
loopback will not refuse a datagram on demand. What is proven is the drain's contract and the
queue's arithmetic; what is not proven is that a real congested path produces these calls in this
order. `quiche_conn_dgram_send`'s own 1024-deep queue plus this 256-deep wrapper are both finite, so
the combined bound is finite without forcing both to fill.

## What is still not proven, stated plainly

1. **Task 2a is the datagram surface, not networking.** Streams, DNS and session lifecycle beyond
   what these five files touch are rows 2b and 2c and are not addressed here.
2. **No receive-side bound in JavaScript.** The runtime's `streams-polyfill.js` never calls `pull`
   and reports `desiredSize` as 1 always, so back-pressure on `datagrams.readable` cannot be
   expressed without editing a sixth file. That is row 2b's streams work — explicitly pending, not
   attempted. The native receive path is bounded per tick as of defect 1's repair; **the two queues
   are not both bounded**, and this row does not claim they are.
3. **No burst test counts events out of a real connection.** Defect 1's proof is at the helper, as
   scoped above.
4. **`closed` still resolves on a session that failed after `ready`.** The polyfill resolves
   `closed` whenever the session had reached ready, so a datagram hard failure rejects the *write*
   (the actionable signal) but does not reject `closed`. This is pre-existing behaviour for every
   post-ready failure, not something this row introduced, and changing it would touch the shared
   session lifecycle rather than the datagram surface. Recorded, not fixed.
5. **`getStats()` was not added.** Its W3C dictionary member names could not be verified from a
   pinned source here, and inventing them would put a wrong shape in a public API. `droppedDatagrams`
   is counted natively and ready to be exposed once the names are confirmed.
