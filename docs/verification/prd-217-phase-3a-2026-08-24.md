# PRD-217 Phase 3A — the desktop spike, per platform

**Ran 2026-08-24, Linux only.** Windows and macOS have not been run and nothing here claims them.

Open question 1 asked whether a `wry` child web view survives contact with the real SDL/WebGPU
window. On Linux the answer is **six rows yes, one row no**, and the one that fails is the one the
whole design rests on.

## What executed

```sh
# the real desktop game, on X11
SDL_VIDEODRIVER=x11 packages/runtime-native/build/tn-linux/mystral run <bundle>.js

# the spike, attached to the window SDL already owns
cd packages/runtime-native/native/ui-overlay
cargo build --release --bin tn-ui-overlay-probe
GDK_BACKEND=x11 ./target/release/tn-ui-overlay-probe "$(xdotool search --name '^ThreeNative$')" 8
```

## Why transparency fails, exactly

`wry` 0.48's webkitgtk backend attaches by creating an X11 child of the parent:

```rust
// wry-0.48.1/src/webkitgtk/mod.rs, create_container_x11_window
let window = unsafe { (xlib.XCreateSimpleWindow)(display, parent, x, y, width, height, 0, 0, 0) };
```

`XCreateSimpleWindow` inherits the parent's visual and takes a background pixel of zero. The
parent is the SDL window at depth 24, so the child is depth 24: no alpha channel, black
background. `with_transparent(true)` does reach the page — the document background is transparent —
and then stops at the window. The probe reads the depth back rather than asking anyone to
interpret a screenshot.

**Wayland is not a second finding, it is the same file:** `new_x11` matches
`RawWindowHandle::Xlib` and returns `UnsupportedWindowHandle` for anything else. A Wayland session
must run SDL under XWayland (`SDL_VIDEODRIVER=x11`) for the attach to be possible at all, which is
what this run did.

## Evidence

- `docs/verification/prd-217/desktop-game-only.png` — the game alone: rotating cube, player cube,
  magenta marker.
- `docs/verification/prd-217/desktop-overlay-opaque.png` — with the web view attached: the HUD
  plate, a live counter, a proportional antialiased font, a stroked SVG circle and a rounded
  button all render correctly, and **the game is gone**. That capture is the failure, not the
  success.

Both captures were taken under a private Xvfb; a capture of the same run on the real display
(KWin, XWayland) is identical in the respect that matters — the game surface is not visible behind
the overlay — so this is not an artefact of running without a compositor.

## What this changes for the PRD

The PRD guessed that Linux was the one real desktop risk. It is, and the risk is narrower and more
tractable than "Linux needs CEF":

- Everything except transparency already works, including the whole bridge and the hit-region
  protocol, unchanged from Android. The host-independent design held.
- The failure has a named cause in one upstream call, so the first thing to try is an ARGB visual
  for the container window rather than 150–250 MB of Chromium. **That is a hypothesis, not a
  measurement** — a depth-32 child still has to blend against the parent's backing store, and this
  run did not establish that it would.
- Windows (WebView2) and macOS (WKWebView) attach through different backends that support
  transparent child web views natively. Neither was run. They are not covered by this result in
  either direction.

Open question 4 — "if a platform fails the parity bar, is CEF worth it for that platform alone?" —
now has one concrete candidate, Linux, and one cheaper thing to try first.
