# PRD-217 Phase 3A — the desktop overlay, and the transparency blocker it hit

**Ran 2026-08-24, Linux only.** Windows and macOS have not been run and nothing here claims them.

Open question 1 asked whether a `wry` child web view survives contact with the real SDL/WebGPU
window. The first answer was **six rows yes, one row no**, and the one that failed was the one the
whole design rests on. It is now fixed, and the fix is measured.

## The blocker

`wry` 0.48's webkitgtk backend attaches by creating an X11 child of the parent:

```rust
// wry-0.48.1/src/webkitgtk/mod.rs, create_container_x11_window
let window = unsafe { (xlib.XCreateSimpleWindow)(display, parent, x, y, width, height, 0, 0, 0) };
```

`XCreateSimpleWindow` inherits the parent's visual and takes a background pixel of zero. The SDL
window is 24-bit, so the container is 24-bit: **no alpha channel at all**. `with_transparent(true)`
does reach the page — the document background is transparent — and then stops at the window. The
web view paints opaque black over the game.

## The fix

`native/ui-overlay/src/argb.rs` builds the container `wry` will not: a depth-32 TrueColor window
with its own colormap and an explicit `border_pixel` (X11 refuses a differing-depth child without
both), handed to `wry` through `build_gtk`, which takes any GTK container and leaves the window to
the caller. Everything else about the attach stays `wry`'s.

## How the run reads pixels, and why it is done that way

Neither obvious method works on both lanes, and the record should say so rather than imply a
screenshot was taken:

- The game presents through Vulkan, so `XGetImage` on the **game window** comes back empty. The
  root window holds what the X server actually has on screen, so that is where the game frame is
  read from — **before** the overlay is mapped, which is what makes the blend two real layers
  rather than an illustration.
- Under a compositor a window's pixels live in a redirected offscreen pixmap, so the run reads
  `XCompositeNameWindowPixmap` first and falls back to the window.
- On **this machine's Wayland session**, XWayland does not expose WebKit's surface through X11 at
  all: the overlay reads back as `argb 0 0 0 0` on the real display while the identical code reads
  `argb 255 127 255 212` on a bare X server. So the numbers above come from the Xvfb lane, and the
  composited screen itself was never captured — `import` and `ffmpeg -f x11grab` see a 0×0 root
  under rootless XWayland, and Spectacle stopped writing files partway through the session.

## Two placements, and which one Linux needs

`Placement::Child` is an X11 child of the game window. `Placement::Overlay` is a top-level,
override-redirect ARGB window held over it. Both produce the same transparent surface — measured —
but **on X11 nothing blends alpha except a compositor, and compositors redirect top-level windows**,
so a child window's contents occlude the parent rather than blending with it however deep its
visual. `Overlay` is therefore the Linux answer, and `compositor_present()` checks the
`_NET_WM_CM_S<screen>` selection so a host can refuse by name rather than draw a black rectangle
over the game on the rare display with no compositing.

## Input, and the desktop half of criterion 2

An overlay is a window, so without help it takes every pointer event over the whole game. The
hit-region protocol maps onto X11 as an **input shape**: the same published rectangles become
`XShapeCombineRectangles(…, ShapeInput, …)`, and the display server routes a click outside them to
the game window underneath. The host forwards nothing — on Android the view hierarchy decides, here
the X server does, and the page publishes the same rects to both.

```
TN_SPIKE:{"row":"click-on-an-island-hits-the-ui","ok":true,"detail":"window under 1088,360 is 0x800004; the overlay is 0x800004"}
TN_SPIKE:{"row":"click-elsewhere-hits-the-game","ok":true,"detail":"window under 400,600 is 0x20002e; the game is 0x20002e"}
```

Asked of `XQueryPointer` after warping the pointer, so the authority answering is the one that
actually routes clicks.

**Mutation: publish no input shape** (`TN_SPIKE_NO_INPUT_SHAPE=1`).

```
TN_SPIKE:{"row":"click-elsewhere-hits-the-game","ok":false,"detail":"window under 400,600 is 0x800003; the game is 0x20002e"}
```

Every click lands on the overlay, which is the failure the protocol exists to prevent.

## The C++ host, end to end

The spike is no longer a spike on Linux: `mystral run <game>.js --ui <dir>` attaches the overlay
from the real host, over the real SDL/WebGPU window.

```
TN_UI_OVERLAY:{"attached":true}
TN_UI_HIT_REGIONS:{"count":2}
```

The second line is the whole protocol working across three languages: the page's registry measured
its two `data-tn-interactive` elements, published them over `wry`'s IPC handler, the C ABI queued
them, the runtime recognised the `tn:hit-regions` frame and kept it out of the game's bridge, and
the host applied them as the X11 input shape. The game kept rendering throughout.

Without a compositor the same command refuses by name rather than covering the game:

```
TN_UI_OVERLAY:{"attached":false,"reason":"no compositing manager is running, so nothing would blend the overlay"}
```

### One build-level defect, fixed here

SDL3's Linux tray dlopens GTK and keeps two entry points in same-named globals — `g_object_ref` and
`g_object_ref_sink`, as pointers in BSS. Statically linked, those common symbols satisfied the
overlay's own references to the real GObject functions, and `gtk_init` died calling a null pointer:

```
#0  g_object_ref ()
#1  gdk_display_manager_open_display ()
#2  gtk_init_check ()
#3  tn_ui_overlay_attach ()
```

SDL globs its tray sources with no option to decline them and `third_party/` is reconstructed by
`download-deps` rather than patched, so the two names are rewritten with `objcopy` in the one
object file that defines them, before `mystral` links. SDL's tray still works: the rename moves the
definitions and the references together. `--exclude-libs` alone was not enough and the record says
why — it keeps SDL's names out of the dynamic table and does nothing about how they resolve inside
the link, which is where the crash was.

## What is still open

- **Windows (WebView2) and macOS (WKWebView)** attach through different backends and were not run.
- **A capture of the composited screen** on a session where that is possible. The blend above is
  computed from two real layers by the same `over` operator a compositor uses; it is not a
  photograph of one.
- **The desktop packager does not stage `ui/` yet**, so `threenative build --target desktop` cannot
  produce a game that uses this. `mystral run --ui <dir>` can, and does.
- **No screenshot of the attached overlay on a composited display.** Two attempts captured the
  wrong window on a multi-monitor Wayland session and were deleted rather than kept as evidence;
  the blend above remains the visual record.
