# PRD-223 final integration — parity, regression repair, and performance

**Date:** 2026-08-26

**Host:** Linux x86_64, NVIDIA GeForce RTX 2080, Vulkan, 1280×720

## Regression found by the full parity gate

The first post-refactor desktop parity run reached 67 PASS, 1 FAIL, and the expected desktop-only
blocked multitouch row. `60-resize-render-target` terminated with `SIGBUS` before
`TN_CONFORMANCE_READY`. GDB placed the signal in `V8Engine::nativeCallback`.

The failure predates PRD-223: the PRD-start commit already stored callback argument vectors in an
outer `std::vector`. A nested native callback can grow that outer vector while its caller holds a
reference to one inner argument vector, invalidating the caller's reference. The fix changes only
the outer pool to `std::deque`; its inner vectors, reuse policy, and values are unchanged.

Observed red:

```text

desktop summary: 67 pass, 1 fail, 1 blocked
```

Observed green after the one-container fix:

```text

60-resize-render-target: 300 frames, TN_CONFORMANCE_READY, pixel verdict PASS
native contract lane passed: 22 of 22 targets
```

## PRD-start versus final steady-state performance

The control binary was built from `d5f458f0285925a8acd7cf04b8a52e8182b99403`, the parent of the
first PRD-223 commit. The final binary used the same compiler, Release mode, V8, Dawn, optional
feature flags, scene bundle, adapter, X display, 1280×720 viewport, and no-vsync mode. No other
ThreeNative renderer ran concurrently. Each reported sample excludes 180 warm-up frames.

| Workload | PRD-start p50 / p95 | Final p50 / p95 | Result |
| --- | ---: | ---: | --- |
| 256 animated objects, L2, 5 × 1,020 measured frames | 28.40 / 31.28 ms | 27.13 / 30.05 ms | final 4.5% faster p50 and 3.9% faster p95 |
| 4,096 animated objects, L2, 3 × 820 measured frames | 33.67 / 40.39 ms | 33.94 / 39.05 ms | p50 tied within 0.8%; final 3.3% faster p95 |

An earlier heavy-scene final leg read 34.70 / 44.30 ms and did not reproduce on the alternating
repeat. It is retained here instead of discarded: the repeat and low-load control are why the
result is classified as within run-to-run noise rather than a claimed universal speedup.

## FPS-framework application check

The web game opened on the RTX 2080 at 1280×720, reached its asset-ready marker, produced a
non-blank inspected screenshot, logged zero console errors, and responded to movement input. A
normal real-time `requestAnimationFrame` measurement began after a 90-second settle and held
movement for 30.03 seconds: 1,019 frames, p50 33.3 ms, p95 33.4 ms, p99 50.1 ms, worst 83.4 ms,
741 frames over 33 ms, 13 over 50 ms, and zero console/page errors. The deterministic
6,600-tick playtest result was rejected for FPS because it advances simulation faster than display
presentation. Desktop game verification is unavailable: the published runtime-native 0.3.0
prebuilt-manifest request returned HTTP 404.

The reusable `.claude/skills/measure-steady-state-fps/SKILL.md` now requires hardware-adapter
provenance, a post-load settle, at least 1,000 real frames or 30 seconds, wall-clock presentation
timestamps, repeated same-workload comparisons, and explicit rejection of accelerated tick data.
