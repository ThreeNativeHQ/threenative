# The alpha bar, and the `round:next` recursion defect — 2026-08-15

PRD-120. Phase 0 reproduces the defect §2 of that PRD asserts from a code read; Phases 1–3 record
what `pnpm alpha:bar` observes on this tree. No platform claim, no mobile claim and no iOS claim is
made anywhere in this file.

## Phase 0 — `round:next` treats a PRD in a batch folder as closed

`scripts/round-next.ts:96` reads `docs/PRDs` with a non-recursive `readdirSync`, so `openPrd`
cannot see a PRD that lives in a batch folder. The claim was a code read. This is the run.

The fixture writes **the same PRD body twice** — byte-identical, `**Status:** OPEN` — once at
`docs/PRDs/PRD-998-top-level.md` and once at `docs/PRDs/alpha-readiness/PRD-999-batched.md`, and
names each in turn from the disposition table of an otherwise-complete round ledger. Every other
input is held constant, so the only variable is which directory the file sits in.

```console
$ pnpm tsx repro-recursion.ts
PRD-999 in batch folder (docs/PRDs/alpha-readiness/PRD-999-batched.md, Status: OPEN)
  -> close round 1
     All evidence and dispositions are recorded; close the round.

PRD-998 in top level  (docs/PRDs/PRD-998-top-level.md,                Status: OPEN)
  -> implement PRD-998
     PRD-998 is still open for gap #1; re-measure before closing the round.
```

**Reproduced.** An open PRD in a batch folder does not merely go unreported — it advances the loop
to `close round 1`, the terminal action. Today that silently covers PRD-113 and PRD-114, which the
round-6 ledger names as blockers and which now live under `docs/PRDs/BLOCKED/`, plus every PRD in
`starter-kits/`, `asset-pipeline/`, `studio-hosting/`, `production-readiness-26-08-14/` and
`alpha-readiness/`.

The fixture is reproduction only; no fix landed in this phase. Phase 3 fixes it, with the spec case
observed red at the previous commit — recorded below.

### A second, separate defect this uncovered: `pnpm round:next` is dead on `main`

Not PRD-120's to fix, and recorded here because nothing else reports it.

```console
$ pnpm round:next
Error: Round ledger is missing '## Arms'.
    at section (scripts/round-ledger.ts:71:24)
    at parseArms (scripts/round-ledger.ts:130:18)
    at readRoundLedger (scripts/round-ledger.ts:333:10)
    at nextRoundAction (scripts/round-next.ts:107:18)
```

`docs/verification/round-10-2026-08-16.md` is a baseline round: it opens on the template visual
floor rather than a paired build, and carries `## Baseline`, `## Gap list`, `## Dispositions`,
`## Gates` and `## Notes` but none of `## Arms`, `## Column verdicts`, `## Deletions this round` or
`## Firewall attestation`. `latestRoundFile` picks it, `parseRoundLedger` demands `## Arms`, and the
loop's own next-action command throws before it computes anything.

Nothing here edits round 10 — it is another lane's evidence record and its round is open. The fix is
either the ledger contract admitting a round with no paired arms or round 10 carrying explicit empty
sections, and that is the round owner's call. **`pnpm alpha:bar` reports it as row A4 `unmeasured`
naming the file and the parse error**, which is how it surfaced.

## Phases 1 and 2 — what `pnpm alpha:bar` reads, and what it answers today

Seven rows. Each names the file it reads or the command it runs; a row that can name neither is
refused at construction rather than printed as a pass.

| Row | Evidence source | Kind |
|---|---|---|
| A1 | `npm view <package> versions --json` for every publishable workspace package | registry query |
| A2 | an `alpha-bar` evidence block for A2 in `docs/verification/` | evidence record |
| A3 | an `alpha-bar` evidence block for A3 in `docs/verification/` | evidence record |
| A4 | every `docs/verification/round-*.md`, parsed by `scripts/round-ledger.ts` | derived |
| A5 | `scripts/check-parity-ledger.ts` over the two 2026-08-10 ledgers | command |
| A6 | an `alpha-bar` evidence block for A6 in `docs/verification/` | evidence record |
| A7 | the generated table in `docs/PRDs/alpha-readiness/README.md` | derived |

An evidence record is a fenced ` ```alpha-bar ` block carrying `row`, `status`, `detail` and
`source`. `source` must name the command that produced the result: a block sourced from a PRD
document is rejected, because a bar that reads `**Status:**` lines is the hand-typed table with
extra steps. A malformed block throws rather than emitting a partial row. An absent file or block
is `unmeasured` — never a pass. Two blocks for the same row that disagree are `unmeasured` too,
because a disagreement is an unanswered question, not a tie to be broken by ordering.

Two of the hand-typed table's cells were already wrong when this ran, in opposite directions, which

  platformer round, both arms archived, both proofs recorded, all three columns decided. The row is
  still not green — but for an entirely different reason, one nobody had noticed.

### The negative controls, each observed red

**Deleting a row's evidence makes it `unmeasured`, never a pass.** A5's evidence is the two ledger
files its command reads:

```console
$ mv docs/verification/parity-2026-08-10-r2.md /tmp/held-parity.md
$ pnpm --silent alpha:bar | sed -n '/^A5/,+2p'
A5  unmeasured  Every platform claim is checkable and the ledgers agree
    Ledger(s) missing, so they cannot be compared: docs/verification/parity-2026-08-10-r2.md.
    evidence: pnpm parity:ledger docs/verification/parity-2026-08-10-r2.md docs/verification/tier-1-2026-08-10.md
$ pnpm --silent alpha:bar >/dev/null; echo $?
2
$ mv /tmp/held-parity.md docs/verification/parity-2026-08-10-r2.md
```

The row that was `fail` with its evidence present is `unmeasured` with it absent. It is never
`pass`, and removing the thing that made a row red never makes the command exit `0`.

**Hand-editing the generated README table is caught, then reverted.** Acceptance criterion 3:

```console
$ sed -i 's/| A7 | The bar is runnable, not transcribed/| A7 | Everything is fine actually/' \
    docs/PRDs/alpha-readiness/README.md
$ pnpm --silent alpha:bar | sed -n '/^A7/,+2p'
A7  fail        The bar is runnable, not transcribed
    The generated table in docs/PRDs/alpha-readiness/README.md does not match this run. Rerun pnpm alpha:bar --write.
    evidence: docs/PRDs/alpha-readiness/README.md
$ pnpm --silent alpha:bar >/dev/null; echo $?
2
$ pnpm --silent alpha:bar --write >/dev/null
$ grep -c 'Everything is fine actually' docs/PRDs/alpha-readiness/README.md
0
```

`--write` does not launder the other rows: it regenerates the table, then **re-reads it from disk**
and recomputes A7 against what is now there. A1 red before `--write` is A1 red after it, and the
command still exits `2`.

## What this does not claim

- No row here executed a device lane, a native build or a browser run. A5 compares two ledgers
  written on 2026-08-10; it does not re-run either lane, and PRD-076 still owns that.
- A2, A3 and A6 are unmeasured, not failing: nobody has run those checks, and the bar says so
  rather than guessing.
- A4 is unmeasured because one ledger will not parse — **not** because the answer is known to be no.
  Round 9 looks like a measured paired round to the same parser; the bar declines to claim it while
  a newer ledger is unreadable.
- Nothing here says the repository is at alpha. It says the opposite, with an exit code.
