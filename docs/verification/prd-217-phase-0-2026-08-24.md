# PRD-217 Phase 0 — the input model, proved on Android

**Ran 2026-08-24.** Android emulator (`emulator-5554`, Android 15, 2400×1080 landscape, x86_64,
V8). The Pixel 8 rows of acceptance criteria 1 and 3 are **not** in this record; nothing here
claims them.

## What executed

```sh
# the UI bundle, the game bundle, and an APK through the real packager path
npx esbuild examples/native-smoke/ui/main.ts --bundle --format=esm --outfile=<ui>/main.js --target=es2022
cp examples/native-smoke/ui/index.html <ui>/
node packages/runtime-native/scripts/build-android-first-proof.mjs
node packages/runtime-native/scripts/package-android.mjs \
  --bundle <game.js> --ui <ui> --config <config.json> --output ui-layer.apk

# the scenario
node packages/playtest/dist/runner/cli.js \
  examples/native-smoke/playtests/ui-layer-input.playtest.json \
  --target android --device emulator-5554 \
  --package com.threenative.game --activity com.threenative.runtime.MystralActivity \
  --touch-rotation 3
```

`--touch-rotation 3` is required on this emulator and is a device fact, not a workaround for the
overlay: the display sits at rotation 0 while the activity is orientation-locked to landscape, so
the app's frame is 90° from the panel and the runner's display-derived rotation is right about the
device and wrong about the window. Without it every injected touch lands somewhere else, with or
without an overlay.


Sampled state per labelled step:

| step | pointerDowns | uiIntents | restarts | what it proves |
| --- | --- | --- | --- | --- |
| `ui-ready` | 0 | 1 | 0 | the page loaded and published **2** interactive rects |
| `empty-hud` | 1 | 1 | 0 | a touch on empty HUD space reaches the game |
| `island` | 1 | 2 | 0 | a touch on a published rect does **not**, and its intent crossed to the game |
| `drag-across` | 2 | 2 | 0 | a drag starting on the game and crossing the island stays with the game |
| `moving-origin` | 3 | 2 | 0 | mid-transition, the island's **old** position no longer eats the touch |
| `moving-settled` | 3 | 3 | 1 | settled, the island's **new** position does, and its click fired |

`uiIntents` unchanged across `drag-across` is the half that makes rule 3 non-vacuous: the drag
passed over the island and did not click it. `restarts` is counted separately from `uiIntents` so
the settled probe never races the transition's end.

## The mutation, and its red

**Named mutation: clear the rect registry.** `TnUiOverlay.applyHitRegions` assigns
`regions = new float[0]` instead of the published set — the host keeps receiving publications and
keeps discarding them. This is the mutation PRD-217 names, and it is deliberately *not*
"remove `pointer-events: none`": that CSS property is not the mechanism and a red produced by
touching it proves nothing.

```
RESULT: FAIL
FAIL  resource.GameState.pointerDowns.atSteps
   island: expected 1, got 2 | drag-across: expected 2, got 3
   moving-origin: expected 3, got 4 | moving-settled: expected 3, got 5
FAIL  resource.GameState.uiIntents.atSteps    island: expected 2, got 1
FAIL  resource.GameState.slide.atSteps        island: expected true, got false
FAIL  resource.GameState.restarts.atSteps     moving-settled: expected 1, got 0
```

Every touch falls through to the game and no UI intent ever fires. Restored, green again.

## Two bugs found on the way, both outside this PRD

1. **`AdbAndroidDriver.setPointers` pressed at the previous gesture's coordinates.** A tracking id
   and a coordinate cannot share one emulator event batch, so they are two batches — and the
   identity batch went first, activating the slot at wherever it still sat. Every tap arrived as a
   press at the previous step's position followed by a drag onto the requested one. Fixed by
   positioning the inactive slot first; covered by
   `device-playtest.spec.ts` → "emulator touch batches position a slot before activating it",
   whose red is the argument order reversed.
2. **The example's pointer counter was frame-sampled.** `native-smoke` counted 0→1 transitions in
   `input.raw.pointers`, so a tap whose down and up landed between two frames was invisible — which
   reads exactly like a touch the overlay swallowed. Now counted from the `pointerdown` event.

## Not established here

- **Frame rate with the overlay attached** (criterion 3). Not measured; the emulator is not the
  instrument for it and the Pixel 8 run has not happened.
- **Visual parity against the web build** (criterion 1). No paired capture yet.
- **Multi-touch across the boundary.** Android hands a whole gesture to whichever view claimed its
  first pointer-down, so while a finger is held on a HUD control a second finger anywhere also goes
  to the web view, and vice versa. Stated in `TnUiOverlay`'s header rather than discovered later.
- **`transitionend` never fired in this WebView**, so the page's `slideDone` intent never arrived
  and the assertion that used it was removed rather than left failing. The mid-transition probe's
  non-vacuity rests instead on `restarts == 0` at `moving-origin` against `restarts == 1` at
  `moving-settled`: the island was not at its origin then and was at its destination later.
- **iOS and desktop.** Untouched by this phase.
