## §6.3 — the visual gate, decided before it was touched

`STUDIO_ASSET_ROOT` was `packages/studio/assets`, and `persistTemplateCapture` wrote every
template frame into it as a second copy beside `docs/verification/visuals`. Nothing in the gate
read it back; the only reader was `studioKits()` in Studio's own server, reached from the gate's
spec. So the gate is not a Studio gate — it gates template visuals and always did.

**The gate stays; the branch goes.** `persistTemplateCapture` now takes one root and writes one
file, `IVisualCaptureOptions.studioAssetRoot` is gone, and the spec that asserted both copies plus
Studio's kit listing now asserts the surviving root.

`scripts/release.spec.ts` kept the case that disproved "publish the scaffolder last". Studio was
the package that proved a dependent of `create-threenative` exists, so removing the package would
have quietly removed the coverage; the fixture now names a synthetic dependent and the comment
records why.

Two things the deletion did not cover, both found by running the gate rather than by reading:

- `scripts/verify-golden-path.ts` enumerates `packages/*` from disk, so the untracked
  `packages/studio/{dist,node_modules}` left behind by `git rm` made it read a `package.json`
  that no longer existed. Both directories were removed from disk.
- `hosting/.env` was untracked and therefore survived `git rm`. It was copied out before the
  directory was removed; it is a secret and belongs in the private repository.

## What is deliberately not done

- **`@threenative/studio@0.2.0` is still published and not deprecated.** Deprecation writes to a
  public registry, so the command in §8 is the owner's to run. 0.2.0 shipped with no `license`
  field and therefore granted nobody anything, so the delay exposes nothing.
- **History was not rewritten**, per §1.3. No commit moved, so none of the 197 SHAs cited across
  `docs/` became unresolvable.
