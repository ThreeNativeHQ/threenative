# PRD-222 — the JS-to-C++ crossing tax, isolated — 2026-08-26

**Finding: the native frame is owned by the JS→C++ seam, not the GPU and not game logic.**
Bayview holds ~19 fps on Pixel 8 because ~2,400–5,000 JavaScript→C++ crossings per frame each
pay V8 API machinery — property reads through accessor/lookup paths, global-handle creation,
argument parsing, scope setup. Only ~13 ms of the ~40 ms render phase is inside measured wgpu
commands. Chrome renders the same authored scene at 59.99 fps on the same phone because its
WebGPU calls are plain in-process C++ with no crossing at all.

This session ran three paired device arms, two desktop probes, and one fresh simpleperf
capture. Everything below is development-grade relative evidence (warm phone under the
owner's standing charging waiver), not Tier-1 acceptance evidence.

## Hypotheses eliminated tonight

1. **Swapchain depth / acquire serialization** — `desiredMaximumFrameLatency=3` chained
   through `WGPUSType_SurfaceConfigurationExtras`, verified present in the Android
   compile flags, flat on device while collapsing desktop frame work. Acquire is not the
   Pixel 8 serializer. Knob kept as infrastructure.
2. **String/handle allocation churn as the device-side bridge cost** — interning keys and
   pooling Persistent owners moved bindingNs 10.14 → 9.98 ms only. The remaining cost is the
   per-call property/accessor machinery itself.
3. **Present blocking** — post-staging present is 3–6 ms p50, down from the 15.9 ms
   recorded before upload staging; not a current lever.
4. **Game logic** — update phase 2.4–2.9 ms; Chrome pays it too.

## Conclusion and next levers

The crossing count × per-crossing tax is the defect-shaped structure. Ranked levers toward
the 20 → 30 → 60 vblank ladder:

1. **Fast-path hot-handler argument parsing** (surgical, days→hours): stop doing generic
   property Gets for things the C++ side already holds — e.g. read typed-array element size
   directly off `v8::TypedArray`, skip `BYTES_PER_ELEMENT` reads when the optional arguments
   are absent, cache descriptor field reads. Expected: single-digit ms on device.
2. **Command-batching seam** (structural, the big one): record WebGPU ops in JS into typed
   arrays and cross once per pass/submit; a C++ interpreter replays opcodes against cached
   native handles. Removes both dispatch cost and per-call argument parsing for ~90% of
   crossings. This is the only lever that reaches the unattributed ~27 ms.
3. **After any seam win, re-rank**: `render_pass_end` (7.9% CPU) becomes the next wall.

Commands used this session are the standard loop-log cycle (desktop ninja rebuild +
package-desktop probe; gradle arm builds via `THREENATIVE_RUNTIME_SOURCE` +
`THREENATIVE_GRADLE_ARGS`; `run-as` simpleperf per the memory note).

## Correction — the symbolized profile re-attributes the frame (2026-08-26, later)

The two claims above ("crossing dispatch owns the frame", F8) and in loop-log F12 ("the unnamed
`libv8android` clusters are mostly V8 executing Three.js") were both read off an **unsymbolized**
profile. Resolving those clusters changes the answer. The correction is below; the measurement
that produced it costs no device time.

### Method

`bayview.perf.data` (the 2026-08-25 control capture, 19,612 samples / 19.96 s, `run-as`,
`-g -f 1000`, arm measured 18.85 fps) re-reported against `binary_cache/` with the unstripped
`libv8android.so`, restricted to `SDLThread` (14,015 samples). Three things the earlier reads
missed:

1. `.text` in this V8 build has a **1.6 MB unsymbolized hole** between
   `SetupIsolateDelegate::SetupBuiltins` (ends `0xeb8284`) and `V8::FatalProcessOutOfMemory`
   (`0x1053ce4`). That hole is V8's **embedded builtins blob**, so every `libv8android.so[+…]`
   address in it is generated builtin code, not "bridge dispatch".
2. The `unknown` DSO is a single ~1.8 MB executable region around `0x71a0…` with **no mmap
   record** in the capture — V8's JIT code space. It is 27% of the thread.
3. The two hottest clusters disassemble to identifiable property-lookup code:
   - `0xf06a80–0xf07000` probes a primary hash table at isolate offset `0x4838` and a secondary
     at `0x4850`, then decodes a smi load handler (`ubfx x4, x4, #9, #11`, inobject vs. properties
     backing store, HeapNumber unboxing against the `heap_number_map` root). That is V8's
     **megamorphic stub cache** — the slow path taken when a JavaScript property-load site has
     seen too many object shapes.
   - `0xf510e0–0xf511b0` reads a `Name`'s hash field and linear-probes a hash table sized from
     the receiver — a **name-dictionary lookup**, the slow path for objects V8 has normalized out
     of fast shape mode.

### Where the frame actually goes

Self time on `SDLThread`, converted at 14,015 samples ÷ 377 frames = **37.2 ms of CPU per
frame** (wall frame 53 ms; the difference is present/vblank wait).

| bucket | % SDLThread | ms/frame |
| --- | ---: | ---: |
| V8 JIT-compiled JavaScript (anonymous exec region) | 27.3% | 10.1 |
| V8 embedded builtins, other (ICs, `CallApiCallback`, interpreter) | 14.9% | 5.5 |
| V8 named C++ (API scaffolding, `LookupIterator`, global handles) | 9.1% | 3.4 |
| V8 megamorphic stub-cache probe | 7.3% | 2.7 |
| V8 name-dictionary lookup | 3.2% | 1.2 |
| **V8 total** | **61.7%** | **22.9** |
| `libmystral-runtime.so` (bindings + wgpu-native) | 21.9% | 8.1 |
| `libc` (scudo alloc/free, `memmove`/`memset`) | 11.6% | 4.3 |
| `libGLES_mali.so` | 6.2% | 2.3 |
| `[vdso]` `clock_gettime` | 2.3% | 0.9 |

**The GPU driver is 2.3 ms of a 53 ms frame.** The frame is CPU-bound inside V8, and only
10.1 of V8's 22.9 ms is running the game's JavaScript. The other 12.8 ms is V8 machinery.

### What that machinery is, and why the runtime causes it

The hot named V8 symbols name the mechanism directly (as % of `libv8android` self time):

| symbol | % | what calls it |
| --- | ---: | --- |
| `LookupIterator::Start` + `LookupInRegularHolder` + `NextInternal` + `Object::Get` | 4.6% | every `v8::Object::Get` by name from C++ — the generic, IC-less property path |
| `GlobalHandles::Create` + `NodeSpace::Release` | 3.2% | one `v8::Persistent` per value crossing the seam |
| `Isolate::Enter`/`Exit` + `Context::Enter`/`Exit` | 3.2% | `Isolate::Scope` + `Context::Scope` re-entered on **every** host API call |
| `Value::IsExternal` | 2.1% | argument type checks |
| `HandleScope` ctor + `CreateHandle` | 0.9% | per call and per handle |
| `ExternalReference::Create(v8::ApiFunction*)` | 0.3% | rebuilt on the hot path instead of cached |
| `String::MakeThin` + `StringTable::LookupString` | 0.6% | string internalization at runtime |
| `JSObject::MigrateToMap` | 0.3% | shape transitions on bridge objects |

All of it follows from one design choice, visible in `src/js/v8_engine.cpp` at HEAD: the runtime
reaches V8 through a generic, engine-agnostic `Engine` interface. Every WebGPU object is a plain
JS object assembled at runtime from C++ (`newObject()` → `Object::New` + `SetPrivate`), every
property write goes through **`Reflect.set`** (`setPropertyWithReflect`) rather than
`Object::Set`, every property read goes through `v8::Object::Get` by name, every value handed
across the seam is wrapped in a `v8::Persistent` and tracked in an `unordered_set`, and
`setProperty`/`getProperty`/`newObject` each open an `Isolate::Scope`, a `HandleScope` and a
`Context::Scope`. `nativeCallback` repeats the scope setup and creates one Persistent per
argument, per crossing.

That shape costs twice. Directly: 3.4 ms/frame of V8 API scaffolding plus most of the 4.3 ms of
scudo allocator traffic. Indirectly, and this is the part nothing had named: the JavaScript side
pays **3.9 ms/frame in megamorphic stub-cache probes and dictionary lookups** — Three.js reading
properties off objects whose shapes the bridge builds dynamically. In Chrome those same objects
are C++-backed with one stable map each, so the same Three.js code keeps its inline caches.

### What this retires

- **F8's "crossing dispatch owns the frame"** — the clusters it attributed to dispatch are V8
  builtins, most of them property-lookup ICs reached from JavaScript, not from `nativeCallback`.
- **F12's "the clusters are V8 executing Three.js"** — half right. 27.3% of the thread really is
  JIT-compiled JavaScript, but the clusters themselves are the IC slow paths, and those are a
  cost the bridge's object model imposes on that JavaScript.
- **Crossing *count* as the lever** — already refuted by F12's own arm (1,900 fewer crossings,
  +5% fps). The tax is per *value* and per *property*, not per call, which is why removing calls
  while keeping the object model barely moved.

### Limits of this evidence

The capture predates upload staging and the bridge micro-fixes; its arm ran 18.85 fps against
HEAD's 18.9–19.6, so the shape is unchanged but the absolute ms are ±5%. Sample-to-millisecond
conversion assumes one sample ≈ 1 ms of CPU at `-f 1000`. The `unknown` region is inferred to be
V8's JIT space from "executable, no mmap record, one contiguous 1.8 MB span, hot only on the JS
thread" — it is not symbolized. The two builtin clusters are identified by disassembly, not by a
builtin-name table.

### Next lever, ranked by what the profile says is there

1. **Stop re-entering the isolate and context per host API call** and hoist the cached
   `ExternalReference` — ~3.5% of the thread, no semantic change.
2. **Replace `Reflect.set` with `Object::CreateDataProperty`, and name-keyed `Object::Get` with
   internal fields / cached `v8::Private` slots** — ~4.6% of the thread, and it stops the shape
   churn feeding `MigrateToMap`.
3. **Stop allocating a `v8::Persistent` (+ `unordered_set` insert) per crossed value**; use
   `v8::Local` inside the callback's own `HandleScope` — ~3.2% plus a share of the scudo traffic.
4. **Give WebGPU wrapper objects fixed shapes** — one `ObjectTemplate` per WebGPU class with
   internal fields instead of dynamically-assembled property bags. This is the one that reaches
   the 3.9 ms/frame of megamorphic and dictionary lookups on the JavaScript side.
5. Only after those: re-rank. `render_pass_end` (2.3 ms of Mali command building) is small.

Items 1–3 are mechanical and desktop-verifiable (`phases.render.p50`, never fps — F11). Item 4 is
structural and is the one that would move Bayview toward the 30 fps cell.
