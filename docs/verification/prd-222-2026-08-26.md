# PRD-222 — the JS-to-C++ crossing tax, isolated — 2026-08-26

**Finding: the native frame is owned by the JS→C++ seam, not the GPU and not game logic.**
Bayview holds ~19 fps on Pixel 8 because ~2,400–5,000 JavaScript→C++ crossings per frame each
pay V8 API machinery — property reads through accessor/lookup paths, global-handle creation,
argument parsing, scope setup. Only ~13 ms of the ~40 ms render phase is inside measured wgpu
commands. Chrome renders the same authored scene at 59.99 fps on the same phone because its
WebGPU calls are plain in-process C++ with no crossing at all.

This session ran three paired device arms, two desktop probes, and one fresh simpleperf
capture. Everything below is development-grade relative evidence (warm phone under the
owner's standing charging waiver), not Tier-1 acceptance evidence.

| 1.5% | `nativeCallback` self | |

Game JS execution does not appear as a major separate owner — the thread burns its time in
V8 C++ internals invoked *by the bridge*, not executing gameplay or Three.js math.

A concrete instance of the pattern, from `bindings.cpp`'s `writeBuffer` handler: every call
reads `BYTES_PER_ELEMENT` off the data argument through a full prototype-chain property Get —
428 times per frame — to interpret optional arguments three.js rarely sends.

## Hypotheses eliminated tonight

1. **Swapchain depth / acquire serialization** — `desiredMaximumFrameLatency=3` chained
   through `WGPUSType_SurfaceConfigurationExtras`, verified present in the Android
   compile flags, flat on device while collapsing desktop frame work. Acquire is not the
   Pixel 8 serializer. Knob kept as infrastructure.
2. **String/handle allocation churn as the device-side bridge cost** — interning keys and
   pooling Persistent owners moved bindingNs 10.14 → 9.98 ms only. The remaining cost is the
   per-call property/accessor machinery itself.
3. **Present blocking** — post-staging present is 3–6 ms p50, down from the 15.9 ms
   recorded before upload staging; not a current lever.
4. **Game logic** — update phase 2.4–2.9 ms; Chrome pays it too.

## Conclusion and next levers

The crossing count × per-crossing tax is the defect-shaped structure. Ranked levers toward
the 20 → 30 → 60 vblank ladder:

1. **Fast-path hot-handler argument parsing** (surgical, days→hours): stop doing generic
   property Gets for things the C++ side already holds — e.g. read typed-array element size
   directly off `v8::TypedArray`, skip `BYTES_PER_ELEMENT` reads when the optional arguments
   are absent, cache descriptor field reads. Expected: single-digit ms on device.
2. **Command-batching seam** (structural, the big one): record WebGPU ops in JS into typed
   arrays and cross once per pass/submit; a C++ interpreter replays opcodes against cached
   native handles. Removes both dispatch cost and per-call argument parsing for ~90% of
   crossings. This is the only lever that reaches the unattributed ~27 ms.
3. **After any seam win, re-rank**: `render_pass_end` (7.9% CPU) becomes the next wall.

Commands used this session are the standard loop-log cycle (desktop ninja rebuild +
package-desktop probe; gradle arm builds via `THREENATIVE_RUNTIME_SOURCE` +
`THREENATIVE_GRADLE_ARGS`; `run-as` simpleperf per the memory note).
