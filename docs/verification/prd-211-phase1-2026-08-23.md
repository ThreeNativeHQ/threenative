## Phase 1 — the runtime decodes Ogg Vorbis

### The defect

`decodeAudioFile` (`src/audio/audio_context.cpp`) was one call to `SDL_LoadWAV_IO`. There was no
Vorbis, MP3 or Opus decoder anywhere in the runtime, so **every** native target rejected the `.ogg`
files the browser half of the same source plays — the templates' `pickup.ogg`, and everything
`create-threenative`'s asset workflow emits. On Android that reached the game as
`TN_NATIVE_START_FAILED: decodeAudioData could not decode the supplied audio` and a black screen.
It is not an Android bug; desktop never noticed because every audio proof here fed a WAV assembled
inline by the test itself.

### The one-line mutations

A red that survives the feature's removal proves nothing, so each half of Phase 1 was reverted on
its own line and rebuilt.

**1. The dispatch.** `decodeAudioFile`'s `std::memcmp(data, "OggS", 4) == 0` condition replaced by
`false`, so the Ogg arm exists and is unreachable:

```
native Ogg Vorbis decode contract failed on V8:
a genuine Ogg Vorbis file decodes: decodeAudioData settled with decodeAudioData could not decode the supplied audio.
the decoded Ogg keeps its duration: no buffer to measure
the decoded Ogg carries audio rather than silence: no buffer to measure
the decoded Ogg is resampled to the context rate: no buffer to measure
```

**2. The resampling.** `buildAudioBuffer`'s
`targetSampleRate > 0.0f && std::fabs(targetSampleRate - sourceRate) > 0.5f` replaced by `false`,
so decode still works and the rate is left alone:

```
native Ogg Vorbis decode contract failed on V8:
a half-rate asset is resampled rather than left to play sharp: buffer rate 22050, context rate 44100
```

Each restored, each green again. The two lines fail different assertions, which is the point: the
decode and the pitch fix are separately proved rather than one hiding behind the other.

### The shape of the fix

- `scripts/download-deps.mjs` provisions `stb_vorbis.c` in the existing stb header set, the same
  vendored single-file precedent as `stb_image.h` and `cgltf.h`. Its skip-if-exists guard was
  per **directory**, which meant adding a header to the list provisioned nothing on any checkout
  that already had the others and reported success while doing it; it is now per header.
- `src/audio/vorbis_impl.c` is the single translation unit that compiles it, with
  `STB_VORBIS_NO_STDIO` because the runtime never hands the decoder a path.
- `decodeAudioFile` dispatches on the container magic: `OggS` to `decodeOggVorbis`, everything else
  to the unchanged SDL WAV path. Never on the extension — the hand workaround for this bug was WAV
  *content* under `.ogg` filenames, and it worked precisely because the decoder reads bytes.

### Fail closed

Every stb_vorbis failure returns `nullptr` and reaches the game as the same rejected
`decodeAudioData` a WAV failure produces. Three negative controls run in the same executable:

| Input | Result |
| --- | --- |
| the fixture truncated to 200 bytes | rejects with an `Error` |
| `OggS` followed by deterministic garbage | rejects with an `Error` |
| an Ogg page carrying `OpusHead` (unit lane) | refused; the container is not the codec |

An Ogg container also carries Opus and FLAC, which this runtime does not implement and must not
pretend to. Handing back a buffer of silence would be worse than the black screen this fixes.

### The latent pitch defect — honoured, not filed

`decodeAudioFile` took a `targetSampleRate` and never read it, and
`AudioBufferSourceNode::process` (`audio_context.cpp:288-335`) advances the read head one buffer
frame per output frame with no rate conversion anywhere in the graph. So a buffer that kept its
own sample rate played at `bufferRate / contextRate` speed — a 22,050 Hz asset an octave high and
half as long on a 44,100 Hz context. WAV hid it because the fixtures and most game audio already
matched the context; Vorbis would not have, because 48,000 Hz is an ordinary Ogg rate and would
play about 9% sharp.

Rather than layer Ogg on top of it, `decodeAudioFile` now resamples to `targetSampleRate` for
every container, which is what Web Audio says `decodeAudioData` does. Proved in the same
executable: a 22,050 Hz WAV decoded on a 44,100 Hz context comes back **44,100 frames** long, one
second in and one second out, at the context's rate.

### The audio decode table

| Container | Native verdict | What the preflight says |
| --- | --- | --- |
| RIFF/WAVE | decodes | passes |
| Ogg Vorbis | decodes | passes; **no ffmpeg advice printed** |
| Ogg Opus | refuses | `is Ogg Opus; no native target decodes this container` |
| Ogg FLAC | refuses | named as Ogg FLAC, refused |
| MP3, MP3 (ID3) | refuses | refused |
| FLAC | refuses | refused |
| MP4/M4A, AAC | refuses | refused |

An Ogg file is now read **down to its codec**, not just to its magic number: Vorbis, Opus and FLAC
all begin `OggS`, and a magic-number match alone would have waved an Opus file straight through to
a failure at game start. The refusal names no platform — every native target compiles the same
`decodeAudioFile`, so "the android target's decoder accepts RIFF/WAVE only" was never true even
when Android was the only target anyone had run, and it sent people hunting an Android problem.

The remaining conversion command targets Ogg Vorbis rather than WAV: roughly a tenth of the size,
already what the web build ships, and now decoded natively, so one file serves both halves of the
same source. **No ffmpeg binary is assumed anywhere in the asset pipeline** — the string is advice
in a message, and nothing in `packages/assets` or in any packager invokes it. Transcode-to-WAV was
not implemented and no `.ogg`-renaming step exists outside git history.

### The WebP capability, per target

| Target | Derivation | Source of truth it mirrors |
| --- | --- | --- |
| android | `deriveAndroidWebpSupport` (Phase 2, unchanged) | `third_party/webp-source/libwebp-*` with a `CMakeLists.txt` and no `lib/` |
| desktop | `deriveDesktopWebpSupport` (new) | `third_party/webp/libwebp-*` with **both** `lib/<library>` and `include/`, which is CMake's `WEBP_LIBRARY AND WEBP_INCLUDE_DIR` |
| ios | `deriveIosWebpSupport` (new) | `CMakeLists.txt` excludes `IOS` from the prebuilt branch and builds from source for `ANDROID` only — nothing to read from disk, so it states the exclusion and a test pins it |

A prebuilt install with no `CMakeLists.txt` fails closed on every target and says exactly why,
rather than guessing. A caller that derives nothing still gets `NO_DECODERS`.

### The anti-staleness leg

The disease Phase 2 named — a hardcoded capability going stale the moment the build changes under
it — applies to the audio table too, and there is no CMake option to derive the audio answer from:
one decoder, compiled into every target, no configuration. What stands in for derivation is
`tests/audio-decode-ogg.test.mjs`, which reads `audio_context.cpp` and `asset-preflight.mjs` side
by side and fails when the containers dispatched and the containers claimed stop agreeing — in
either direction. It also fails if the `targetSampleRate` resampling is removed, if `stb_vorbis.c`
leaves the provisioning list, or if any packager stops calling the gate.

## Open — what needs the device

The end-to-end acceptance criterion cannot be closed from here. Ordered, with what each proves:

1. **The bug-5 repro, end to end.** Clean clone → `threenative build --target android` from the
   repository's own `public/` → install → boot. Proves: an APK builds and boots from repo assets
   with zero manual steps, `.ogg` audio plays, and logcat carries
   `[Audio] Decoded audio: N frames, C channels, 44100 Hz (Ogg Vorbis)` instead of
   `TN_NATIVE_START_FAILED`. This is PRD-211's first acceptance criterion and Phase 3's second
   checkbox.
2. **Phase 2's device criterion, in the same boot.** The same APK logs
   `[Mystral] WebP format support: YES` and its WebP-textured models render rather than showing
   white. One install proves both; it was sequenced behind Phase 1 because before Ogg decoded, a
   repo-assets APK died on audio before WebP ever mattered.
3. **Lane naming.** The Pixel 8 and the emulator are separate results and have disagreed before;
   whichever runs must be named as itself.

Also open, and deliberately not done here:

- **iOS.** `deriveIosWebpSupport` and the iOS packager gate are unit-proved and source-pinned only.
  No iOS claim is made and none belongs in acceptance until a physical lane exists.
- **`templates/starter/assets/pickup.wav`.** `main` swapped the template's `pickup.ogg` for a
  39 KB WAV because the runtime could not decode Ogg. That reason is gone on desktop and the WAV
  is ten times the size, but swapping it back should follow the device boot above, not precede it.
- **MP3, AAC, FLAC and Opus** stay honestly undecodable. The message changed; no decoder was added.
