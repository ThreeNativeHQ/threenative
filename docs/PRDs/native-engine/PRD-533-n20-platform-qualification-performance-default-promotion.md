## Context

§15.3 compares against current optimized ThreeNative (projection and batching included), not vanilla
Three.js, and separates the native C++ driver from the native-AOT game driver to isolate binding and
compiler cost. §15.4 sets investment gates (targets, not forecasts). §19 defines completion for a
declared capability profile. Desktop Windows/macOS/Linux and physical Android are the qualification
targets (§2.3); software adapters and virtual displays are not performance evidence. Existing meters:
`pnpm bench:engines` (`scripts/engine-load-test/cli.ts`), playtest `perf`, and the measured record in
`docs/verification/runtime-perf-state.md`, which §3 says must be reproduced natively before it counts.

## Solution

1. Workloads (§15.3): heterogeneous renderables, a moving skinned crowd, streaming Machinefall content,
   and a GPU-heavy visual holdout. Assets, resolution, quality, shaders, camera path and presented
   workload are held equal between arms.
2. Meters: frame p50/p95/p99, CPU stage time, GPU timestamps, startup, peak and steady memory,
   allocations, input latency, scene load/unload, shader compilation, binary size, build time and
   adapter overhead; cold and warm caches reported apart; long frames attributed.
3. Gates (§15.4): about 2× lower CPU in the identified hot paths on two CPU-heavy workloads; about 20%
   better end-to-end frame time on a CPU-bound real game beyond noise; no unexplained GPU-time or
   visual regression; no memory growth across repeated load/unload; AOT binding overhead measured
   against the C++ driver.
4. A perf win never waives a failed compatibility or JS-free gate. If the gates are not met, stop and
   investigate before promotion.
5. Promotion makes `native` the default engine profile with the legacy profile still explicitly
   selectable; retiring legacy is [PRD-535 (N21)](PRD-535-n21-the-js-engine-is-deleted.md), one release later (owner decision 10). The web default moves to the Wasm engine in the same promotion (owner decision 4).

Native `native_engine_update_scaling` analysis (2026-10-08, no engine or gate change). Readings on this Ryzen 9 5900X (L2 512 KB per core, L3 32 MB per CCD), pinned to CPU 8: in the gate's own process 4k 0.39-0.40 ms and 64k 19.4 ms (48-50x; the coordinator's tree read 10.4 ms, 25.6x); 64k alone in a fresh process (`TN_UPDATE_OBJECTS=65536`) 11.0-11.9 ms, 4k alone 0.392 ms, about 30x. The 64k case therefore costs 60 % more when it runs after the 4k and 16k cases in one process: the freed scenes leave a fragmented glibc heap and consecutive objects stop being adjacent. A busy machine moves the 64k reading between 11 and 16 ms in a single session (two sibling lanes were running), so the gate's verdict also depends on neighbours. Work per object is the same at every size: `perf stat` on the 4k and 64k runs gives 33 and 29 L2 misses per object per frame (cache-misses:u 41 M over 300 frames at 4k, 575 M at 64k) and the instruction count per object is equal; only the cost of a miss changes, L3 hit at 4k, DRAM at 64k. A controlled floor, `artifacts/native-engine-perf/walk.cpp` (no engine code, objects walked in order, K lines read and a few written per object, independent loads so the prefetcher helps as much as it can), isolates the mechanism. Per-object ns at 4k / 16k / 64k objects: 14 lines of a 1024-byte object 23.2 / 23.4 / 38.3 (x1.65 at 64k, 26x over 16x the objects); 8 lines of 512 bytes 15.2 / 15.1 / 17.1 (x1.13, 18x); 6 lines of 384 bytes 11.0 / 11.0 / 11.1 (x1.0); 4 lines of 256 bytes 8.2 / 8.4 / 8.3. The step appears exactly where objects x stride passes the L3 slice (25 MB flat, 33.6 MB x1.13, 67 MB x1.65). The gate's 18x limit is 16x more objects at 1.125x the cost per object, so it passes only if the memory the update touches per object per frame is about 500 bytes or less at 64k on a 32 MB L3. The engine touches about 1.4 KB per object (Mesh 256 B, Material 504 B, Record 128 B, position/quaternion/scale/matrix/matrixWorld about 340 B, batch outputs about 130 B) and measures x1.88 per object from 4k to 64k, 15 % above the floor the walk gives for its footprint. The immediate-observation rule (P25) requires every uniform-affecting Material field to be read each frame, which alone is about 250 B, and the two 128-byte matrices per object are another 256 B, so about 800 B is the smallest footprint the current data model allows (the hot fields of Mesh, Material and Record packed into contiguous blocks, no engine API change); by interpolating the walk (an estimate, not built) that would still read about x1.4-1.5 at 64k, 22-24x. In short: the gate measures the L3 capacity of the machine it runs on, not the update algorithm's scaling; it fails here for any engine that touches more than about 500 B per object, and a 32 MB-L3 CPU with a half-size scene would pass the same code. It is left unchanged and red; the options for the owner are to keep it as a known machine-dependent red, to state the limit against the cache-resident cost (4k to 16k, 4.5-5x of an ideal 4x), or to invest in a hot-state redesign of Mesh, Material and Record, which no per-commit tweak substitutes for.
