# PRD-236 — The wave field is the engine's; the ocean is the kit's

**Status: CLOSED, 2026-08-31.** `WaveField`, `Buoyancy3D`, the `sailing` template, numeric TSL
proof, and the enumeration sweep are delivered. Browser template playtests and desktop native
conformance passed; Android/iOS device lanes were not run. See the
[`starter-kit Linchpin evidence`](../../../verification/starter-kits-linchpin-resume-2026-08-31.md).

Source of the borrowed material: [`VictorZakharov/beautiful-water`](https://github.com/VictorZakharov/beautiful-water),
MIT, cloned at depth 1 on 2026-08-28. Every claim in "What the source actually contains" was read
from that clone and is cited by file and line. No claim here has been measured.

Parent batch: [PRD-087](./PRD-087-genre-borrow-ledger.md), whose kit bar and delivery rail this
PRD reuses rather than re-argues.

## The question

A game that floats a boat on an ocean writes the wave function **twice** — once in TSL so the
surface displaces on the GPU, once in TypeScript so the hull knows where the surface is. The two
copies drift, and nothing catches it: the boat sinks into a crest or hovers over a trough, and the
bug looks like a physics bug.

Is that a look problem (the kit's) or a plumbing problem (the framework's)? This PRD's answer:
**the wave shape is the kit's, the guarantee that both evaluations agree is the framework's.**

**Consequence: the `WaterSurface3D` reflection package considered earlier in scoping is
withdrawn before it is written.** There is nothing to absorb — WebGPU needs no render targets for
this, and the WebGL path is Three.js code we would be re-exporting. Building it would have been new
code justified by a borrow that does not exist.

What survives the read is smaller and load-bearing: the wave field, and floating something on it.

## Phase 1 — `WaveField` in `@threenative/core`

One field object, two consumers, one guarantee.

```ts
const swell = new WaveField({ waves: [...], domainWarp: [...] });   // the game's numbers
material.positionNode = swell.displacementNode();                   // GPU
const { height, normal } = swell.sample(x, z, ctx.elapsed);         // CPU, same frame, same answer
```

The framework owns: the CPU evaluator, the matching TSL node, and the fact that they are generated
from **one** parameter array so they cannot disagree. The game owns every number in that array —
amplitude, wavelength, direction, steepness, speed, warp — which is what makes the water look like
anything at all.

**Why this is the framework's under the two questions.** (a) A game cannot portably guarantee the
agreement: the node graph is `three/webgpu`, the evaluator is TypeScript, and the seam must also
hold on the native host. (b) It decides nothing about how anything looks — swap the wave array and
the ocean is a millpond, a storm, or a stylised sine sea, with no package edit.

**Kill switch.** Score with `pnpm tsx scripts/count-loc.ts` against the honest alternative: a game
hand-writing the sum-of-sines in TSL *and* in TS and keeping them in sync. Two implementations
become one. If the score does not show that, this phase is deleted and Phase 3 absorbs the wave
code as generated source.

### Acceptance

1. `packages/core/__tests__/wave-field.spec.ts`: for 64 sample points and 8 times, the CPU
   `sample()` height matches the value the TSL graph computes for the same input to 1e-4.
   **Red-green mutation:** change one coefficient in the CPU evaluator only; paste the failure. A
   red that survives deleting the shared-parameter plumbing proves nothing and does not count.
2. `sample()` on a field with zero waves returns `height: 0` and `normal: (0,1,0)`; a malformed
   wave entry **throws at construction**, not at first sample.
3. Native parity: one entry in `packages/runtime-native/conformance/registry.json` that evaluates
   the same field on the native host and diffs it. A helper admitted for being unportable ships its
   native proof in the same commit.
4. `capabilities.json` entry regenerated by `pnpm build`, with situations including *"float a boat
   on waves"*, *"make water move"*, *"find the water surface height at a point"*.

## Phase 2 — `Buoyancy3D` in `@threenative/physics`

Floats a `RigidBody3D` on any height source, sampling at game-supplied hull points and applying
displaced-volume force plus drag. `CollisionShape3D.heightfield`
(`packages/physics/src/CollisionShape3D.ts:140`) is a **static** heightfield and cannot serve a
moving surface; there is no buoyancy anywhere in `packages/` today.

The game owns hull points, density and drag coefficients. The framework owns the per-point sample,
the force integration and the ordering against the physics step.

**Convention, on by default:** a body given a `Buoyancy3D` floats correctly without further
configuration, `buoyancy: false` turns the force off, and `body.buoyancy.submergedFraction` keeps
reporting either way — turning a convention off must not turn its measurement off.

### Acceptance

1. `packages/physics/__tests__/buoyancy.spec.ts`: a box released above a flat field settles within
   2% of its analytic waterline and stays there for 600 steps.
   **Red-green mutation:** drop the displaced-volume term; paste the sink.
2. A body on a `WaveField` never penetrates the surface by more than one hull-point spacing across
   600 steps.
3. Empty hull-point set throws at construction.

## Phase 3 — the `sailing` starter kit

**Name.** `ocean-boat` was the request; `sailing` is proposed instead, and the choice is the
owner's. The existing kits are single lowercase activity nouns — `racing`, `defense`, `shooter`,
`platformer` — and `sailing` is the word an agent searching by situation would type. If `ocean-boat`
is preferred, nothing else in this PRD changes.

Not a template — a **kit**, to PRD-087's bar: it must boot, play, and be lost.

- **Win:** round four course buoys in order.
- **Fail:** capsize, or the wind dies before the last buoy.
- **First thing edited:** the wind/handling system, not an entity.

Borrowed from `beautiful-water` into `templates/sailing/src/render/`, MIT header retained and
`VictorZakharov` credited in the kit's `README.md`:

| File | Source | Lines |
|---|---|---|
| `water-material.ts` | `src/scene/webgpu-water-material.js` | 510 |
| `water-shaders.ts` | `src/shaders/water/{functions,fragment,vertex}.js` | 1,006 |
| `wave-nodes.ts` | `src/scene/webgpu-wave-nodes.js` | 180 |
| `sky.ts` | `src/scene/sky-webgpu.js`, trimmed to the kit's palette | 298 |

The wave **parameters** move out of the borrowed code into the kit's own `palette.ts`-adjacent
constants so they read as the game's numbers, which is what Phase 1 requires of them.

### Acceptance

4. `--target` proof on native in the same commit as the kit lands.

## Phase 4 — the enumeration sweep

Adding a kit touches at least five hand-maintained lists, and a previous kit landed in one of them
and reddened two gates. Every one, in the landing commit:

`packages/create-threenative/src/index.ts` (`FULL_LOADING_TEMPLATES`) ·
`__tests__/template.spec.ts` · `__tests__/playtest.spec.ts` · `__tests__/loading-screen.spec.ts` ·
`__tests__/scaffold-mcp.spec.ts` · the kit registry that PRD-091 shipped · `pnpm sync:agents`.

**No new CLI verb.** `packages/create-threenative/src/commands.ts:5-8` holds the surface at `build`
and `doctor` and records why: v1 shipped 178 command forms and failed *because models are bad at
discovering novel APIs*. The kit is reached by `--template sailing` and by the capability manifest.
Anything shaped like `threenative add water` is the closed bespoke-CLI-vocabulary reject.

## Build order

Phase 1 and Phase 2 in parallel (2 depends on 1 only at its test seam, which can use a flat field).
Phase 3 after both. Phase 4 lands inside Phase 3's commit, not after it.
