# PRD-462: Prove a bounded slice of the colour lane's materials per frame, and ship that as the default

**Status:** DONE — all five phases and the acceptance criterion landed and verified 2026-09-28. Phases 1–3 are the history that found the poll (and rejected four cheaper mechanisms); phases 4–5 are the spread that shipped, with the exact per-member check kept as a named alternative.
**Date:** 2026-09-28
**Target branch:** `develop`
**Owner request:** close the last row where Godot beats ThreeNative on the PRD-449 scoreboard, the same way a real game benefits.

## Problem

A settled L4@4,096 frame on the quiet machine is **10.0 ms**, of which the render projection's per-frame reconcile (`collapseMs`) is **7.53 ms** — 75% of the whole frame. The shared-material lane, L3, does the equivalent reconcile over the *same* 4,096 moving cubes (`mutationRate 1`) in **~0.8 ms**. Both lanes are the same projection over the same member count; the colour lane pays roughly ten times the per-frame sync, and that difference — not a drift check — is what the can't-batch row is losing to (Godot 5.95 ms for L4@4,096, 1.73 ms at 1,024, against TN's 7.88 and 2.08).

**Phase 1 attributed it, and not where this file expected.** The `InstancedMesh` path in `projection-apply.ts` was the suspect — per-member `setMatrixAt`/`compose`, a whole `instanceMatrix` re-upload, per-member colour writes, per-member map lookups — and the profile says it is the same code in both lanes: `#syncBatched` is 0.27 ms a frame at L3 and 1.17 at L4, and the difference is the cache damage of what runs immediately before it in the same loop, not a different write path. The colour write is already skipped when the colour has not moved, and `flushBatch` already flags the upload once per batch. The cost is `uniformUnchanged`: one `Object.values` and one compare per member per frame, 4.61 ms of L4's 7.01 ms (66%), plus the ~1.3 ms it costs everything that runs after it.

## Design

The poll is at its floor, and that is the finding. Per member it is 1,126 ns in situ, measured apart on the same 4,096 objects: the bulk read alone 816 ns, the compare 369 ns, the small-object component reads and the `defines` walk 251 ns. Each part is load-bearing and each cheaper alternative was measured and is worse:

- **Reading the values by name instead of in one bulk copy: 1,353 ns a member, 2.3x the shipped poll.** The code already says so; the number now has a lane behind it.
- **A change signal instead of a poll** — accessor pairs, which is what this PRD was first filed for — makes a settled material O(1) and was measured 4x cheaper in isolation, and lost at 4,096 on the GPU, because it trades one sequential read of 81 values for 74 lookups into a per-material store. Rejected and reverted; see ## Decisions.
- **Hoisting the poll out of the member loop into its own pass**, to give the material reads and the mesh reads a locality each: 10.95 ms a frame against 7.62 for the interleaved loop it replaced. Worse, because the second walk over 4,096 members costs more than the locality returns.

What is left is what the profile names outside the poll, and it is small: the structure proof asks `displacesVertices` of every material in the scene every frame, and that was three `Reflect.get` calls — runtime calls on a key the engine cannot fold — where a direct read of an absent property is a load it can. That is the fix, and it is the whole of it.

## Decisions

**Spread material checks by default; `everyFrame` kept as the exact alternative — owner, 2026-09-28.** The poll is at its floor, so the remaining question is not how cheaply a material can be checked but how many of them a frame has to check. Phases 1–3 closed that: a version counter misses an in-place write, a Proxy pays the accessor, a per-name read is 2.3x, a separate pass is 1.4x, and a change signal was a wash on the GPU and is reverted. What none of them tried is **checking fewer of them**, which is the one answer a JavaScript game can afford because the *values* a game animates on a material are not the ones it draws. So the default proves a bounded slice per frame, the bound is `ceil(materials / 512)` frames and is reported in `TN_RENDER_PROJECTION` as `materialCheckStaleFrames`, and the exact per-member check it replaced is kept as a named alternative rather than deleted — a game that animates a material's roughness every frame and would rather pay 7.6 ms than accept 8 frames of lag sets `renderer: { projection: { materialChecks: "everyFrame" } }` and gets the poll as it shipped. Two things the default never trades away, both asserted rather than asserted-by-comment: a base-colour edit lands the same frame (that write is O(1) per member) and a material swap is immediate (a changed identity, which the structure proof compares every frame). What it accepts is bounded, measured, and named in the marker: a non-colour material edit leaves the group and is drawn exactly, up to the reported number of frames later.

**Site page waits for this PRD — owner, 2026-09-28.** The public benchmarks page on threenative-site ships once TN beats Godot on the can't-batch row, with charts and a "run it yourself" guide.

**Change notification rejected; code reverted — owner rule (no benchmaxxing, kill switch), 2026-09-28.** The quiet-machine A/B in `4ba74c9c5` (`tn-notify-quiet-{before,after}-{1..4}-2026-09-28.json`, load 3.35–4.77, B A B A B A B A, `--frames 400 --warmup 250`) put L4@4,096 at **+0.33 ms median** against a **1.68 ms** spread between two runs of the *same* build, with half the pairs pointing the other way; L3 moved +0.07 and +0.01, inside its own spread. A frame that a different mechanism already dominates cannot be won by a cheaper drift check, so `bd88d3682` is reverted and the per-frame poll stays. What it had built, and why none of it stays ticked: the watch/dirty-check/restore in `projection-uniform.ts` with release on every `projection-apply.ts` exit path, the budgeted sliced install that fell back to the exact poll, the row that a watched material keeps the fingerprint it was classified with so one drifting member stops re-deriving 4,096 of them (14 existing `projection-uniform-batch.spec.ts` rows plus 7 new, all green here), and the projection on/off pixel match at `?rung=uniform&count=4096` — `compareCaptures` 0 pixel mismatch, ΔE 0, byte-identical on the RTX 2080 at the one-tick and 140-tick settles. The isolated win is real and is the premise this PRD now attacks from the other end: 1.04 µs polled against 0.23 µs watched at 4,096 members, and worth ~0 ms in a frame. Three gaps the mechanism accepted and this PRD inherits as unproven: `delete material.<key>` and `Object.freeze` on a batched material, and a property added to a watched material.

**The row's remaining gap is inside the projection's own 7.5 ms — 2026-09-28.** The host-gap split (`tn-notify-quiet-hostgap-settled-2026-09-28.json`, `TN_HOST_GAP_DETAIL=1`) closed the earlier guess: a 10.03 ms period is 9.10 ms inside the rAF callback — 7.53 of it the reconcile, 0.69 the game transform loop, 0.88 three.js render and submit — against 0.63 ms of native replay (6%), 0.10 present and 0.18 of everything else. There is no ~7 ms of L4@4,096 hiding outside the reconcile to find, which is why phase 1 profiles the reconcile itself.

**The poll is the gap, and it is at its floor — 2026-09-28.** Phase 1's result, recorded here because it closes this file's original question rather than opening one. 66% of the colour lane's reconcile is one `Object.values` plus one compare per member, needed because a member whose material drifted must leave its group instead of drawing with a roughness that is not its own. Every cheaper mechanism was measured on the same 4,096 objects and is worse: a named read per property 2.3x, a separate pass 1.4x, a change signal 4x cheaper in isolation and slower in the frame. **What is left is a change signal that does not exist in JS** — a version counter misses an in-place write to a uniform value, a Proxy pays the accessor's cost — and the one built for this file lost on the GPU and is reverted. A game that wants the last factor of ten here writes one material per colour and stops animating it, and the projection is 0.8 ms.
