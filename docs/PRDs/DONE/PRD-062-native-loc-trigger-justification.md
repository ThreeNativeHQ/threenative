# PRD-062 — the native LOC trigger has no owner

**Status: COMPLETE, 2026-08-10.** The 61,617-line measurement, attribution, area verdicts,
owning-PRD justifications, and residual are recorded in the verification file. The trigger
and `LIMITS.nativeRuntimeLoc` remain unchanged.

**Complexity: 3 → SMALL mode.** One measurement script run, one attribution pass, one
kill-switch verdict per added area, one justification section written into the owning PRDs.

**Blast radius:** this PRD, a justification section in each
owning native PRD, `docs/verification/native-loc-trigger-2026-08-10.md`, and whatever
`packages/runtime-native/` source the kill switch actually deletes. **No public API change,
no gameplay, no template, no package added or removed.**

**Depends on:** nothing unshipped. `scripts/check-budgets.ts` already computes the number.

**Charter authority:** `CHARTER.md` §10b (review triggers), §3 (the kill switch),
`/AGENTS.md` Budgets: *"Crossing one obliges a justification in the owning PRD and a
kill-switch pass over what you added. Never silence a trigger; a number routed around is
worse than no number."*

## 1. Why this exists

The direct budget command on 2026-08-10 produced:

```
budgets trigger: native runtime LOC review trigger: 61617 lines (trigger 50000, +11617).
                 Justify in the owning PRD and run the kill switch over what was added.
budgets ok: 6 framework packages, 3 example workspaces, 5975/15000 framework LOC,
            61617/50000 native runtime LOC, 4 PRD files, largest template 1395 LOC
```

At the historical pre-fixture review snapshot, the trigger had fired on every run for at least a
week and **no PRD carried the
justification it demands.** `OPPORTUNITY-AREAS.md` records 53,851 on 2026-08-09 and calls the overage
"reported, not silently routed around" — but reporting a number is not justifying it, and
nobody had run the kill switch over the 7,738 lines added since that 61,589-line snapshot. A review trigger that fires
forever with no owner is exactly the failure mode §10b exists to prevent: the number stops
carrying information and every future overage inherits an already-numb signal.

This PRD does not raise the trigger. Moving a budget is a `CHARTER.md` change and is not in
scope here; if the honest conclusion is that 50,000 was the wrong number for an owned C++
runtime, this PRD produces the evidence and stops, and the owner decides separately.

## 2. What is actually in the number

`packages/runtime-native/` tracked files, excluding `third_party/`, measured 2026-08-10:

| Area | Lines | First read |
|---|---:|---|
| `src/` | 37,179 | the host itself — render, platform, shims, physics ABI |
| `conformance/` | 5,613 | PRD-054's parity registry and its runners |
| `tests/` | 4,962 | fail-closed contract tests |
| `scripts/` | 4,827 | build, download-deps, release, emulator lanes |
| `include/` | 3,550 | public headers |
| `android/`, `native/`, CMake, iOS, manifests, config | 5,486 | platform packaging and build configuration |
| **Total** | **61,617** | trigger is 50,000 |

That table is a starting read, not the attribution the charter asks for. Phase 0 produces the
real one.

## 3. Phases

**Phase 0 — attribute the growth.** For each commit that moved
`packages/runtime-native/` since the last recorded measurement (53,851 on 2026-08-09) and
since the trigger was first crossed, record lines added, the owning PRD, and the area. Output
is a table in `docs/verification/native-loc-trigger-2026-08-10.md`, generated by a command
that is written down and re-runnable — not by hand-reading the log.

**Phase 1 — the kill-switch pass.** For every area in the Phase 0 table, answer the §3
question in one row: *does this cost more code than the plain alternative?* The plain
alternative for a native host is not "vanilla Three.js" — it is "the game does not run on this
platform at all." Areas where the answer is genuinely *yes, it costs more than it buys* are
deleted in this PRD, however much work they took. Areas where the answer is *no* get a
one-sentence justification and stay.

Three areas need the verdict stated explicitly because they are the cheapest to rationalize:

- `conformance/` (5,613) — is a parity registry runtime code, or is it a gate that belongs
  beside the tests? If it is a gate, say so and record why it counts against a runtime budget.
- `scripts/` (4,827) — build and release orchestration measured as runtime lines.
- `tests/` (4,962) — the fail-closed contract suite. Deleting tests to clear a budget is
  forbidden; if tests are the reason the number is over, that is the finding.

**Phase 2 — write the justification where the charter says it goes.** Each owning native PRD
gains a `## Budget justification` section naming its lines, its kill-switch verdict, and the
date. A PRD already in `done/` or `blocked/` still gets the section; closure does not exempt
it.

**Phase 3 — record what remains.** If the number is still over 50,000 after Phase 1, the
verification file states the residual overage, the areas it lives in, and the single sentence
an owner would need to accept to move the trigger. It does **not** move it.

## 4. Acceptance criteria

1. `docs/verification/native-loc-trigger-2026-08-10.md` exists, attributes every line of the
   overage to a commit and an owning PRD, and names the command that regenerates it.
2. Every area in that table carries a kill-switch verdict with a reason, including a verdict
   for `conformance/`, `scripts/` and `tests/`.
3. Every owning native PRD carries a `## Budget justification` section.
4. Anything the kill switch rejects is deleted in this PRD's commit, with `pnpm typecheck &&
   pnpm lint && pnpm test` green after the deletion.
5. `LIMITS.nativeRuntimeLoc` in `scripts/check-budgets.ts` is **unchanged**, and the trigger
   text is unchanged. Silencing the trigger fails this PRD.

## 5. Self-verification

```sh
pnpm budgets                       # before and after; both outputs pasted into the evidence file
pnpm typecheck && pnpm lint && pnpm test
```

The evidence file records both `pnpm budgets` outputs verbatim. If the number did not move,
say so — "justified, not reduced" is a valid outcome of this PRD and a silent reduction claim
is not.

## 6. What would make this PRD wrong

If Phase 0 finds the growth is dominated by generated or vendored code that the counter should
never have measured, the fix is the counter, not the runtime — and that is a change to
`scripts/check-budgets.ts` with its own test, still inside this PRD. Fixing the counter to
exclude something real, to get under the line, is the failure this PRD is written against.
