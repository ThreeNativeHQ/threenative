## 1. A1 — the publish. **Owner action, and the only thing between here and alpha.**

```text
2 of 8 publishable package(s) are absent from the registry: @threenative/assets,
threenative-engine-mcp. Unpublished workspace version(s): @threenative/core 0.3.0,
@threenative/physics 0.3.0, @threenative/playtest 0.3.0, @threenative/runtime-native 0.3.0,
@threenative/ui 0.3.0, create-threenative 0.2.3.
```

Nothing in the code blocks this. The chain, in order:

1. **CI green on `main`.** `.github/workflows/native-release.yml`'s `gates` job refuses to build
   without a completed successful CI push run for the release commit. There has never been one —
   see [ci-has-never-been-green-2026-08-29](../../verification/ci-has-never-been-green-2026-08-29.md).
   One lane is still red; §3 below is all of it.
2. **Tag `runtime-native-v0.3.0`**, so the four-platform prebuilt build runs and
   `.../runtime-native-v0.3.0/prebuilt-lock.json` stops being a 404. `pnpm publish:check` names
   this as its one non-self-referential finding; the other 55 are the chicken-and-egg that
   `pnpm release` resolves in a single run by design.
3. **`pnpm release --yes`** with registry credentials. Takes the untracked local `.npmrc`
   explicitly (`npm --userconfig .npmrc <command>`), and it is never printed.

**npm versions are immutable.** A bad publish can be deprecated, never replaced.

## 3. `golden-path` — the last red lane, and it is a real finding

Two platformer scenarios — `stomp` and `stomp-rise` — pass and fail run to run **with identical
tick counts**:

| Run | firstTick | lastTick | span | frames | result |
| --- | --- | --- | --- | --- | --- |
| Hardware (RTX 2080) | 27 | 144 | **117** | **115** | pass |
| CI `33317257682` | 48 | 165 | **117** | **115** | **pass** |
| CI on `3672e04e` | 63 | 180 | **117** | **115** | **fail** |

### The likely cause, and the evidence for it

Not the frame rate: `GameLoop` calls `#onUpdate(this.step)` with a **fixed** step, so N ticks is N
identical updates. The span is 117 in every run.

What does move is **`firstTick` — 27, 48, 63.** That is how many ticks elapsed before the
scenario's first step, and it varies with boot time. `Patrol.update(dt)` runs every one of those
ticks from the moment the level loads, walking the enemy between `#from.x` and `#to.x` and
reversing at each end. So when the scenario finally presses a key, **the patrol is at a different
point in its cycle every run** — and a stomp is a landing on a moving target. Same 117 ticks, and
the enemy is somewhere else under the player.

### The fix to try first

The harness already has the vocabulary for exactly this: `setup.place[]` puts a named entity at an
explicit transform before the run, and `frozen: true` sets `PLAYTEST_FROZEN_MARKER` so the game can
suppress its motion. See `packages/playtest/AGENTS.md`, "Scenario-controlled spawn & aim".

Place the patrol deterministically in `stomp.playtest.json` and `stomp-rise.playtest.json` and the
scenario stops depending on how long boot took. Confirm by running the same scenario several times
and checking `firstTick` varies while the result does not.

### What not to do

- **Do not lengthen the waits.** The tick counts already match; padding cannot fix a phase offset,
  it only changes which runs get lucky.
- **Do not delete or quarantine the gate.** This lane is why this session found the scaffold's 40
  failing assertions, the eighteen scenarios that never left the menu, and the harness reporting an
  unmeasured zero as a measurement. A green board that means nothing is what let all three hide.
- **Do not assume it is only these two scenarios.** Any scenario whose subject interacts with an
  entity that moves from boot has the same exposure. Worth an audit once the cause is confirmed.

**The broader point:** a playtest harness whose fixed-step runs are not reproducible cannot prove a
regression from a green run. That is worth more than this one lane.

## 6. Two things another lane reported and nobody has picked up

From the parity-ledger lane, recorded here so they are not lost:

1. **The Android conformance lane is blocked by a stale pin, not by the device.**
   `androidDependencyBlocker()` in `packages/runtime-native/conformance/run-conformance.mjs:1350`
   hardcodes `SDL3-3.2.8.aar`; `third_party` holds `SDL3-3.2.30.aar`. It blocked all 74 rows in a
   fraction of a second. `android/app/build.gradle.kts:34` documents the same bug being fixed by
   finding the AAR by name — this is the fifth hand-written copy of that version. The three
   fixtures in `packages/runtime-native/tests/conformance-runner.test.mjs` hardcode `3.2.8` too.
2. **The Android execution report's exit code bypasses `reportExitCode`.**
   `run-conformance.mjs:1910` overrides it to `1` when `supplemental.androidMultitouch` fails, and
   `check-parity-ledger.ts` imports `reportExitCode` "so the two can never drift apart" and
   therefore cannot see the override. The clean fix is folding the override into `reportExitCode`.

## What landed this session, for context

Three shipped defects, each with a red-green record in `docs/verification/`:

- **`buffer.mapAsync` mapped over bytes the GPU had not written** — the host records `queue.submit`
  into a frame op stream and replays it at the frame boundary, so a same-frame readback mapped
  early and the deferred submit landed on a mapped buffer. Closed A5.
- **Hot reload restored state into the start scene** — a playing session came back on its main menu
  with no entities and no physics world. `Game` now carries the scene name across the update.
- **The starter scaffold failed its own `npm test`** — 40 assertions, because eighteen of twenty-one
  scenarios never left the menu. Plus the harness reporting a fallback distance of `0` as a
  measurement, which `maxDistance` had already refused to do and `minDistance` had not.
