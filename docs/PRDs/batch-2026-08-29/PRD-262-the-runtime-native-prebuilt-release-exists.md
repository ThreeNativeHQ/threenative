# PRD-262 — the runtime-native prebuilt release exists

**Status:** PROPOSED — filed 2026-08-29. **Hard dependency on Lane A**
([PRD-229](../refactor-2026-08-28/PRD-229-the-native-host-is-provable-before-it-is-moved.md) Phase 5,
files 1–2): the release workflow's own `gates` job refuses to build without a green CI push run on
`main` for the release commit, and CI is red on `main` today.

Third lane of [the release batch](./README.md). Blocks [PRD-263](./PRD-263-version-0-3-0-is-installable-by-a-stranger.md).

**Goal: `@threenative/runtime-native` becomes installable as something that actually runs.**
Today it is publishable and inert.

**Complexity:** +2 (workflow + release credentials) +2 (four platform builds, three of them on
runners we do not own) +1 (an irreversible published artifact) = **5 → MEDIUM mode.**

## The problem, measured today at `8491c5d5`

```text
$ gh api repos/ThreeNativeHQ/threenative/releases --jq 'length'
0

$ gh api repos/ThreeNativeHQ/threenative/tags --jq '.[].name' | head -5
runtime-native-v0.1.14
runtime-native-v0.1.13
runtime-native-v0.1.12
runtime-native-v0.1.11
runtime-native-v0.1.10

$ curl -sI ".../releases/download/runtime-native-v0.2.0/prebuilt-lock.json" | head -1
HTTP/2 404
$ curl -sI ".../releases/download/runtime-native-v0.3.0/prebuilt-lock.json" | head -1
HTTP/2 404
```

**Zero releases exist. Five release-shaped tags do.** `.github/workflows/native-release.yml` fires
on `push: tags: runtime-native-v*`, so those five tags either never triggered it or never reached
its `publish` job. Establishing which is the first task here, because the two have different fixes.

`pnpm publish:check` states the consequence in one line:

```text
FAIL  @threenative/runtime-native: No prebuilt release exists at
https://github.com/ThreeNativeHQ/threenative/releases/download/runtime-native-v0.3.0/prebuilt-lock.json;
publish runtime-native-v0.3.0 before publishing the runtime package.
```

### What this has cost every user so far

`@threenative/runtime-native@0.2.0` **is** on the registry. Its `install` hook
(`packages/runtime-native/scripts/install-prebuilt.mjs`) treats a 404 manifest as
`PREBUILT_RELEASE_MISSING` and deliberately does not fail the install — the comment is explicit that
a web game must not lose `node_modules/.bin` over an optional native binary, and that is the right
call. It records the outcome in `prebuilt/install-status.json`.

The result is nonetheless that **no installed user has ever had a working native runtime**. The
framework's own rule — *a feature that works on web only is unfinished* — is currently violated at
the distribution layer rather than in the code: every native capability we ship is real in this
repository and unreachable from npm.

### What the workflow already does

The pipeline is written and looks complete; it has just never produced a release.

| Job | Runner | Produces |
| --- | --- | --- |
| `validate-tag` | ubuntu-24.04 | refuses a tag that does not match `packages/runtime-native/package.json` |
| `gates` | ubuntu-24.04 | refuses unless a completed successful `ci.yml` push run on `main` exists for the commit |
| `build` | ubuntu-24.04 / macos-15 / windows-2025 | `linux-x64`, `darwin-arm64`, `win32-x64` runtimes |
| `build-android` | ubuntu-24.04 | both ABIs, QuickJS and V8 |
| `build-ios-simulator` | macos-15 | unsigned simulator host |
| `publish` | ubuntu-24.04 | `prebuilt-lock.json` from the verified assets, plus the runtimes |

`PREBUILT_KEYS` in `install-prebuilt.mjs` lists **17** artifact keys; only three
(`darwin-arm64`, `linux-x64`, `win32-x64`) are auto-installed by `platformKey`. The rest are fetched
by the Android and iOS packaging lanes. A lock that covers the three desktop keys unblocks
`publish:check`; a lock that covers all seventeen is what the Android and iOS lanes need.

## Solution

Find out why five tags produced no release, fix that, and cut `runtime-native-v0.3.0` from a green
`main`. Nothing here changes the workflow's shape unless the investigation says it must.

**Data changes:** one `prebuilt-lock.json` per release, generated by the `publish` job. Never
hand-written — a hand-authored checksum lock is a supply-chain artifact with no provenance.

## Execution phases

#### Phase 1: Name why five tags produced nothing

**Files:** the record only. **This phase changes no code.**

- [ ] `gh run list --repo ThreeNativeHQ/threenative --workflow native-release.yml --limit 20` and
      record the result verbatim, including an empty one.
- [ ] For each of `runtime-native-v0.1.10` … `v0.1.14`, establish whether the workflow file existed
      at that tag's commit, and whether a run was created.
- [ ] Write the finding down as one of: the workflow postdates the tags; the workflow ran and failed;
      the workflow never triggered. **The fix differs for each — do not skip to Phase 2 on a guess.**

**Revert check:** none; this phase asserts nothing about the tree.

#### Phase 2: Prove the pipeline end to end without publishing 0.3.0

**Files:** possibly `.github/workflows/native-release.yml` (EDIT), the record.

- [ ] **Push `main` first, and get the owner's go-ahead to do it.** `git ls-remote origin main` is
      `7ac47850`, 157 commits behind local `main` and the commit CI last went red on. The `gates`
      job matches `ci.yml` runs by `--commit $GITHUB_SHA --headBranch main`, so a release commit
      that only exists locally can never satisfy it. Local green is necessary and not sufficient.
- [ ] Establish a green `ci.yml` push run on `main` **on the remote** — Lane A made the tree green
      locally (`pnpm typecheck`, `pnpm lint`, `pnpm test` all exit 0 at `73e158c8`). Paste the run
      id. The `gates` job is not bypassable and should not be made bypassable.
- [ ] Exercise the pipeline against a throwaway prerelease tag rather than `v0.3.0`, so a failure
      costs a tag and not a version number.
- [ ] Confirm the `publish` job emitted `prebuilt-lock.json` and that every key it names resolves
      to a downloadable asset with a matching `sha256`.

**Revert check:** at a red CI commit, the same tag must fail at `gates` and publish nothing. Paste
that failure — a release pipeline that would ship off a red tree is the defect this proves absent.

#### Phase 3: Cut `runtime-native-v0.3.0`

**Files:** the tag, the record.

- [ ] Tag the commit that will also be published to npm — **the same tree**, so the lock and the
      package cannot disagree.
- [ ] `curl -sI .../runtime-native-v0.3.0/prebuilt-lock.json` → `HTTP/2 200`. Paste it.
- [ ] Install `@threenative/runtime-native` from a tarball in a directory with no workspace above it
      and confirm `prebuilt/install-status.json` reports `ok: true`.
- [ ] Record which of the 17 `PREBUILT_KEYS` the lock covers, and name any that it does not. **An
      uncovered key is reported, not quietly omitted.**

**Revert check:** point `THREENATIVE_PREBUILT_MANIFEST` at a lock with a wrong `sha256` → the
install fails with the checksum error rather than installing. Paste it.

## Acceptance criteria

- [ ] `pnpm publish:check` no longer reports the `@threenative/runtime-native` prebuilt finding.

- [ ] A fresh install outside this repository writes `install-status.json` with `ok: true`, pasted.
- [ ] The record names why the five earlier tags produced nothing, so it cannot recur unexplained.
- [ ] No step in this PRD asserts a platform it did not execute. An unbuilt key is named as unbuilt.
